Em `t1 = 5; t2 = t1 + 3; x = t2`, o valor final de `x` é sempre 8. Se ninguém observar `t1` e `t2`, podemos substituir as três atribuições por `x = 8`. Uma **otimização** conserva o comportamento observável, incluindo efeitos e exceções definidos pela linguagem, e procura reduzir o custo. Pode atuar no código intermédio antes da geração final ou em representações posteriores.

## Análise de fluxo de dados

A análise associa factos às entradas e saídas dos blocos. Aplica o efeito de cada bloco e combina informação dos blocos ligados, na direção da análise, até estabilizar num **ponto fixo**. Duas análises clássicas:

- **Variáveis vivas**: uma variável está viva num ponto se existe um caminho em que o seu valor atual é lido antes de ser redefinido. Decide o que manter em registos e o que pode ser descartado.
- **Definições que alcançam**: que atribuições podem ter produzido o valor lido em cada uso. Sustenta a propagação de constantes e de cópias.

```
t2 = t1 + 3  # chega a t2 = t1 + 3 ao uso na linha 3? sim, única
x = t2       # chega ao fim? sim, via x
```

Pergunta para trás: de onde veio este valor? Uma definição constante que chega a todos os caminhos permite substituir o nome por essa constante. Uma única definição, por si só, não prova que o valor é constante nem que repetir a expressão é seguro.

A pergunta sobre liveness olha para usos futuros, mas o cálculo propaga-se **para trás**.

### Equações e direção da propagação

Para um bloco `B`, `USE` contém nomes lidos antes de uma definição no bloco e `DEF` contém nomes definidos:

```text
OUT[B] = união de IN[S], para cada sucessor S
IN[B] = USE[B] ∪ (OUT[B] − DEF[B])
```

Começa com conjuntos vazios, exceto os valores observáveis na saída, e repete. Em `x = x + 1`, o `x` antigo pertence a `USE`: a leitura acontece antes da nova definição.

As definições que alcançam propagam-se **para a frente**. Damos uma etiqueta a cada atribuição; `GEN` contém as definições que sobrevivem até à saída do bloco e `KILL` as outras definições dos mesmos nomes:

```text
IN[B] = união de OUT[P], para cada antecessor P
OUT[B] = GEN[B] ∪ (IN[B] − KILL[B])
```

Numa junção, uma variável só é uma constante conhecida se todos os caminhos possíveis concordarem no valor. Se um ramo define `x = 2` e outro `x = 7`, não podemos substituir o `x` seguinte por nenhum deles. Esta decisão sobre valores é diferente da união de definições possíveis. Nas análises de conjuntos acima, a iteração monotónica a partir do vazio acrescenta factos até estabilizar; os ciclos exigem voltar a visitar os blocos.

## Propagação, dobramento e código morto

Bloco básico de entrada:

```
t1 = 5
t2 = t1 + 3
x = t2
y = 10
```

A análise de definições que alcançam diz que, no uso de `t1`, a única definição possível é `t1 = 5`. A **propagação de constantes** substitui: `t2 = 5 + 3`, que o **dobramento de constantes** avalia em `t2 = 8`. Propaga outra vez: `x = 8`. Agora `t1` e `t2` não têm nenhum uso restante, por isso a **eliminação de código morto** remove as duas primeiras instruções. E `y = 10`? Se `y` não está viva à saída do bloco (nenhum sucessor no grafo a lê), remove-se também.

Aqui assumimos variáveis locais, expressões sem efeitos nem exceções, e apenas `x` observável à saída. Uma atribuição a uma variável morta não pode desaparecer se a expressão fizer uma chamada observável ou lançar uma exceção. Sob as hipóteses deste exemplo, o bloco reduzido é:

```
x = 8
```

Neste modelo, a versão reduzida conserva o valor de `x` e não há outros efeitos observáveis. Num compilador real, também é preciso preservar chamadas, escrita em memória observável e exceções, segundo as regras da linguagem.

O estado intermédio ainda conserva as quatro atribuições, mas já não usa os temporários. Só então desaparecem as definições sem usos, depois de verificar que não têm efeitos. A análise de vivacidade isolada não autoriza apagar a avaliação de uma chamada.

| Etapa                  | Instruções relevantes | Justificação                                                 |
| ---------------------- | --------------------- | ------------------------------------------------------------ |
| Propagar `t1`          | `t2 = 5 + 3; x = t2`  | A única definição que chega ao uso de `t1` é 5.              |
| Dobrar e propagar `t2` | `t2 = 8; x = 8`       | A soma é constante e não pode falhar neste modelo.           |
| Eliminar               | `x = 8`               | Os temporários já não têm usos; `y` também não é observável. |

### Vivacidade dentro de um bloco

Apenas `x` está viva à saída do bloco original. Percorremos as instruções de baixo para cima, retirando o destino e acrescentando os operandos lidos:

| Antes da instrução | Variáveis vivas | Passo                                           |
| ------------------ | --------------- | ----------------------------------------------- |
| `y = 10`           | `x`             | O valor antigo de `y` não é necessário.         |
| `x = t2`           | `t2`            | O `x` antigo é substituído; precisamos de `t2`. |
| `t2 = t1 + 3`      | `t1`            | Precisamos do valor que alimenta a soma.        |
| `t1 = 5`           | nenhuma         | O bloco produz os valores sem ler uma entrada.  |

Numa aresta de regresso, um uso no teste da próxima iteração pode manter um valor vivo através de todo o corpo. Por isso, uma única passagem pelos blocos não basta em geral. O exercício do ciclo aplica as mesmas equações até não haver alterações.

:::warning[Otimizar cedo demais esconde erros]
Aplica as otimizações sobre código intermédio já validado e confirma cada transformação no grafo de fluxo. No projeto, depura primeiro com as otimizações desligadas: um erro no código gerado com otimizações ligadas pode estar na otimização ou no código original, e sem a versão simples não distingues.
:::
