Duas threads a escrever na mesma variável sem coordenação podem produzir resultados errados difíceis de depurar. Esta página mostra o mecanismo e a correção.

## A condição de corrida

Uma **condição de corrida** acontece quando o resultado depende da ordem dos acessos entrelaçados das threads. Incrementar um contador parece atómico, mas são três passos, ler, somar 1, escrever. Se duas threads lerem o mesmo valor antes de qualquer uma escrever, um dos incrementos perde-se.

A zona de código que só pode executar numa thread de cada vez chama-se **secção crítica**. Protegê-la é o trabalho da sincronização. Em OpenMP, `#pragma omp critical` protege um bloco de instruções. `#pragma omp atomic` protege uma operação suportada sobre uma posição de memória, como um incremento. Todos os acessos concorrentes a essa posição precisam de proteção compatível; proteger apenas uma das threads não elimina a corrida.

O desenho mostra um modelo simplificado de um incremento perdido. As duas threads leem 0 antes de qualquer escrita, por isso ambas escrevem 1 e o contador termina a 1 em vez de 2. Este entrelaçamento ajuda a perceber o problema, mas não descreve todos os comportamentos possíveis de um programa C com uma corrida de dados.

## Contador partilhado

Os excertos seguintes distribuem 400000 incrementos de um contador partilhado por uma equipa de quatro threads. O resultado correto é 400000. Sem proteção:

```c
long contador = 0;
#pragma omp parallel for num_threads(4)
for (long i = 0; i < 400000; i++) contador++;
printf("%ld\n", contador);
```

:::warning[Uma corrida de dados não tem resultado garantido]
Há acessos concorrentes ao mesmo contador, pelo menos um escreve e não existe sincronização. Em C, esta corrida de dados causa **comportamento indefinido**. Pode aparecer um valor como 287341, mas não há garantia de que fique abaixo de 400000 nem de que mude entre execuções. Obter 400000, mesmo muitas vezes seguidas, não prova que o programa esteja correto.
:::

Com proteção:

```c
long contador = 0;
#pragma omp parallel for num_threads(4)
for (long i = 0; i < 400000; i++) {
    #pragma omp atomic
    contador++;
}
printf("%ld\n", contador);
```

Agora imprime sempre 400000. O preço é a serialização dos incrementos, que a [lei de Amdahl](/cadeiras/cpd/lei-de-amdahl/) conta como fração serial. Daqui sai a regra de ouro da sincronização: secções críticas curtas e raras. Proteger cada incremento de um ciclo longo anula o paralelismo, por isso na prática acumula-se em variáveis privadas e combina-se no fim, como a redução da página de [OpenMP](/cadeiras/cpd/paralelismo-openmp/).
