Ao somar a imagem, cada thread pode atualizar uma soma privada e combinar no fim. Se todas atualizarem diretamente o mesmo contador, os acessos passam a interferir. A sincronização precisa de proteger a operação que mantém o estado correto.

## A condição de corrida

Uma **condição de corrida** acontece quando o comportamento depende da ordem relativa das tarefas. Uma **corrida de dados** é um caso mais específico: acessos concorrentes à mesma posição, pelo menos um escreve, sem a sincronização exigida pelo modelo de memória.

No modelo simplificado de `contador++`, lemos o contador, somamos 1 e escrevemos. Se duas threads lerem 0 antes de qualquer escrita, ambas escrevem 1. Perdemos um incremento.

Em C, uma corrida de dados provoca **comportamento indefinido**. O desenho explica um incremento perdido, não enumera os resultados permitidos pelo programa real. Obter o valor esperado em muitos ensaios não demonstra correção.

## Atomic e secção crítica

Uma transferência entre `a=100` e `b=50` debita 10 de `a` e credita 10 em `b`. Entre as duas escritas, o estado é `(90, 50)`, cuja soma é 140 em vez de 150. Mesmo que cada escrita seja atómica, o par intermédio continua observável. Para conservar a soma nas leituras, protegemos a transferência inteira e as leituras do par pelo mesmo mecanismo.

Uma **secção crítica** protege um conjunto de operações que não pode ser intercalado com outro acesso protegido pelo mesmo mecanismo. Em OpenMP, `critical` permite proteger um bloco. `atomic` protege uma operação suportada sobre uma posição, como um incremento; não torna um bloco inteiro atómico.

Estes são excertos para colocar num programa com OpenMP e `stdio.h`. O primeiro contém uma corrida:

```c
long contador = 0;
#pragma omp parallel for num_threads(4)
for (long i = 0; i < 400000; i++) contador++;
printf("%ld\n", contador);
```

O segundo protege cada incremento:

```c
long contador = 0;
#pragma omp parallel for num_threads(4)
for (long i = 0; i < 400000; i++) {
    #pragma omp atomic
    contador++;
}
printf("%ld\n", contador);
```

O segundo obtém 400000. Há uma barreira implícita no fim de `parallel for`, por isso a leitura feita por `printf` ocorre depois de todos terminarem. Todos os acessos simultâneos ao contador precisam de proteção compatível. Proteger apenas os escritores enquanto outro lê sem proteção durante o ciclo continua a ser um problema.

Incrementos atómicos disputam a mesma posição, mas isso não prova que o programa inteiro deixe de ganhar com paralelismo. Para uma soma, [acumuladores privados com redução](/cadeiras/cpd/paralelismo-openmp/#uma-redução-em-openmp) costumam reduzir essa contenção.

## Barreiras e condições

Uma **barreira** impede uma thread de passar antes de todas as threads do grupo chegarem. É útil entre produzir dados e consumi-los. Não impede duas threads de escreverem no mesmo elemento durante a fase anterior; não substitui um `atomic`, uma secção crítica ou a atribuição de elementos distintos.

Um **mutex** permite a uma thread entrar numa região protegida de cada vez. Uma variável de condição permite esperar por uma condição sobre o estado. Por exemplo, um consumidor espera enquanto a fila está vazia. Esperar liberta o mutex; ao acordar, recupera-o e testa de novo a fila. Outro consumidor pode ter retirado o elemento antes disso. A notificação permite voltar a verificar, não reserva um elemento para esta thread.

## Deadlock e ordem de bloqueios

Um **deadlock** ocorre quando tarefas ficam presas à espera umas das outras. A thread A tem o bloqueio X e espera por Y. A thread B tem Y e espera por X. Nenhuma consegue chegar ao ponto onde liberta o bloqueio que a outra precisa.

Uma correção é impor a mesma ordem em todas as threads: adquirir X antes de Y e libertar depois. Elimina esse ciclo de espera, embora não resolva todas as causas possíveis de bloqueio. A correção tem duas partes: proteger o estado para evitar resultados inválidos e garantir que o programa ainda consegue avançar.
