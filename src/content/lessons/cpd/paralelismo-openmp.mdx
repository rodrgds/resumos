Para calcular o brilho médio da imagem, cada núcleo pode somar os píxeis da sua fatia. No fim, combinamos as somas e dividimos pelo número de píxeis. As fatias são independentes; a soma final depende de todas elas. Esta análise vem antes da diretiva que distribui o ciclo.

## Tipos de paralelismo

No paralelismo **funcional**, executamos tarefas diferentes, como tratar áudio e comprimir imagens. No paralelismo **de dados**, aplicamos a mesma operação a fatias diferentes, como somar partes de um vetor. Num **pipeline**, cada elemento atravessa fases; fases diferentes tratam elementos diferentes ao mesmo tempo.

Considera três fases dedicadas à leitura, transformação e escrita de imagens, com tempos de 2, 3 e 1 ms. Cada fase dispõe de um recurso próprio e de espaço para esperar entre fases. Ignoramos transferências. A primeira imagem termina aos 6 ms. A transformação ocupa 3 ms por imagem, por isso limita as conclusões seguintes a uma por 3 ms.

## Dividir antes de programar

Identifica tarefas e dependências. Decide como dividir os dados, quando comunicar resultados e onde sincronizar. Escolhe uma **granularidade**, a quantidade de trabalho por tarefa, que não faça a coordenação dominar o cálculo.

Se cada iteração tiver custo semelhante, uma distribuição estática costuma ter pouco custo. Se os custos variarem muito, uma distribuição dinâmica pode equilibrar melhor a carga, pagando pela atribuição de trabalho durante a execução. Mede, porque equilíbrio perfeito também não garante ganho se a memória já estiver saturada.

## Trabalho e caminho crítico

Num modelo ideal de tarefas, o **trabalho** $W$ é a soma dos tempos de todas as tarefas numa execução sequencial. O **caminho crítico** $D$ é a maior soma de tempos numa cadeia de dependências. Mesmo com recursos ilimitados, essa cadeia tem de ser respeitada.

Com $p$ unidades iguais, sem comunicação nem outros custos, o tempo não pode ser menor do que $\max(W/p,D)$. É um limite inferior, ou seja não é uma promessa de escalonamento perfeito. Por exemplo, três tarefas independentes de 2 s seguidas de uma combinação de 1 s têm $W=7$ s e $D=3$ s. Com três unidades, as três primeiras tarefas podem correr juntas e a combinação acaba aos 3 s.

O limite pode não ser atingível. Três tarefas independentes e indivisíveis de 2 s em duas unidades têm $W/p=3$ s e $D=2$ s, mas precisam de 4 s: uma unidade terá de executar duas tarefas.

Este modelo obriga a olhar para as dependências. Amdahl usa uma divisão mais simples entre fração serial e trabalho perfeitamente divisível.

## Uma redução em OpenMP

O OpenMP é um modelo de memória partilhada com diretivas de compilador. Este programa completo soma um milhão de uns. Precisa de um compilador C com OpenMP instalado localmente; o motor C do navegador não oferece OpenMP.

```c
#include <omp.h>
#include <stdio.h>
#define N 1000000

int main(void) {
    static double v[N];
    for (long i = 0; i < N; i++) v[i] = 1.0;
    double soma = 0.0;
    double t0 = omp_get_wtime();
    #pragma omp parallel for default(none) shared(v) reduction(+:soma) schedule(static)
    for (long i = 0; i < N; i++) soma += v[i];
    double tempo = omp_get_wtime() - t0;
    printf("soma = %.0f tempo = %.6f s\n", soma, tempo);
    return 0;
}
```

Guarda em `soma.c` e compila com `gcc -O2 -fopenmp soma.c -o soma`. Com esse compilador disponível, corre no terminal:

```sh
OMP_NUM_THREADS=1 ./soma
OMP_NUM_THREADS=4 ./soma
```

`parallel for` cria uma equipa e distribui as iterações. `i` é privado a cada thread; `v` é partilhado e só lido. `default(none)` obriga a declarar o tratamento dos dados que precisam dessa decisão. A cláusula `reduction(+:soma)` dá a cada thread uma soma privada, inicialmente zero, e combina-as no fim. Sem a redução, as atualizações de `soma` criariam uma corrida de dados.

Com oito uns e duas fatias de quatro, as somas privadas são 4 e 4. A combinação produz 8. Não há uma atualização partilhada por cada elemento. ## Correção e custo

Neste programa, a soma correta é 1000000. Para valores gerais em vírgula flutuante, mudar a associação das adições pode alterar o arredondamento. Em precisão binária de 64 bits, `(1e16 + -1e16) + 1` dá 1, mas `1e16 + (-1e16 + 1)` dá 0: no segundo caso, o 1 perde-se no arredondamento da soma interior. A redução pode agrupar valores noutra ordem, por isso não exige igualdade bit a bit à soma sequencial.

O tempo medido inclui criar a equipa, somar e combinar, mas não inclui inicializar o vetor. Repete medições para distinguir variação de ganho, porque uma só medição confunde ruído com efeito. Comparar uma e quatro threads mede esta versão, não necessariamente o ganho face à melhor implementação sequencial.

Se os tempos forem 0,32 s e 0,09 s, $S_4\approx3{,}56$ e $E_4\approx88{,}89\%$. São valores ilustrativos. Num vetor curto, o custo de coordenação pode superar o trabalho útil.

Uma redução resolve acumulações compatíveis, não qualquer dependência. O ciclo `a[i] = a[i-1] + x[i]` continua a precisar de uma estratégia que respeite os resultados anteriores.
