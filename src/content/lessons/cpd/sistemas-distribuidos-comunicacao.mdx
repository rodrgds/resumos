Num sistema distribuído, processos com memória própria cooperam por mensagens. Cada processo só conhece o seu estado e o que já recebeu. Uma máquina pode falhar enquanto outras continuam, uma **falha parcial**.

## Modelos de comunicação

Na **troca de mensagens**, a aplicação envia e recebe dados explicitamente. Uma **invocação remota**, RPC, oferece uma chamada a uma operação noutro processo: serializa os argumentos, envia-os e devolve uma resposta. Um ponteiro local não tem o mesmo significado noutra máquina; os dados precisam de uma representação acordada.

O **multicast** dirige uma mensagem a um grupo. Um envio não prova que todos a receberam nem que a entregaram na mesma ordem. As garantias dependem do protocolo usado.

| Transporte | O que oferece                                                                                      | O que a aplicação ainda decide                               |
| ---------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| TCP        | Fluxo de bytes ordenado, com retransmissão de dados perdidos enquanto a ligação consegue progredir | Fronteiras dos pedidos, timeouts e significado das respostas |
| UDP        | Datagramas, preservando as fronteiras de cada mensagem entregue                                    | Tratamento de perda, duplicação e reordenação                |

TCP não preserva as fronteiras dos teus `write`: uma leitura pode receber parte de um pedido ou vários juntos. Define um enquadramento, como uma linha por mensagem ou um tamanho antes do conteúdo. Nem TCP nem UDP garantem que uma operação da aplicação executou só por o envio local ter terminado.

## Atraso, timeout e repetição

Num modelo **síncrono**, há limites conhecidos para os tempos de comunicação e processamento. Num modelo **assíncrono**, não podemos usar um limite conhecido para concluir que um processo morreu. Um timeout cria uma suspeita, não uma prova. Também pode haver uma partição da rede que impeça processos vivos de comunicar.

Considera `debitar(10)`. O servidor debita 10 euros, mas a resposta perde-se. Se o cliente repetir como uma nova operação, pode debitar mais 10 euros. Já `definir_estado("pago")` é **idempotente** quanto ao estado: repetir o mesmo pedido tem o mesmo efeito que aplicá-lo uma vez. Ler a hora não altera estado, mas as respostas de duas leituras podem diferir.

Uma solução para o débito usa um identificador de pedido estável. O servidor regista o identificador e o resultado e, ao receber uma repetição, devolve o resultado guardado. Para sobreviver a falhas, o registo e o efeito precisam de uma atualização atómica e durável. Guardar só em memória perde a proteção após reiniciar.

**Pelo menos uma vez** permite repetições até obter resposta, podendo repetir efeitos. **No máximo uma vez** evita executar duplicados, mas não garante que o pedido execute. Nenhuma delas dá, por si só, ao cliente conhecimento do resultado após qualquer falha.

## Um servidor local em Go

Este programa completo atende ligações TCP uma de cada vez. Escuta apenas no computador local. A quebra de linha delimita a resposta e fechar a ligação indica o fim do fluxo.

```go
package main

import (
    "fmt"
    "log"
    "net"
    "time"
)

func main() {
    ln, err := net.Listen("tcp", "127.0.0.1:8080")
    if err != nil {
        log.Fatal(err)
    }
    defer ln.Close()
    for {
        conn, err := ln.Accept()
        if err != nil {
            log.Print(err)
            continue
        }
        if err = conn.SetWriteDeadline(time.Now().Add(2 * time.Second)); err != nil {
            log.Print(err)
            conn.Close()
            continue
        }
        if _, err = fmt.Fprintln(conn, time.Now().Format(time.RFC3339)); err != nil {
            log.Print(err)
        }
        conn.Close()
    }
}
```

Precisas de Go instalado. Guarda em `servidor.go`, corre `go run servidor.go` e mantém esse terminal aberto. Noutro terminal, `nc 127.0.0.1 8080` recebe uma linha com a hora, como `2026-03-14T10:30:00Z`. A hora real e o fuso dependem do computador. Ctrl C termina o servidor.

No código, `:=` declara e atribui uma variável, `defer` agenda uma operação para quando a função termina e `for` sem condição repete até ser interrompido. O teste `err != nil` trata uma operação que falhou, em vez de usar uma ligação inválida.

Uma **goroutine** é uma execução concorrente gerida pelo runtime Go. Um canal Go liga goroutines no mesmo programa; não transporta dados entre máquinas. Num canal sem buffer, como `make(chan string)`, um envio espera por uma receção correspondente:

```go
package main

import "fmt"

func main() {
    ch := make(chan string)
    go func() { ch <- "pontual" }()
    fmt.Println(<-ch)
}
```

O resultado é `pontual`. Este canal sincroniza as duas goroutines. Para comunicar com outro processo, usa sockets ou outra biblioteca de comunicação de rede.

## Servidores com estado e eventos

Um servidor **sem estado de sessão** não precisa de recordar pedidos anteriores do cliente para interpretar o próximo. Isso não significa ausência de base de dados. Um servidor **com estado de sessão** mantém, por exemplo, a fase de uma transferência; recuperar ou replicar esse estado faz parte do protocolo.

Um servidor iterativo trata um pedido de cada vez. Um servidor com threads ou goroutines pode tratar outros pedidos enquanto um espera por I/O, mas precisa de coordenar o estado partilhado. Um servidor baseado em eventos usa I/O não bloqueante e mantém o estado de cada pedido entre eventos. Bloquear o seu ciclo de eventos pode atrasar todos os clientes.

Ter só uma thread não elimina todos os problemas de concorrência. Dois pedidos podem ler o mesmo saldo e, em eventos posteriores, gravar resultados incompatíveis. A unidade que precisa de proteção é a operação sobre o estado, não apenas cada instrução isolada.

## Ordenar mensagens

A ordem **FIFO** preserva a ordem de cada emissor. A ordem **causal** respeita dependências: se B envia uma mensagem depois de receber a de A, entrega-se a de A antes da de B. A ordem **total** faz os destinatários concordarem na ordem de entrega, mesmo para mensagens independentes. Ordem total, por si só, não exige respeitar a causalidade.

Estas propriedades não são garantias de entrega fiável. TCP ordena bytes de uma ligação; não estabelece uma ordem global entre vários emissores. Difundir uma atualização a três réplicas pode exigir confirmação, eliminação de duplicados e uma política de ordem. Se C não confirma, o coordenador sabe apenas que ainda não recebeu a confirmação, não que C morreu.
