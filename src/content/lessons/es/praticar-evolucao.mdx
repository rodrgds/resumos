<Exercise
  id="es-manutencao-tipos"
  revision={3}
  title="Porque mudamos o sistema?"
  explanation="/cadeiras/es/construcao-evolucao/#manutenção"
  answer={{
    kind: 'self',
    checklist: [
      'Classifiquei correção como corretiva e API como adaptativa.',
      'Classifiquei recorrência como perfetiva.',
      'Classifiquei a extração preventiva, se preservar comportamento.',
      'Distingui aumentar o máximo por pedido novo de corrigir um limite mal implementado.',
    ],
  }}
>
  <div>
    Classifica: corrigir uma reserva duplicada; adaptar à nova API de salas;
    acrescentar recorrência; extrair duplicação sem alterar resultados.
    Considera ainda a mesma mudança no código, máximo de 120 para 180 minutos,
    em dois contextos: a escola altera a regra de 120 para 180; a escola sempre
    exigiu 180, mas o programa usa 120. Classifica e justifica a diferença.
  </div>
  <div slot="hint">
    O motivo principal importa mais do que o tamanho da alteração.
  </div>
  <div slot="hint-more">
    Pergunta se corrigimos um defeito, mudamos ambiente, acrescentamos
    capacidade ou reduzimos risco futuro.
  </div>
  <div slot="solution">
    São, respetivamente, manutenção corretiva, adaptativa, perfetiva e
    preventiva. A última pode usar refactoring se preservar resultados. Uma
    alteração real pode ter vários motivos. Classifica pelo motivo principal e
    explica o contexto. No primeiro contexto do limite, responder ao pedido novo
    é perfetiva. No segundo, restaurar a regra já acordada é corretiva. O diff
    pode ser igual; o motivo e o comportamento anteriormente esperado distinguem
    as classificações.
  </div>
  <div slot="mistakes">
    Não chames adaptativa a qualquer funcionalidade nova. Não confundas
    preventiva com uma mudança já necessária por erro observado.
  </div>
</Exercise>

<Exercise
  id="es-ci-entrega"
  revision={2}
  title="Pipeline verde e produto entregue"
  explanation="/cadeiras/es/construcao-evolucao/#entrega-e-implantação"
  answer={{
    kind: 'self',
    checklist: [
      'Identifiquei continuous delivery com decisão de implantação.',
      'Distingui implantação automática de preparação automatizada.',
      'Limitei a evidência aos checks executados.',
    ],
  }}
>
  <div>
    Cada integração produz um artefacto testado. Uma pessoa decide quando o
    implantar. É continuous delivery ou continuous deployment? O pipeline verde
    prova a validação com utilizadores?
  </div>
  <div slot="hint">
    Pergunta se a implantação acontece sem decisão humana adicional.
  </div>
  <div slot="solution">
    É continuous delivery se a preparação mantém o produto entregável e a
    implantação depende de decisão humana. Continuous deployment implanta
    automaticamente após os critérios. O verde demonstra os checks executados
    nessa revisão, não que todas as necessidades foram validadas com
    utilizadores.
  </div>
  <div slot="mistakes">
    Não confundas um artefacto construído com uma versão já em uso. Não atribuas
    ao pipeline requisitos que nunca verificou.
  </div>
</Exercise>
