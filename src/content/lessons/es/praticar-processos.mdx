<Exercise

  title="Duas formas de avançar"

  answer={{

      'Identifiquei incremento ao acrescentar reservas.',
      'Expliquei que as ideias podem coexistir.',
    ],

>
  <div>
    A equipa redesenha três vezes o mesmo protótipo de pesquisa, sem entregar
    nova capacidade. Depois acrescenta reserva a uma versão que já consultava
    salas. Classifica cada mudança.
  </div>
  <div slot="hint">
    Pergunta se melhorámos a mesma solução ou acrescentámos capacidade.
  </div>
  <div slot="hint-more">
    Muitas versões de um desenho não implicam funcionalidades utilizáveis
    adicionais.
  </div>
  <div slot="solution">
    As três revisões são iterações. Acrescentar reservas é um incremento da
    capacidade do produto. A construção desse incremento também pode envolver
    várias iterações.
  </div>
  <div slot="mistakes">
    Não uses iterativo e incremental como sinónimos. Entrega frequente não diz,
    por si só, o que foi acrescentado.
  </div>
</Exercise>

<Exercise
  id="es-rup-risco"
  revision={1}
  title="Código na elaboração"
  explanation="/cadeiras/es/processos-software/#rup"
  answer={{
    kind: 'self',
    checklist: [
      'Expliquei que disciplinas atravessam as fases.',
      'Liguei o protótipo à redução de risco arquitetural.',
      'Indiquei a evidência pretendida, uma reserva confirmada por intervalo.',
    ],
  }}
>
  <div>
    Durante a elaboração do RUP, a equipa implementa um pequeno serviço para
    testar reservas concorrentes. Está a saltar indevidamente para construção?
    Justifica.
  </div>
  <div slot="hint">Uma fase do RUP não corresponde a uma única atividade.</div>
  <div slot="hint-more">
    A elaboração precisa de avaliar a arquitetura nos cenários críticos.
  </div>
  <div slot="solution">
    Não. A elaboração pode incluir implementação e testes para estabilizar a
    arquitetura, porque o protótipo testa o risco de concorrência antes de
    desenvolver as funcionalidades dependentes. A fase é identificada pelo
    objetivo predominante, não pela ausência de código.
  </div>
  <div slot="mistakes">
    Não confundas as fases do RUP com departamentos estanques de requisitos,
    desenho, código e teste.
  </div>
</Exercise>

<Exercise
  id="es-processo-incerteza"
  revision={1}
  title="Planear o conhecido e investigar o incerto"
  explanation="/cadeiras/es/processos-software/#escolher-um-processo"
  answer={{
    kind: 'self',
    checklist: [
      'Mantive marcos e critérios para a migração com data fixa.',
      'Propus experimentar a API antes de assumir toda a integração.',
      'Defini uma pergunta e um resultado que orientam a decisão seguinte.',
    ],
  }}
>
  <div>
    A escola tem uma data fixa para substituir a aplicação antiga e regras de
    migração conhecidas. A nova API de horários ainda pode devolver dados
    incompletos. Propõe uma forma de organizar o trabalho e uma experiência
    inicial, sem escolher um nome de processo como justificação suficiente.
  </div>
  <div slot="hint">
    As duas partes do projeto têm graus diferentes de incerteza.
  </div>
  <div slot="hint-more">
    Que observação te faria aceitar ou rejeitar a API como fonte de
    disponibilidade?
  </div>
  <div slot="solution">
    Planeamos migração, validação dos dados e marcos de aprovação com a data
    conhecida. Antes de depender da API, fazemos uma experiência delimitada que
    compara horários de salas de teste com uma fonte de referência e regista
    falhas e latência. Se faltarem dados críticos, revemos a fonte ou o âmbito.
    Podemos trabalhar em iterações e orientar o primeiro ciclo pelo risco; os
    compromissos conhecidos continuam a exigir planeamento.
  </div>
  <div slot="mistakes">
    Não adies o risco para a integração final. Não afirmes que iterações
    dispensam datas e planos, nem que uma data fixa proíbe feedback.
  </div>
</Exercise>
