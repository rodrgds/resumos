Com a base de dados a guardar e a proteger os dados, falta a aplicação que os mostra e os altera. O Laravel organiza essa aplicação em peças com papéis fixos: a **rota** recebe o pedido HTTP, o **controlador** executa a lógica, o **modelo** fala com a tabela e a **vista** gera o HTML. Middleware, autorização e outros serviços podem participar no percurso. Nem todas as respostas usam uma vista HTML.

## O recurso Sessões de ponta a ponta

No percurso de um pedido, distingue o software pelo papel:

| Peça          | Papel                                                      | Exemplos                               |
| ------------- | ---------------------------------------------------------- | -------------------------------------- |
| Navegador     | Pede recursos e apresenta a página                         | Firefox, Brave                         |
| Servidor HTTP | Recebe pedidos e devolve recursos ou encaminha a aplicação | Apache HTTP Server, Nginx              |
| Aplicação     | Executa regras e produz a resposta dinâmica                | Uma aplicação Laravel executada em PHP |
| Base de dados | Guarda e consulta dados                                    | PostgreSQL                             |

O servidor pode devolver um ficheiro estático ou obter uma resposta da aplicação. O navegador é o cliente deste percurso. O motor que interpreta e apresenta HTML no navegador não substitui o servidor HTTP.

Um **recurso** é algo identificável por um endereço, como uma sessão ou a lista de sessões. A aplicação define que operações permite sobre ele. As sessões da loja são um recurso. Estas rotas usam métodos HTTP com a semântica esperada; uma aplicação REST também tem outras condições, explicadas em [HTTP](/cadeiras/lbaw/http-estado/#rest-e-estado-da-aplicação):

```php
Route::get('/sessoes', [SessaoController::class, 'index']);
Route::post('/sessoes', [SessaoController::class, 'store'])->middleware('auth');
```

O `GET` lista, o `POST` cria. O controlador recebe o pedido já encaminhado e devolve uma resposta, sem gerar HTML à mão:

```php
// Excerto: Request, Gate e Sessao são importados no controlador.
class SessaoController extends Controller
{
    public function index()
    {
        $sessoes = Sessao::where('data_hora', '>', now())
            ->orderBy('data_hora')
            ->get();
        return view('sessoes.index', ['sessoes' => $sessoes]);
    }

    public function store(Request $request)
    {
        Gate::authorize('create', Sessao::class);
        $dados = $request->validate([
            'evento_id' => 'required|exists:eventos,id',
            'data_hora' => 'required|date|after:now',
            'preco' => 'required|numeric|min:0',
            'lotacao' => 'required|integer|min:1',
        ]);
        Sessao::create($dados);
        return redirect('/sessoes', 303);
    }
}
```

O método `validate` é o ponto a fixar: se os dados cumprirem as regras, devolve os campos validados. Não os sanitiza para todos os destinos. Se falharem num formulário web, interrompe e redireciona com os erros; um pedido que espera JSON recebe normalmente 422. A regra `exists:eventos,id` repete na aplicação a chave estrangeira da base de dados, para dar erro amigável antes do erro técnico. A regra `after:now` valida a criação de uma sessão futura. Sessões antigas continuam a existir no histórico.

Antes do exemplo, associa `SessaoPolicy` ao modelo. O seu método `create` recebe o utilizador autenticado e permite apenas os papéis que podem gerir sessões. `Gate` é a facade `Illuminate\Support\Facades\Gate`; recusa com 403 quando a policy não permite. O formulário usa `@csrf` e apresenta os erros com `@error` e os valores anteriores com `old(...)`.

## Migração e modelo

A tabela nasce de uma **migração**, código versionado que cria e altera o esquema. Este excerto cria as colunas e a FK da tabela do [esquema relacional](/cadeiras/lbaw/esquema-relacional/), com campos adicionais de criação e atualização:

```php
Schema::create('sessoes', function (Blueprint $table) {
    $table->id();
    $table->foreignId('evento_id')->constrained('eventos');
    $table->dateTime('data_hora');
    $table->decimal('preco', 8, 2);
    $table->integer('lotacao');
    $table->timestamps();
});
```

O excerto de migração não declara os `CHECK` de preço e lotação. Mantém essas garantias no SQL de PostgreSQL, além da validação do formulário. Se usares o esquema sem `created_at` e `updated_at`, o modelo deve declarar `public $timestamps = false`.

O modelo liga a classe à tabela e declara o que se pode preencher em massa:

```php
class Sessao extends Model
{
    protected $table = 'sessoes';
    protected $fillable = ['evento_id', 'data_hora', 'preco', 'lotacao'];

    public function evento()
    {
        return $this->belongsTo(Evento::class);
    }
}
```

O nome da tabela é explícito porque as convenções de pluralização não garantem os nomes portugueses do esquema. Os restantes modelos precisam do mesmo cuidado. O `belongsTo` espelha a associação do UML: cada sessão pertence a um evento. A partir daqui, `$sessao->evento->titulo` navega da sessão ao evento sem SQL escrito à mão.

## Um POST que falha a validação

Com um utilizador autorizado a criar sessões, preenche o formulário de nova sessão com lotação `0` e carrega em guardar. O pedido `POST /sessoes` chega ao `store`, o `validate` rejeita `lotacao` por violar `min:1`, e o utilizador volta ao formulário com a mensagem de erro junto ao campo e os restantes valores preservados. Nenhuma linha tocou na base de dados: a validação correu antes de qualquer escrita.

Se a autorização e a validação passassem, o `create` inseria a sessão e o redirecionamento voltava à lista. Se dois compradores disputarem o último lugar, a validação anterior à compra pode estar desatualizada. O [protocolo de concorrência](/cadeiras/lbaw/triggers-transacoes/) decide qual compra pode confirmar.

O bloco seguinte isola a condição «inteiro positivo». Usa um inteiro PHP; um formulário HTTP enviaria texto, que o validador Laravel também precisa de interpretar:

## Entrar e proteger rotas

A loja tem registo e login nos requisitos, e as compras exigem saber quem compra. A autenticação no Laravel segue o mesmo molde do recurso: formulário, validação e tentativa de entrada.

```php
public function entrar(Request $request)
{
    $dados = $request->validate([
        'email' => 'required|email',
        'palavra_passe' => 'required',
    ]);
    if (!Auth::attempt([
        'email' => $dados['email'],
        'password' => $dados['palavra_passe'],
    ])) {
        return back()->withErrors([
            'email' => 'Credenciais inválidas.',
        ]);
    }
    $request->session()->regenerate();
    return redirect('/sessoes');
}
```

Este fragmento pressupõe o modelo autenticável e a coluna `password` do starter Laravel. Para usar `utilizadores.palavra_passe_hash` do esquema anterior, configura o provider e o modelo para essa tabela e esse atributo de hash. A chave `password` das credenciais continua a receber a palavra-passe em claro para a API a verificar. Não passes o hash como credencial.

O `Auth::attempt` verifica a palavra-passe com hash e inicia a sessão. Se falhar, volta atrás com erro genérico de propósito: dizer "email certo, palavra-passe errada" ajuda quem ataca a adivinhar contas.

Com a entrada feita, protege as rotas que precisam de comprador autenticado com o middleware `auth`:

```php
Route::middleware('auth')->group(function () {
    Route::post('/compras', [CompraController::class, 'store']);
});
```

Quem não entrou é redirecionado para o login em vez de chegar ao controlador. O middleware auth verifica autenticação. A autorização sobre a operação e o recurso precisa de uma policy, gate ou verificação equivalente no servidor.

## Ambiente e ferramentas

O ambiente do projeto usa PHP e Laravel para a aplicação, Composer para as dependências, PostgreSQL para os dados e Docker Compose para a infraestrutura local. Git e GitLab guardam versões e permitem rever as alterações do grupo. Usa o template e o guia da edição atual, ligados na [apresentação da cadeira](/cadeiras/lbaw/#referências-complementares).

Uma **imagem** Docker descreve o sistema de ficheiros e a configuração que servem para criar contentores. Um **contentor** é uma instância em execução dessa imagem. Um volume conserva os dados fora da camada descartável do contentor. Parar ou recriar o contentor não é o mesmo que apagar o volume da base de dados.

## Blade: gerar uma vista

`view('sessoes.index', ['sessoes' => $sessoes])` passa os dados à vista `resources/views/sessoes/index.blade.php`. Blade compila o template para PHP:

```blade
<ul>
  @foreach ($sessoes as $sessao)
    <li>{{ $sessao->evento->titulo }}: {{ $sessao->data_hora }}</li>
  @endforeach
</ul>
```

`@foreach` repete o elemento para cada sessão. `{{ ... }}` escreve texto escapado para HTML. O acesso a `evento` precisa da relação do modelo e pode provocar consultas adicionais, como veremos no caso N+1.

## Separar responsabilidades no pedido

Uma rota escolhe a operação. Middleware pode verificar sessão e proteção CSRF antes do controlador. O controlador coordena o caso de uso, a policy decide a autorização, o modelo representa dados e relações, e a vista produz a representação. Nem todos os pedidos usam uma vista HTML: uma API pode devolver JSON, e uma operação pode redirecionar ou devolver 204.

**Validação** pergunta se os dados têm o formato e o domínio esperados. **Autorização** pergunta se esta pessoa pode executar esta operação sobre este objeto. **Autenticação** identifica a pessoa. As três são necessárias em contextos diferentes e nenhuma substitui as restantes.

```php
public function atualizar(Request $request, Bilhete $bilhete)
{
    Gate::authorize('update', $bilhete);
    $dados = $request->validate(['estado' => 'required|in:reservado,pago,cancelado']);
    // A transição de estado e a capacidade exigem ainda a regra de negócio.
    return $this->servicoCompras->alterarEstado($bilhete, $dados['estado']);
}
```

Este fragmento usa a facade `Gate` e mostra a separação; pressupõe uma policy e um serviço com o protocolo de compra definido. Autorizar uma alteração não torna válida qualquer transição. Por exemplo, passar de cancelado a pago pode exigir voltar a reservar capacidade.

## ORM e o problema N+1

Se carregares 100 sessões e, num ciclo, acederes a `$sessao->evento`, o carregamento preguiçoso pode fazer uma consulta inicial e mais 100 consultas. É o problema **N+1**. Carregamento antecipado, como `Sessao::with('evento')->get()`, pode carregar as relações em consultas agrupadas. Mede as consultas e os dados transferidos; antecipar todas as relações sem necessidade também custa recursos.

O modelo não é a página. Não coloques decisões de autorização só no template: um pedido direto pode contorná-lo. Não aceites campos privilegiados só porque estão no `$fillable`; esse atributo limita a atribuição em massa, não determina quem pode alterar cada valor.

## Resposta e proteção de dados

Usa parâmetros para valores nas consultas; valida escolhas de coluna e direção de ordenação por uma lista explícita. Escapa dados na vista e usa proteção CSRF nas rotas de alteração que recebem cookies. Quando a base de dados recusar uma regra conhecida, traduz o resultado para uma resposta útil sem expor SQL, credenciais ou stack traces.

Uma atualização feita em vários modelos pode precisar de `DB::transaction(...)`, mas só envolver código nessa função não resolve a corrida do último lugar. Aplica também a coordenação de [transações](/cadeiras/lbaw/triggers-transacoes/).

As APIs concretas variam com a versão do projeto. Os exemplos explicam o desenho e não constituem uma aplicação Laravel completa.
