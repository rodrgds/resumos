Um pedido HTTP identifica uma operação sobre um recurso. A aplicação interpreta-o, verifica permissões, consulta ou altera dados e devolve uma resposta. Saber onde vivem os dados e as decisões ajuda a explicar tanto a arquitetura como as falhas de segurança.

## URL e recurso

Em `https://bilhetes.example:443/sessoes/12?idioma=pt#preco`, `https` é o esquema, `bilhetes.example` o host, `443` a porta, `/sessoes/12` o caminho, `idioma=pt` a query e `preco` o fragmento. O fragmento fica no cliente e não é enviado no alvo do pedido HTTP. A porta 443 é a porta predefinida de HTTPS e pode ser omitida.

O caminho é um identificador interpretado pela aplicação; não precisa de corresponder a um ficheiro no disco.

## Pedido e resposta

Um exemplo textual em HTTP/1.1:

```http
GET /sessoes/12 HTTP/1.1
Host: bilhetes.example
Accept: text/html
Cookie: sessao=identificador_opaco
```

A primeira linha contém método, alvo e versão. Os cabeçalhos acrescentam metadados. Após uma linha vazia pode existir um corpo. Uma resposta contém código de estado, cabeçalhos e, quando apropriado, um corpo:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: private, no-store

<!doctype html><title>Sessão 12</title>
```

`Content-Type` descreve o corpo enviado. `Accept` diz quais as representações aceites pelo cliente. `Authorization` pode transportar credenciais e `Cookie` transporta os cookies que o navegador associou ao pedido. Nunca assumes que um cabeçalho enviado pelo cliente prova um papel ou uma identidade sem validação no servidor.

## Seguro e idempotente são propriedades diferentes

| Método    | Semântica habitual                                   | Seguro? | Idempotente?  |
| --------- | ---------------------------------------------------- | ------- | ------------- |
| GET, HEAD | Ler a representação, ou só metadados.                | Sim     | Sim           |
| POST      | Pedir processamento ou criar um recurso subordinado. | Não     | Não garantido |
| PUT       | Criar ou substituir o estado no endereço indicado.   | Não     | Sim           |
| DELETE    | Remover a associação do recurso ao endereço.         | Não     | Sim           |
| PATCH     | Aplicar uma alteração parcial.                       | Não     | Não garantido |

**Seguro** significa que a semântica pedida não pretende alterar o estado. Registos de acesso são efeitos laterais possíveis de uma leitura. **Idempotente** significa que repetir o mesmo pedido tem o mesmo efeito pretendido que fazê-lo uma vez. Duas eliminações podem responder 204 e depois 404 e continuar a ser idempotentes.

`GET /apagar-conta` não se torna seguro por usar GET. Viola a semântica do método e pode ser ativado por um link, pré-carregamento ou crawler. Alterações exigem um método adequado, autorização e proteção contra CSRF quando usam credenciais automáticas.

POST e PATCH podem ser desenhados com operações idempotentes, mas o método sozinho não dá essa garantia.

## Códigos que distinguem falhas

| Código    | Significado relevante                                                      |
| --------- | -------------------------------------------------------------------------- |
| 200 / 201 | Sucesso; 201 indica criação e pode incluir Location.                       |
| 204       | Sucesso sem corpo.                                                         |
| 303       | Consultar outro endereço com GET, útil após um formulário POST.            |
| 304       | A representação em cache continua válida; não transporta o corpo completo. |
| 400 / 422 | Pedido inválido; 422 pode identificar conteúdo semanticamente inválido.    |
| 401       | É necessária autenticação válida, com o desafio adequado.                  |
| 403       | O servidor compreende o pedido mas recusa a operação.                      |
| 404       | Recurso não encontrado, ou existência deliberadamente não revelada.        |
| 409       | Conflito com o estado atual, como uma reserva já confirmada.               |
| 500       | Falha interna; o detalhe técnico fica nos registos do servidor.            |

O padrão POST, redirecionamento, GET evita reenviar o formulário ao recarregar a página de confirmação. Não resolve duplicados causados por repetição de pedidos na rede. Para uma compra, um identificador único de operação pode permitir reconhecer uma repetição e devolver o resultado já registado.

## HTTP sem estado e sessões com estado

HTTP não pressupõe memória da interação anterior. A aplicação pode acrescentar estado: o servidor guarda uma sessão e envia ao navegador um identificador opaco. Em pedidos seguintes, o cookie permite procurar essa sessão. Autenticação, carrinho e permissões continuam a ser decisões da aplicação.

- `Secure`: o cookie só é enviado em ligações seguras adequadas.
- `HttpOnly`: impede leitura do cookie pelas APIs de JavaScript. Não impede que um XSS execute ações com a sessão.
- `SameSite`: limita o envio do cookie em certos contextos entre sites. É uma defesa adicional, não substitui toda a proteção contra CSRF.
- `Path`, domínio e expiração delimitam o envio e a duração; não servem como autorização sobre recursos.

Renova o identificador da sessão ao autenticar para impedir que um identificador escolhido antes do login seja aproveitado por outra pessoa. No logout, termina a sessão no servidor e invalida as credenciais associadas.

## Cache e validação

Uma resposta pública pode ser partilhada por caches se a política o permitir. Uma página pessoal exige uma política adequada para evitar exposição. `Cache-Control: no-store` pede que não seja armazenada; `no-cache` permite armazenamento mas exige validação antes de reutilizar.

`ETag` identifica uma versão de representação. O cliente envia `If-None-Match` e o servidor pode responder 304 se continuar válida. A resposta reduz o corpo transmitido; não elimina o pedido nem a autorização. Um resultado em cache não deve contornar a verificação de permissões.

## Origem, CORS e HTTPS

A origem combina **esquema, host e porta**. `https://loja.example` e `http://loja.example` têm origens diferentes. A política da mesma origem limita certas leituras entre origens no navegador. CORS permite ao servidor autorizar leituras de respostas por código de determinadas origens; alguns pedidos precisam de um preflight OPTIONS.

CORS não é autenticação, não impede pedidos de clientes fora do navegador e não impede por si só CSRF. Um formulário pode enviar um pedido que altera estado mesmo quando o atacante não consegue ler a resposta. HTTPS protege o transporte, mas não corrige SQL injection, autorização em falta ou HTML inseguro.

## REST e estado da aplicação

**REST** é um estilo de arquitetura. Entre as suas condições estão separação cliente-servidor, interface uniforme, mensagens que se descrevem a si próprias, cache quando permitido e comunicação sem estado de sessão no servidor entre pedidos. Usar JSON ou nomes no plural não chega para cumprir essas condições.

O estado dos **recursos**, como os bilhetes guardados na base de dados, pode continuar no servidor. A condição sem estado diz respeito ao contexto da interação: cada pedido precisa da informação necessária para ser compreendido. Uma aplicação com sessão de login guardada no servidor pode usar rotas e métodos HTTP adequados sem cumprir REST estritamente. HTTP ser sem estado não impede a aplicação de guardar essa sessão.

## Especificar um recurso web

Antes de implementar, descreve método e caminho, permissões, parâmetros e os resultados possíveis. Por exemplo, para `GET /api/sessoes/12`:

| Parte         | Contrato do exemplo                                                |
| ------------- | ------------------------------------------------------------------ |
| Pedido        | `id` no caminho identifica uma sessão.                             |
| Acesso        | Só devolve os campos públicos de uma sessão visível.               |
| Sucesso       | 200 e `application/json`, com `id`, `titulo` e `livres`.           |
| Ausência      | 404 quando não existe ou não deve ser revelada.                    |
| Falha técnica | 500 sem detalhes internos; o cliente mostra uma mensagem de falha. |

OpenAPI permite escrever este contrato de forma estruturada. Documentar só a página ou só os parâmetros deixa o cliente sem saber interpretar sucesso e falha. Uma resposta AJAX pode ser HTML ou JSON, consoante o contrato; o método JavaScript que lê o corpo tem de corresponder a essa escolha.
