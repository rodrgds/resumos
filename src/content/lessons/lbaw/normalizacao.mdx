Com as tabelas definidas a partir do modelo, esta página pergunta se alguma tabela repete a mesma informação em várias linhas.

Uma **chave**, ou seja, a coluna ou colunas que identificam cada linha sem duplicados, não elimina toda a repetição. Se guardarmos o gabinete de um docente em cada matrícula, mudar de gabinete exige alterar muitas linhas. A **normalização** usa regras do domínio para encontrar essas repetições e decompor tabelas, ou seja, não deduz uma regra só porque coincide nos dados atuais.

## Dependência funcional e fecho

Em `R(aluno, uc, docente, sala)`, vamos assumir três regras: um aluno pode frequentar várias UC; cada UC tem um docente; cada docente tem uma sala. Escrevemos `uc → docente` e `docente → sala`. A dependência `X → Y` diz que duas linhas que concordam em todos os atributos de X também concordam em Y. Não afirma que Y identifica X.

Por transitividade, `uc → sala`. A dependência `(aluno,uc) → aluno` é **trivial**, porque o lado direito já está no esquerdo. As regras de Armstrong são reflexividade, aumento e transitividade: se `X → Y`, então `XZ → YZ`; se também `Y → Z`, então `X → Z`.

O **fecho X⁺** reúne os atributos que X determina. Começa em X e aplica dependências até deixar de acrescentar atributos:

| Passo para `{uc}⁺` | Atributos conhecidos |
| ------------------ | -------------------- |
| Inicial            | uc                   |
| uc → docente       | uc, docente          |
| docente → sala     | uc, docente, sala    |

Falta aluno. `{uc}` não é superchave. `{aluno,uc}⁺` contém os quatro atributos, logo é superchave. É **chave candidata** porque retirar qualquer dos dois atributos deixa de determinar tudo. Uma superchave pode ter atributos a mais; uma chave candidata é mínima por inclusão, não apenas a que tem menos caracteres.

Um atributo é **primo** se pertence a alguma chave candidata. Ao estudar 3FN precisas de todas as chaves candidatas, não só da chave primária escolhida para o SQL.

## As anomalias que queremos retirar

Com `(Ana,PFL,Joana,B204)` e `(Bruno,PFL,Joana,B204)` na mesma tabela:

- **Atualização:** mudar a sala da Joana exige atualizar as duas linhas. Alterar só uma viola `docente → sala`.
- **Inserção:** não conseguimos guardar uma UC nova sem inventar uma matrícula, se aluno fizer parte da chave obrigatória.
- **Eliminação:** apagar a última matrícula de PFL também apaga a informação de quem a leciona.

Escolher um `id` artificial para cada linha não resolve nenhuma destas repetições. As dependências do domínio continuam a existir.

## 1FN, 2FN, 3FN e BCNF

Considera dependências não triviais que resultam das regras declaradas, incluindo as inferidas.

| Forma | O que verificar                                                                                              |
| ----- | ------------------------------------------------------------------------------------------------------------ |
| 1FN   | Cada posição contém um valor do domínio definido, sem um grupo repetido usado como várias linhas escondidas. |
| 2FN   | Está em 1FN e nenhum atributo não primo depende de uma parte própria de uma chave candidata.                 |
| 3FN   | Para cada X → A, X é superchave ou A é primo.                                                                |
| BCNF  | Para cada X → Y não trivial, X é superchave.                                                                 |

Uma lista de UC separada por vírgulas numa coluna torna difíceis as restrições e as junções por UC. Converte-a numa relação de matrículas. O facto de o PostgreSQL suportar arrays e JSON não elimina a necessidade de escolher o modelo adequado ao problema.

Na nossa relação, `uc → docente` viola 2FN: UC é uma parte da chave `(aluno,uc)` e docente não é primo. `docente → sala` também impede BCNF: docente não é superchave da relação completa.

Decompomos em:

```text
matricula(aluno, uc)      chave: (aluno, uc)
uc(uc, docente)           chave: uc
docente(docente, sala)    chave: docente
```

Em cada relação, os determinantes das dependências não triviais são chaves, sob estas regras. As três estão em BCNF. Se uma UC puder ter vários docentes, `uc → docente` deixa de valer e esta solução tem de mudar. Normaliza a partir das regras reais, não de uma relação que gostarias de ter.

## Sem perda não significa sem dependências perdidas

Uma decomposição é **sem perda** quando juntar as projeções recupera exatamente a relação original, sem fabricar combinações. Para uma decomposição binária `R1,R2`, sob dependências funcionais, basta que os atributos comuns determinem todos os atributos de R1 ou de R2. Este critério também é necessário neste contexto.

Ao separar `docente,sala` do resto, a interseção é docente e `docente → sala` determina a primeira relação. Ao separar `uc,docente`, a interseção é UC e UC determina essa relação. Os dois passos são sem perda.

A decomposição **preserva dependências** se as regras projetadas nas relações novas permitem verificar todas as dependências originais, sem fazer uma junção. No exemplo, `uc → docente` e `docente → sala` ficam em tabelas próprias, logo são preservadas.

Contraexemplo: em `R(A,B,C)`, sejam `AB → C` e `C → B`. As chaves candidatas são AB e AC. `C → B` satisfaz 3FN porque B é primo, mas viola BCNF porque C não determina A. Decompomos em `CB` e `AC`: é sem perda porque C determina CB. Porém, `AB → C` não fica preservada.

:::details[Ver dados que cada tabela aceita isoladamente]

```text
CB: (c1,b1), (c2,b1)
AC: (a1,c1), (a1,c2)
```

A junção produz `(a1,b1,c1)` e `(a1,b1,c2)`, violando `AB → C`. Para impedir isto precisamos de coordenação entre tabelas, ou de uma decomposição que preserve a regra. BCNF reduz certas anomalias adicionais, mas nem sempre conserva todas as dependências; uma síntese em 3FN pode ser preferível quando essa conservação é essencial.

:::

## Resolver uma pergunta de normalização

1. Escreve os atributos e as dependências que o enunciado autoriza.
2. Calcula fechos para encontrar todas as chaves candidatas.
3. Identifica os atributos primos e testa a forma pedida.
4. Mostra uma dependência concreta que viola a forma, quando existe.
5. Decompõe e justifica separadamente ausência de perda e preservação de dependências.

Dizer apenas «tem uma chave primária, portanto está normalizada» não demonstra nenhuma forma normal. Identifica as dependências e justifica BCNF, porque é preciso apresentar as tabelas e a verificação.

## Desnormalização é uma decisão de custo

Depois de normalizar, pode haver uma leitura frequente cujo custo justifica guardar um valor derivado. Um total de bilhetes pagos por sessão evita contar sempre todas as linhas, mas precisa de ser atualizado em cada compra, cancelamento ou correção. Se um desses caminhos o esquecer, o total deixa de representar os dados.

Esta **desnormalização** troca certas leituras por mais armazenamento e coordenação nas escritas. Mede a carga antes e depois. Não é uma garantia automática de maior velocidade, nem uma razão para omitir as dependências e as invariantes do desenho. Um preço histórico da compra tem outro significado que o preço atual; guardá-lo não é duplicar o mesmo facto.
