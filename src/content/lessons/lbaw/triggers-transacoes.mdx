Com consultas e índices a responder depressa, falta garantir que duas vendas ao mesmo tempo não quebram as regras.

Uma **transação** é um grupo de operações que só produz efeito em conjunto, e um **trigger** é um procedimento que corre em resposta a uma operação. Nenhum dos dois garante, sozinho, que duas vendas concorrentes preservam uma regra que compara várias linhas. Para vender o último lugar, tens de escolher também como as compras se coordenam.

Neste capítulo, a tabela `sessoes` recebe uma coluna `livres` que não existia no esquema base: é uma extensão deliberada para estudar concorrência. Inicializa `livres` com o valor de `lotacao` e mantém a invariante de que `livres` iguala `lotacao` menos bilhetes ativos. Se algum caminho escrever bilhetes sem atualizar `livres` na mesma transação, a invariante quebra.

## ACID e o que cada letra promete

| Propriedade  | Aplicação à compra                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Atomicidade  | Reservar um lugar e criar um bilhete ficam ambos confirmados ou ambos anulados.                                                 |
| Consistência | Restrições e protocolo da aplicação mantêm as invariantes declaradas. Não é uma prova automática de todas as regras de negócio. |
| Isolamento   | Define quais os efeitos de outras transações que podem ser observados e como se coordenam.                                      |
| Durabilidade | Uma confirmação mantém-se após falhas, segundo as garantias de armazenamento e configuração do sistema.                         |

```sql
BEGIN;
UPDATE sessoes SET livres = livres - 1 WHERE id = 12 AND livres > 0;
-- Verificar que foi alterada exatamente uma linha antes de continuar.
INSERT INTO bilhetes(utilizador_id,sessao_id,codigo,estado)
VALUES (7,12,'B-1043','reservado');
COMMIT;
```

Se o `UPDATE` afetar zero linhas, faz `ROLLBACK` e responde «esgotado». Se o `INSERT` falhar, anula também a redução dos lugares. `SAVEPOINT nome` e `ROLLBACK TO nome` permitem anular uma parte sem terminar a transação inteira. Um erro de instrução em PostgreSQL deixa normalmente a transação em estado de erro até ser anulada ou recuperada com um savepoint apropriado.

## Um COUNT dentro de um trigger pode falhar

Imagina uma sessão de lotação 1, sem bilhetes. Um trigger faz `COUNT(*)`, vê zero e permite inserir. Duas transações podem executar:

| Passo | Compra A                      | Compra B                                              |
| ----- | ----------------------------- | ----------------------------------------------------- |
| 1     | Conta 0 bilhetes confirmados. |                                                       |
| 2     |                               | Conta 0; não vê a inserção ainda não confirmada de A. |
| 3     | Insere um bilhete.            |                                                       |
| 4     |                               | Insere outro bilhete.                                 |
| 5     | Confirma.                     | Confirma.                                             |

Ficaram dois bilhetes para um lugar. Cada trigger correu dentro de uma transação, mas as leituras não reservaram a capacidade. Um `CHECK` numa linha também não deve consultar outras linhas para tentar resolver este caso.

## Coordenar a alteração da mesma linha

Em PostgreSQL, no isolamento padrão **Read Committed**, este `UPDATE` é uma forma de disputar um contador único:

```sql
UPDATE sessoes
SET livres = livres - 1
WHERE id = 12 AND livres > 0
RETURNING id, livres;
```

A primeira compra bloqueia e altera a linha. A segunda espera. Se a primeira confirmar, o PostgreSQL volta a avaliar a condição sobre a versão atual da linha: livres já é zero, logo a segunda não altera nenhuma linha. Se a primeira anular, a segunda pode reservar esse lugar. O `RETURNING` permite distinguir esses resultados.

O esquema pode ter `CHECK (livres BETWEEN 0 AND lotacao)`, mas o contador só coincide com os bilhetes se **todas** as compras, cancelamentos e alterações de lotação seguirem o mesmo protocolo. Criar um bilhete por outro caminho sem diminuir livres quebra a regra. A inserção e o contador pertencem à mesma transação; alterações diretas exigem permissões limitadas ou uma operação central na base de dados.

Outra estratégia é bloquear primeiro a sessão com `SELECT ... FOR UPDATE` e só depois contar e inserir. Todos os escritores têm de obter esse mesmo bloqueio. Em Read Committed, a contagem deve ser uma instrução posterior à aquisição do bloqueio, para obter um snapshot atualizado. Um bloqueio num sítio que os outros caminhos ignoram não coordena nada.

## Snapshots e níveis de isolamento

| PostgreSQL       | O que esperar                                                                                                                                                     |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Read Uncommitted | Implementado como Read Committed.                                                                                                                                 |
| Read Committed   | Cada instrução vê um snapshot dos dados confirmados ao começar, além das suas próprias alterações. Pode observar diferenças entre duas leituras.                  |
| Repeatable Read  | O snapshot é estável desde a primeira instrução relevante. PostgreSQL impede também phantom reads neste nível, mas ainda pode permitir anomalias de serialização. |
| Serializable     | Só permite efeitos compatíveis com alguma ordem serial das transações confirmadas; pode abortar uma transação para preservar essa garantia.                       |

Uma **dirty read** lê uma alteração não confirmada. Uma **non-repeatable read** volta a ler uma linha e encontra um valor confirmado diferente. Um **phantom** é uma alteração no conjunto de linhas que satisfaz o mesmo predicado. **Write skew** acontece quando duas transações leem uma condição comum e alteram linhas diferentes, preservando a condição só quando analisadas isoladamente.

No exemplo de dois médicos de serviço, ambos leem que há dois e cada um retira o seu próprio turno. Um snapshot estável não basta para impedir que fiquem zero. Serializable pode detetar o conflito e exigir uma nova tentativa. Ao receber um erro de serialização, repete a transação completa com um novo snapshot, não só a última instrução.

Para seguir execuções concorrentes e identificar as anomalias e as garantias de cada nível de isolamento, vê a aula seguinte com a pergunta «que leituras consegue cada transação ver?» na cabeça. Pausa em cada entrelaçamento e decide se o resultado final seria possível numa execução sequencial.

## Deadlock não é uma espera qualquer

A bloqueia a linha 1 e pede a 2; B bloqueia a 2 e pede a 1. Há um ciclo de espera, um **deadlock**. PostgreSQL deteta o ciclo e aborta uma das transações. Adquirir os mesmos recursos numa ordem consistente reduz esse risco. Mantém transações curtas e prepara a aplicação para repetir uma transação abortada quando isso for seguro.

## Triggers: momento, unidade e retorno

- `BEFORE`: pode validar ou alterar NEW antes de guardar. Num trigger por linha, devolver NULL pode cancelar a operação dessa linha.
- `AFTER`: observa a alteração concluída; continua dentro da transação, antes do `COMMIT`. O retorno de um trigger AFTER por linha é ignorado.
- `INSTEAD OF`: substitui a operação, por exemplo numa vista suportada por um trigger por linha.
- `FOR EACH ROW`: dispara uma vez por linha afetada. `FOR EACH STATEMENT`: uma vez por instrução, mesmo quando nenhuma linha é afetada.

`NEW` está disponível na inserção; `OLD` na eliminação; ambos na atualização. Não uses OLD num INSERT. Uma exceção no trigger pode anular a instrução; as alterações do trigger pertencem à mesma transação.

```sql
CREATE FUNCTION auditar_preco() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.preco IS DISTINCT FROM OLD.preco THEN
    INSERT INTO historico_preco(sessao_id,preco_anterior,preco_novo)
    VALUES (NEW.id,OLD.preco,NEW.preco);
  END IF;
  RETURN NEW;
END;
$$;
CREATE TRIGGER preco_alterado
AFTER UPDATE OF preco ON sessoes
FOR EACH ROW EXECUTE FUNCTION auditar_preco();
```

`UPDATE OF preco` depende das colunas mencionadas pela instrução, não de o valor ter mudado. O teste `IS DISTINCT FROM` distingue a mudança real e trata NULL de forma definida. O histórico também desaparece se a transação for anulada.

Uma transação da base de dados não anula um pagamento que já aconteceu num serviço externo. Pagamentos, emails e chamadas remotas precisam de um protocolo próprio: regista uma operação pendente e processa-a com identificação que impeça duplicados. E não mantenhas um bloqueio de linha enquanto esperas pela pessoa preencher um formulário.

## Função, procedure e trigger

Uma rotina guardada na base de dados concentra código junto dos dados. Em PostgreSQL, uma **função** é usada numa expressão, enquanto uma **procedure** é chamada com `CALL`. Um trigger é ativado por um evento e executa uma função de trigger.

```sql
CREATE FUNCTION preco_com_taxa(p numeric) RETURNS numeric
LANGUAGE SQL IMMUTABLE AS $$ SELECT p * 1.23 $$;
SELECT preco_com_taxa(10);

CREATE TABLE mensagens_exemplo (texto text);
CREATE PROCEDURE registar_mensagem(p_texto text)
LANGUAGE SQL AS $$ INSERT INTO mensagens_exemplo VALUES (p_texto) $$;
CALL registar_mensagem('confirmado');
SELECT texto FROM mensagens_exemplo;
```

O exemplo PostgreSQL dá `12.30` e uma linha `confirmado`. `CALL` não é uma forma alternativa de invocar qualquer função. Uma procedure pode ter parâmetros de saída; uma função pode produzir efeitos, por isso «função calcula, procedure altera» não é uma definição segura.

Uma rotina pode reduzir viagens entre aplicação e base de dados e centralizar uma operação. Tem custos de testes, manutenção e dependência do dialeto ou linguagem, como PL/pgSQL. Não concluas que será sempre mais rápida nem que o código será reutilizável noutro SGBD. Procedures podem controlar transações apenas nas condições admitidas pelo PostgreSQL; colocar `COMMIT` numa função não o torna válido.

## Compra coordenada passo a passo e identificadores

Segue a compra com `livres=1`: A corre `UPDATE ... WHERE livres > 0 RETURNING`, bloqueia a linha e reserva; B espera pelo bloqueio. A insere o bilhete na mesma transação e confirma. B volta a avaliar a condição sobre a versão confirmada, altera zero linhas e não insere bilhete. Se A anulasse, B reservaria. Verifica sempre as linhas afetadas pelo `RETURNING` antes de inserir.

Gera o identificador da sessão com `GENERATED ALWAYS AS IDENTITY` e lê o valor da tua própria inserção com `currval('sessoes_id_seq')`: `currval` devolve o último valor obtido na sessão atual, por isso outra sessão a inserir em paralelo não o altera. Escolhe o isolamento por transação e justifica: `READ COMMITTED` com `UPDATE` condicionado coordena o contador; `REPEATABLE READ` dá snapshot estável mas não dispensa coordenação de escrita; `SERIALIZABLE` pode abortar e exige repetir a transação completa.
