Ler `0x60` no i8042 pode retirar um byte recebido. Ler uma variável C limita-se a obter o valor guardado. Esta diferença importa: os registos de um controlador ligam o programa aos dados, ao estado e às ordens de um periférico, e os acessos podem alterar esse estado.

## Registos e espaços de endereçamento

Há registos de **dados**, de **estado** e de **controlo**. A classificação indica a função, mas não obriga cada um a ter um endereço distinto. O mesmo endereço pode selecionar registos diferentes conforme leias ou escrevas.

No i8042, ler `0x64` consulta o estado; escrever `0x64` envia um comando ao controlador. Ler `0x60` retira dados do output buffer; escrever `0x60` envia um byte pelo input buffer. Os nomes input e output referem-se ao ponto de vista do controlador, não do processador.

Há duas maneiras de colocar esses endereços no sistema:

| Acesso            | Espaço de endereçamento    | Operação do processador                       |
| ----------------- | -------------------------- | --------------------------------------------- |
| Memory-mapped I/O | Parte do espaço de memória | Instruções de acesso à memória                |
| Port-mapped I/O   | Espaço de I/O separado     | Instruções próprias, como `IN` e `OUT` em x86 |

As portas do timer, do i8042 e da UART são port-mapped I/O. O framebuffer é memória mapeada. Não chames memory-mapped I/O a todas as leituras de portas. A arquitetura ARM usa memória mapeada para este acesso; x86 também suporta memória mapeada, além do seu espaço de portas de 16 bits.

## Privilégios e Minix

Um processo normal não pode executar qualquer operação de hardware, porque o sistema limita o acesso para proteger os outros processos. No Minix, os drivers são processos em espaço de utilizador com permissões próprias. O programa de LC usa **kernel calls** para pedir operações privilegiadas ao microkernel, por exemplo `sys_inb` e `sys_outb`.

Uma máquina virtual fornece um PC emulado. O Minix acede ao hardware da máquina virtual, não recebe por isso acesso livre aos dispositivos físicos do computador anfitrião. O código dos laboratórios depende da imagem Minix e das bibliotecas de apoio fornecidas para LC.

`sys_inb` escreve o resultado numa variável de 32 bits, mesmo quando lê apenas um byte. Passar o endereço de um `uint8_t` através de um cast não aumenta o objeto: permitiria escrever para lá do seu fim. Esta função completa faz a adaptação segura no ambiente Minix/LCF:

```c
#include <lcom/lcf.h>
#include <stdint.h>

int read_port_byte(int port, uint8_t *value) {
  if (value == NULL) return 1;
  uint32_t raw;
  int result = sys_inb(port, &raw);
  if (result != OK) return result;
  *value = (uint8_t)raw;
  return OK;
}
```

O chamador recebe um byte apenas após uma leitura bem-sucedida. A função não é executável no navegador: precisa dos cabeçalhos, serviços e permissões Minix do laboratório. Os nomes de tipos antigos `u32_t` e `u8_t` aparecem em algumas APIs com o mesmo papel.

## Testar e alterar campos

Uma máscara tem bits a 1 nas posições que interessam. Num byte `r`, as operações usuais são:

| Intenção                                     | Expressão      |
| -------------------------------------------- | -------------- |
| Saber se algum bit da máscara `m` está ativo | `(r & m) != 0` |
| Saber se todos estão ativos                  | `(r & m) == m` |
| Ligar os bits de `m`                         | `r \| m`       |
| Limpar os bits de `m`                        | `r & ~m`       |
| Inverter os bits de `m`                      | `r ^ m`        |

`&` faz AND posição a posição. `&&` testa a verdade das expressões e devolve 0 ou 1. Para `r = 0x20` e `m = 0x01`, `r & m` é 0, mas `r && m` é 1, por isso o segundo teste não diz se o bit 0 está ativo.

Para substituir um campo, limpa primeiro o campo antigo e insere o novo. Se os bits 4 a 2 contêm um modo, a máscara é `0x1C`. Com `r = 0xA7` e o novo modo 5:

```c
uint8_t next = (uint8_t)((r & ~0x1Cu) | (5u << 2));
```

Os três passos conservam os bits exteriores ao campo:

| Passo            | Byte        | Campo 4:2 |
| ---------------- | ----------- | --------- |
| Registo inicial  | `1010 0111` | `001`     |
| Limpar `0x1C`    | `1010 0011` | `000`     |
| Inserir `5 << 2` | `1011 0111` | `101`     |

O resultado é `0xB7`. Usar apenas OR deixaria bits do modo anterior ligados. Usa valores sem sinal nas máscaras e garante que a contagem de um deslocamento é menor do que a largura do operando.

Esta leitura, alteração e escrita só é válida se o registo for legível e permitir essa semântica. Um registo write-only, ou com bits que se limpam ao escrever 1, exige a sequência descrita pelo dispositivo.

## Polling e timeout

Em **polling**, o programa consulta o estado até a condição ser satisfeita, porque ainda não recebeu nenhuma notificação. Antes de ler o output buffer do i8042, espera `OBF = 1`. Antes de escrever uma ordem, espera `IBF = 0`. São condições diferentes.

Numa leitura concreta, lê `0x64`. Se OBF estiver a 0, espera e volta a ler. Quando OBF for 1, lê `0x60` uma vez e interpreta esse byte. Se o estado assinalar erro de paridade ou timeout, consome na mesma o byte e descarta-o, para não deixar lixo no buffer a bloquear a entrega seguinte.

Um ciclo sem limite pode nunca terminar. Define uma política de falha e deixa o controlador ter tempo para responder. Esta função completa do ambiente Minix espera até cinco tentativas, espaçadas por 20 ms:

```c
#include <lcom/lcf.h>
#include <stdint.h>

int wait_kbc_input_empty(void) {
  const unsigned attempts = 5;
  const unsigned delay_us = 20000;
  for (unsigned i = 0; i < attempts; ++i) {
    uint32_t status;
    int result = sys_inb(0x64, &status);
    if (result != OK) return result;
    if ((status & (1u << 1)) == 0) return OK;
    if (i + 1 < attempts)
      tickdelay(micros_to_ticks(delay_us));
  }
  return 1;
}
```

O resultado esperado é `OK` assim que IBF estiver a 0, ou erro se a leitura falhar ou a condição não surgir. São cinco observações e no máximo quatro atrasos, cerca de 80 ms mais o custo das chamadas e o arredondamento a ticks. Isto é uma política para este exemplo, não uma constante do dispositivo.

Polling não implica sempre espera ativa sem corpo, porque o programa pode consultar periodicamente e executar outra tarefa entre consultas. Com período de consulta $P$, um evento que fica disponível até ser lido espera entre aproximadamente 0 e $P$ antes de ser detetado. Se os instantes forem uniformes, a espera média é $P/2$. Um buffer pequeno pode perder eventos durante esse intervalo.

## Quando escolher polling

Polling evita o custo de configurar e receber interrupções, por isso pode servir para uma operação curta e esperada, como obter uma resposta a um comando. Interrupções permitem bloquear à espera de eventos pouco frequentes. A escolha depende da frequência dos eventos, do tempo de resposta permitido, da capacidade do buffer e do custo de cada consulta ou atendimento.

Não concluas que uma das opções é sempre mais rápida. A próxima página separa o pedido de interrupção do dispositivo, o atendimento no kernel e a notificação recebida pelo programa.
