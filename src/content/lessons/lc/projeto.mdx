Uma aplicação recebe bytes, transforma-os em eventos e atualiza o estado. O desenho apresenta uma fotografia desse estado, ou seja, se separares estes passos, consegues testar o raciocínio sem precisar de reproduzir sempre o mesmo movimento na máquina virtual.

## Programação por eventos

Um evento pode ser um tick, uma tecla completa, um pacote de rato ou uma mensagem recebida pela UART, porque nem todo o dado bruto já é um evento útil. Um prefixo E0 precisa do byte seguinte.

A divisão de responsabilidades é:

1. O driver acede a registos e recolhe os dados.
2. O descodificador produz eventos completos.
3. A aplicação atualiza estado e decide ações.
4. O módulo gráfico desenha o estado num frame.

O driver do rato não deve decidir se um clique inicia um jogo. Isso depende da aplicação. O código do menu não deve saber a porta do i8042. Uma biblioteca é reutilizável quando o contrato esconde esses detalhes e conserva a informação de que os chamadores precisam.

No ciclo Minix, recebe a mensagem, atende todas as máscaras ativas e processa os eventos produzidos antes de voltar a bloquear. Deixar um evento numa variável para o tratar "quando não houver interrupções" pode fazer o programa bloquear antes de o consumir.

## Máquinas de estados

Uma máquina de estados explicita o que cada evento faz em cada situação. Para um jogo simples, podemos ter MENU, JOGO, PAUSA e FIM.

A transição não depende apenas da tecla. Enter no menu começa, enquanto Enter no fim regressa ao menu. Um tick na pausa pode atualizar um cursor do menu, mas não deve avançar o tempo do jogo se a regra diz que o jogo está parado.

Uma máquina **Mealy** associa saídas à transição, dependendo de estado e entrada. Uma máquina **Moore** associa saídas ao estado. Ambas podem representar a mesma função, embora possam precisar de diferentes números de estados. Em código por eventos, produzir uma ação ao aceitar uma transição é uma representação frequente.

Os dados também fazem parte do estado. Um `enum` sozinho não representa vidas, posição ou ticks acumulados. Podes usar uma `struct` com o estado e os dados comuns, ou uma tagged union para dados que só existem em algumas alternativas.

## Um exemplo completo sem hardware

Este programa C portátil simula Enter, ticks e P. Um jogo termina após três ticks ativos, ou seja, o tick durante a pausa não aumenta o contador.

```c
#include <stdio.h>

enum state { MENU, GAME, PAUSE, END };
enum event { ENTER, P_KEY, TICK };
struct game { enum state state; unsigned active_ticks; };

static void handle(struct game *g, enum event event) {
  switch (g->state) {
    case MENU:
      if (event == ENTER) {
        g->active_ticks = 0;
        g->state = GAME;
      }
      break;
    case GAME:
      if (event == P_KEY) g->state = PAUSE;
      else if (event == TICK && ++g->active_ticks == 3) g->state = END;
      break;
    case PAUSE:
      if (event == P_KEY) g->state = GAME;
      break;
    case END:
      if (event == ENTER) g->state = MENU;
      break;
  }
}

int main(void) {
  struct game g = {MENU, 0};
  const enum event events[] = {ENTER, TICK, P_KEY, TICK, P_KEY, TICK, TICK};
  const char *names[] = {"MENU", "JOGO", "PAUSA", "FIM"};
  for (size_t i = 0; i < sizeof events / sizeof events[0]; ++i) {
    handle(&g, events[i]);
    printf("%s %u\n", names[g.state], g.active_ticks);
  }
  return 0;
}
```

O programa imprime:

```text
JOGO 0
JOGO 1
PAUSA 1
PAUSA 1
JOGO 1
JOGO 2
FIM 3
```

Cada linha permite seguir o estado depois de um evento, porque este exemplo usa uma condição de fim por ticks com o mesmo mecanismo de transição do diagrama.

## Filas, ordem e ritmo

Se chegam vários bytes ou eventos antes de os tratares, usa uma fila, com limite e política de overflow. Uma variável com o último evento não guarda toda a sequência. Quando os eventos são movimentos absolutos, por vezes podes substituir uma posição antiga pela mais recente; quando são cliques ou deltas, essa substituição muda o comportamento.

A ordem também muda resultados. Se `PAUSE` e `TICK` estão prontos na mesma iteração, decide qual aplicar primeiro. Num jogo com tempo limite, essa escolha determina se o último tick conta. Conserva a mesma regra em testes, execução local e protocolo remoto.

Atualiza a lógica quando recebe entradas, porque desenhar a um ritmo escolhido, por exemplo a cada dois ticks de um timer de 60 Hz, evita redesenhar o ecrã inteiro por cada byte de um scancode.

Carrega recursos gráficos antes do ciclo e liberta-os depois. Não faças parsing de XPM ou alocações grandes em cada tick. Otimiza depois de medir: copiar linhas contíguas de um pixmap pode custar menos do que chamar uma função de desenho por píxel, mas deve preservar transparência, clipping e pitch.

## Inicialização e falha parcial

A inicialização precisa de um caminho inverso. Se obténs timer, teclado, pixmaps e vídeo por esta ordem, uma falha no vídeo obriga a libertar os pixmaps e as subscrições já obtidas. Uma flag de recurso adquirido, ou uma função de limpeza que tolere recursos ausentes, permite tratar todos os caminhos.

Não chames a aplicação "pronta" antes de todos os recursos obrigatórios estarem válidos. Mantém erros distinguíveis: alocação falhada, configuração VBE recusada, subscrição falhada e timeout do dispositivo pedem verificações diferentes.

Na saída normal, deixa de gerar novos eventos, repõe configurações alteradas, remove subscrições, liberta pixmaps e buffers e restaura o modo de texto. A ordem deve respeitar as dependências, para uma rotina não usar um recurso já destruído.

## Debugging como experiência

Começa por uma observação reproduzível. "O cursor salta para a esquerda ao mover depressa para a direita" sugere uma hipótese concreta: um delta positivo acima de 127 foi interpretado como `int8_t`.

Prevê antes de alterar: para um pacote `08 C8 00`, o delta correto é +200. O erro produziria -56. Simula exatamente esse pacote no descodificador. Se obténs -56, o problema está antes da atualização do cursor ou do desenho. Se obténs +200, verifica a soma, o clipping e a representação da posição.

O método é sempre o mesmo, por isso reduz a entrada à menor sequência que ainda falha e formula uma hipótese sobre uma operação ou estado antes de alterar o código:

1. Reduz a entrada à menor sequência que ainda falha.
2. Formula uma hipótese sobre uma operação ou estado.
3. Escolhe a observação que distinguiria essa hipótese das alternativas.
4. Altera uma causa, volta a correr a mesma sequência e compara.

Para uma interrupção ausente, observa configuração do dispositivo, subscrição, máscara recebida e leitura do buffer. Para imagem errada, verifica modo, pitch, offset e formato de cor. Para ligação errada, começa com bytes conhecidos antes de culpar o parser de mensagens.

Regista valores no limite entre módulos, evitando imprimir em cada ciclo de espera sem necessidade. O logging altera tempo e carga. Se um erro desaparece quando acrescentas prints, isso é uma observação sobre temporização, não prova de correção.

Depois da correção, conserva um caso que reproduza o comportamento, como uma sequência de bytes ou eventos, e verifica também o caso vizinho que poderia quebrar. O objetivo é explicar o erro e a correção por resultados observáveis.
