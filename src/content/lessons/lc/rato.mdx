O rato PS/2 comunica através do i8042, como o teclado, mas usa IRQ12 e pacotes de três bytes, ou seja, o hardware entrega um byte por interrupção e só depois de reunir os três bytes podes interpretar botões e movimento.

## Anatomia do pacote

Os dois contadores de deslocamento do rato têm nove bits em complemento para dois. O primeiro byte contém o bit mais significativo de cada delta; os bytes seguintes contêm os oito bits inferiores.

| Byte             | Conteúdo                           |
| ---------------- | ---------------------------------- |
| 0, bit 7         | Overflow de Y                      |
| 0, bit 6         | Overflow de X                      |
| 0, bit 5         | Bit de sinal de Y                  |
| 0, bit 4         | Bit de sinal de X                  |
| 0, bit 3         | Sempre 1 no primeiro byte          |
| 0, bits 2, 1 e 0 | Botões do meio, direito e esquerdo |
| 1                | Oito bits inferiores do delta X    |
| 2                | Oito bits inferiores do delta Y    |

Os botões indicam o estado no instante do pacote, não apenas uma mudança, por isso um botão a 1 em vários pacotes pode significar que continua premido.

## Reconstruir nove bits

Se o bit de sinal de X estiver a 0, $\Delta x$ é o valor sem sinal do segundo byte. Se estiver a 1, subtrai 256:

$$\Delta x=b_1-256\cdot s_x,\qquad\Delta y=b_2-256\cdot s_y.$$

Aqui $b_1$ e $b_2$ estão entre 0 e 255; $s_x$ e $s_y$ são 0 ou 1 obtidos do primeiro byte. Isto representa o intervalo de nove bits, de -256 a 255, na ausência de overflow.

Não uses apenas `(int8_t)b1`, porque se o sinal X for 0 e `b1 = 0xC8`, o delta correto é +200 e um inteiro de oito bits com sinal representaria -56. Se o sinal X for 1 e `b1 = 0x05`, o delta é $5-256=-251$, apesar de o bit 7 de `b1` estar a 0.

No pacote `28 05 FB`, o sinal X é 0 e o sinal Y é 1. Obtemos $\Delta x=5$ e $\Delta y=251-256=-5$.

No protocolo, Y positivo significa movimento para cima. Num ecrã onde Y cresce para baixo, atualiza `screen_y -= delta_y`, ou seja, partindo de `(100, 100)`, o pacote do exemplo leva a `(105, 105)`.

O programa seguinte imprime `dx=5 dy=-5 x=105 y=105`, porque aplica a fórmula de nove bits e a conversão para coordenadas de ecrã:

Este exemplo assume ausência de overflow e não aplica limites do ecrã. Na aplicação, mantém a soma num tipo com sinal, limita às coordenadas permitidas e só depois converte para o tipo da posição.

## Montagem e sincronização

Mantém um array de três bytes e um índice. Se o índice for 0, aceita apenas um byte com bit 3 a 1. Se não tiver esse bit, descarta-o. Nos índices 1 e 2, guarda o byte sem repetir o teste, porque os dados podem ter qualquer valor.

Quando o índice chega a 3, entrega o pacote completo e volta a 0, porque o bit 3 também pode estar ativo nos bytes de dados. É uma ajuda de sincronização, não uma prova de que nunca juntaste pedaços de dois pacotes.

Se uma leitura falhar ou houver erro de comunicação durante a montagem, invalida o pacote parcial e volta a procurar um primeiro byte. Um erro não deve produzir um movimento com bytes antigos. Se os bits de overflow estiverem ativos, a magnitude correspondente não é fiável. Define se ignoras esse eixo ou todo o movimento; ainda podes interpretar os botões se o pacote foi recebido validamente.

## Stream, remote e reporting

Em **stream mode**, o rato envia pacotes quando há movimento ou mudança de botões, até à taxa de amostragem configurada. Ativar o modo não é o mesmo que ativar o envio: data reporting pode estar desligado.

Em **remote mode**, o programa pede um pacote com `0xEB`. Isso é útil para uma experiência de polling. Cada byte do pacote continua a passar pelo output buffer do i8042; não chega um array de três bytes numa única leitura.

| Comando do rato | Função                                       |
| --------------- | -------------------------------------------- |
| `0xF4`          | Ativar data reporting em stream mode         |
| `0xF5`          | Desativar data reporting                     |
| `0xEA`          | Selecionar stream mode                       |
| `0xF0`          | Selecionar remote mode                       |
| `0xEB`          | Pedir dados em remote mode                   |
| `0xF3`          | Definir taxa de amostragem, com um argumento |
| `0xF6`          | Repor parâmetros por defeito                 |

Subscreve IRQ12 com a política exclusiva apropriada ao laboratório, para o driver normal do Minix não disputar os bytes. Guarda a configuração relevante e repõe o modo e reporting ao sair.

## Enviar um comando

Os comandos do rato não se escrevem diretamente na porta de comandos do KBC. Para enviar cada byte:

1. Espera IBF a 0 e escreve `0xD4` em `0x64`, a ordem ao KBC para encaminhar o byte seguinte ao rato.
2. Espera IBF a 0 e escreve o byte em `0x60`.
3. Espera a resposta e lê-a de `0x60`, tratando timeout e erros.

O rato confirma cada byte recebido: `0xFA` é ACK, `0xFE` pede reenvio e `0xFC` assinala erro. Limita as tentativas. O ACK não é o conteúdo da resposta de um comando que devolve dados: essa resposta vem depois.

Para definir taxa de amostragem, há uma sequência para `0xF3` e outra para o argumento. Cada uma usa `0xD4` e recebe o seu ACK. Se o argumento provocar pedido de reenvio, a política do protocolo pode exigir repetir o comando completo, não apenas o argumento.

Em stream mode com reporting ativo, desativa reporting antes de enviar outros comandos para não misturar pacotes de movimento com respostas. A fase de comandos e a fase de receção de pacotes devem ter um dono claro do output buffer.

## De pacotes a gestos

Um gesto depende de uma sequência, por isso precisa de estado. Num exemplo próprio, queremos um arrasto horizontal para a direita com botão esquerdo premido, comprimento de pelo menos 100 unidades e desvio vertical absoluto no máximo 5.

Começa em `WAIT_PRESS`. Na transição de botão solto para premido, passa a `DRAWING` e põe os acumulados a zero. Enquanto o botão continuar premido, soma os deltas. Se o movimento voltar para a esquerda ou o desvio ultrapassar a tolerância, passa a `INVALID` e ignora os movimentos até o botão ser largado. Só uma nova pressão inicia outro candidato. Se $x\geq100$ e $|y|\leq5$, reconhece o gesto. Largar o botão antes disso cancela-o.

A decisão de usar desvio vertical **acumulado** é parte do enunciado. Aceitar cada pacote com $|\Delta y|\leq5$ permitiria dez pacotes de +5 e um desvio final de 50. O parser de bytes e a máquina do gesto resolvem problemas distintos: a primeira produz pacotes completos; a segunda interpreta o seu significado ao longo do tempo.
