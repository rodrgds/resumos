Imagina um jogo simples com um herói que se move e uma pontuação que aumenta. Um colega alterou o movimento e tu alteraste a pontuação, e é preciso guardar cada decisão e combinar o trabalho sem perder nenhuma versão.

O Git, que é o programa que guarda esse histórico de versões, regista cada decisão numa fotografia dos ficheiros chamada commit. O Gradle, que é a ferramenta que descreve como montar o projeto, diz como transformar o código em programa e como correr os testes, para qualquer máquina fazer o mesmo.

## As três áreas do Git

O **working tree** contém os ficheiros que estás a editar. O **índice**, ou staging area, contém o próximo snapshot que escolheste com `git add`. Um **commit** guarda esse snapshot no histórico local, com mensagem e referência aos seus pais.

```text
ficheiros editados  --git add-->  índice  --git commit-->  histórico
```

`git add` copia o conteúdo daquele instante para o índice. Se voltares a editar depois, o próximo commit continua a usar a versão preparada, até repetires o `add`.

Experimenta numa pasta nova:

```bash
mkdir treino-git
cd treino-git
git init -b main
printf 'versao 1\n' > regra.txt
git add regra.txt
printf 'versao 2\n' > regra.txt
git diff
git diff --cached
git commit -m "Regista a primeira regra"
```

`git diff` compara working tree com índice, por isso mostra a passagem de versão 1 para versão 2. `git diff --cached` compara índice com o commit atual, por isso mostra o ficheiro novo com versão 1. O commit guarda versão 1; versão 2 continua como alteração local.

No estado curto, a primeira coluna descreve o índice e a segunda o working tree. `M  regra.txt` significa alteração preparada; ` M regra.txt`, alteração por preparar; `MM regra.txt`, as duas. `??` identifica um ficheiro ainda não seguido.

Antes de um commit, consulta `git status --short`, `git diff` e `git diff --cached`. Prepara caminhos concretos quando há trabalho de várias tarefas na mesma pasta. Um commit deve explicar uma alteração e o seu motivo.

## Branches e merges

Um branch é uma referência móvel para um commit. `HEAD` costuma indicar o branch atual; num checkout de um commit isolado pode estar destacado, sem branch. Criar um branch não copia os ficheiros para outra pasta.

```bash
git switch -c movimento
# edita e guarda os ficheiros da funcionalidade
git add regra.txt
git commit -m "Permite mover o heroi para cima"
git switch main
git merge movimento
```

O merge integra `movimento` no branch em que estás, aqui `main`. Há dois casos:

- Se `main` é antepassado de `movimento`, um **fast-forward** move a referência de `main` para a frente. Não precisa de commit de merge.
- Se ambos avançaram a partir de um antepassado comum, o merge combina as mudanças. Um commit de merge tem os dois históricos como pais.

```text
              C---D  movimento
             /     \
A---B-------E-------M  main
```

Neste desenho, `M` integra `D` e `E`. Os commits `C` e `D` não desaparecem. O branch é o nome que aponta para o seu último commit.

## Resolver um conflito

Um conflito surge quando Git não consegue decidir o conteúdo final. Pode acontecer em linhas sobrepostas ou, por exemplo, quando um branch remove um ficheiro e outro o altera.

```text
  <<<<<<< HEAD
  int velocidade = 2;
  =======
  int velocidade = 3;
  >>>>>>> movimento
```

`HEAD` é a versão do branch atual. A outra parte vem do branch integrado. Escolhe o comportamento certo, edita o ficheiro e remove todos os marcadores. Depois corre os testes, prepara o ficheiro com `git add regra.txt` e conclui com `git commit`. A solução pode combinar as duas versões, não tem de escolher uma por inteiro.

Se precisas de abandonar este merge ainda por concluir, `git merge --abort` tenta repor o estado anterior. Começa a integração com o working tree limpo para não misturar uma resolução com trabalho por guardar.

## Repositório local e remoto

O remoto é outro repositório, frequentemente alojado no GitHub. Os commits existem localmente antes do `push`. `origin` é o nome convencional do remoto criado por `clone`, não uma regra sobre qual repositório manda.

| Comando                           | Efeito                                                                                 |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| `git fetch origin`                | Obtém objetos e atualiza referências como `origin/main`, sem integrar no branch atual. |
| `git pull --ff-only`              | Obtém e integra apenas se for possível avançar sem divergência.                        |
| `git push -u origin movimento`    | Publica o branch e configura a referência remota acompanhada.                          |
| `git log --oneline --graph --all` | Mostra o histórico e os ramos conhecidos.                                              |

Se `pull --ff-only` recusar, os históricos divergiram. Inspeciona o grafo e combina com merge ou rebase segundo o workflow da equipa. **Rebase** reaplica commits sobre outra base e cria identificadores novos; reescrever commits já partilhados exige coordenação.

## Workflows em equipa

Uma opção simples para o projeto é usar branches curtos e pull requests. Atualiza `main`, cria um branch, implementa um comportamento, testa e pede revisão. Integra quando o resultado está compreendido e o build passa.

A revisão deve confirmar o contrato, os casos limite e as dependências, não apenas a formatação. Evita incluir ficheiros gerados ou alterações de outra tarefa no mesmo commit. No `.gitignore`, `build/`, `.gradle/` e `*.class` são exclusões habituais; ficheiros já seguidos continuam seguidos mesmo depois de acrescentares uma regra.

## Desfazer sem perder a história

`git revert <commit>` cria um commit que inverte as mudanças de outro. É adequado para um commit já partilhado, porque preserva a história.

`git restore regra.txt` descarta mudanças desse ficheiro no working tree e recupera o conteúdo do índice. `git restore --staged regra.txt` retira a mudança do índice sem apagar a edição local. `git reset` move uma referência e pode alterar índice e ficheiros conforme a opção; `--hard` descarta mudanças locais. Identifica primeiro o que queres recuperar e onde existe a versão a preservar.

## Dependências com Gradle

Um build deve especificar versões e tarefas, para não depender de ficheiros `.jar` copiados à mão. O **Gradle Wrapper**, `gradlew` e `gradle/wrapper/`, fixa a versão do Gradle do projeto. Guarda-o no Git e usa `./gradlew`, ou `gradlew.bat` no Windows, em vez de uma instalação global diferente.

Vamos preparar o projeto que usaremos nos testes. Este exemplo local usa JDK 17 para correr Gradle 8.14.3 e compila código compatível com Java 8. A versão de Java que corre a ferramenta pode ser diferente da versão alvo do programa. Usa o wrapper e o JDK indicados no projeto da cadeira quando forem diferentes.

Guarda este `build.gradle` na raiz:

```groovy
plugins {
    id 'java'
    id 'application'
    id 'jacoco'
}

repositories {
    mavenCentral()
}

java {
    sourceCompatibility = JavaVersion.VERSION_1_8
    targetCompatibility = JavaVersion.VERSION_1_8
}

dependencies {
    testImplementation 'org.junit.jupiter:junit-jupiter:5.13.4'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher:1.13.4'
    testImplementation 'org.mockito:mockito-core:4.11.0'
}

application {
    mainClass = 'Main'
}

tasks.named('test') {
    useJUnitPlatform()
}

tasks.named('jacocoTestReport') {
    dependsOn test
    reports {
        html.required = true
    }
}
```

`implementation` seria uma dependência do programa; `testImplementation` só participa nos testes. `testRuntimeOnly` fornece código necessário ao executar testes, sem o pôr na compilação do programa. JUnit Jupiter escreve e executa os testes; `useJUnitPlatform()` seleciona a plataforma correspondente.

A estrutura é:

```text
build.gradle
settings.gradle
src/main/java/Main.java
src/test/java/LimiteTest.java
src/main/resources/
src/test/resources/
```

Em `settings.gradle`, escreve `rootProject.name = 'treino-ldts'`. Se ainda não tens wrapper e dispões de Gradle 8.14.3, corre `gradle wrapper --gradle-version 8.14.3` uma vez. Num projeto recebido da cadeira, o wrapper já deve existir.

```bash
./gradlew test
./gradlew run
./gradlew jacocoTestReport
```

`test` compila os testes e executa-os; o relatório HTML fica em `build/reports/tests/test/index.html`. `run` precisa de uma classe `Main` com método `main`. O relatório de cobertura fica em `build/reports/jacoco/test/html/index.html`.

No IntelliJ, abre a pasta que contém `settings.gradle`, seleciona o JDK e sincroniza o projeto Gradle. Se falhar, lê a primeira causa indicada no erro e compara JDK, wrapper, repositórios e dependências. Uma falha de descarga e um erro de compilação pedem verificações diferentes.
