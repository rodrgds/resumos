O herói está na célula 3 e pede um movimento que chegaria à célula 5, fora da arena. O modelo recusa; a vista tem de continuar a mostrar 3. MVC separa a regra dos limites, a interpretação do pedido e a apresentação do resultado.

## Model, View e Controller

O **Model** representa estado e regras do domínio. Mantém invariantes, como ficar dentro da arena. Não precisa de saber se mostramos o herói em Swing ou num terminal.

A **View** apresenta o estado e recolhe ou encaminha eventos da interface. Traduz valores em texto, formas e componentes. Não decide se um movimento é válido.

O **Controller** interpreta ações e coordena operações. Um clique, uma tecla ou outro evento pode transformar-se no mesmo pedido ao modelo. Depois a vista apresenta o estado resultante.

Existem variantes de MVC. Nesta página, o controlador atualiza explicitamente a vista. Noutra variante, a vista subscreve mudanças do modelo com Observer. Em ambos os casos, as regras não dependem dos componentes gráficos.

## Seguir uma ação completa

Vamos usar uma arena com cinco células, de zero a quatro. O herói começa em dois. Pedimos `+1`, depois `+2`, depois `-1`.

A saída é `heroi: 3`, `heroi: 3` e `heroi: 2`. Segue os pedidos consecutivos, sempre a partir do estado aceite anterior:

| Antes | Pedido | Destino | Aceite? | Mostrado |
| ----- | ------ | ------- | ------- | -------- |
| 2     | +1     | 3       | Sim     | 3        |
| 3     | +2     | 5       | Não     | 3        |
| 3     | -1     | 2       | Sim     | 2        |

A segunda tentativa devolve `false` e mantém 3. O controlador lê `getX()` depois da tentativa. Mostrar `x + deslocamento` na vista inventaria um estado que o modelo recusou.

O cálculo usa `long` para que um deslocamento inteiro muito grande não faça overflow antes de verificar os limites. Só converte para `int` depois de validar um destino dentro da largura inteira.

## O que depende de quê

A montagem, aqui o `main`, escolhe `VistaTexto`. O controlador conhece o modelo e a interface `Vista`. O modelo não importa nenhuma dessas classes de apresentação.

```text
montagem: escolhe e liga os objetos
controlador --> modelo
controlador --> contrato da vista <-- vista concreta
```

Uma `VistaSwing` pode implementar o mesmo contrato. Os listeners traduzem eventos em chamadas ao controlador. Liga o botão sem pôr regra na vista:

```java
somar.addActionListener(evento -> controlador.mover(1));
```

O clique vira `mover(1)`; o controlador pede ao modelo e mostra `modelo.getX()`. A vista nunca calcula limites. Como os eventos Swing são tratados na EDT, operações curtas do modelo podem correr aí; operações demoradas precisam de uma tarefa separada e de voltar à EDT para apresentar o resultado.

Não escondas uma regra no desenho. Se a vista limita a posição mas o modelo aceita qualquer valor, os testes do modelo e outra vista continuam vulneráveis.

## Testar cada comportamento

O modelo pode ser testado sem janela: começa em dois, move para três, recusa cinco e mantém três. Testa também a construção inválida, ambos os limites e deslocamentos extremos. O esperado vem do intervalo da arena.

Para o controlador, passa uma vista controlada e confirma que recebe a posição aceite. O cenário de movimento bloqueado distingue mostrar `getX()` de mostrar o destino pedido. Concretiza sem janela:

```java
class VistaMemoria implements Vista {
    int ultimo = -1;
    public void mostrar(int x) { ultimo = x; }
}
```

Usa-a com as classes `Modelo` e `Controlador` da lição:

```java
Modelo modelo = new Modelo(5, 4);
VistaMemoria vista = new VistaMemoria();
new Controlador(modelo, vista).mover(1);
assert vista.ultimo == 4;
```

Se executares este excerto num `main`, usa `java -ea Main` para ativar a instrução Java `assert`; sem `-ea`, a verificação não corre. Nos testes JUnit, usa `assertEquals(4, vista.ultimo)`, que não depende dessa opção.

`VistaMemoria` guarda o valor de `mostrar(int x)` num campo. O modelo recusa 5 e fica em 4; o controlador errado mostraria 5 e este teste falhava. Um teste só com movimentos válidos não reconhece esse erro.

Para a vista concreta, verifica a tradução para texto ou componentes, incluindo os eventos que envia. Não precisas de abrir uma janela para testar a regra dos limites. Um teste completo da aplicação pode depois verificar que uma tecla percorre todas as peças.

## Onde entram os padrões

Command pode representar cada ação do utilizador. Strategy pode variar o movimento de um inimigo. State pode controlar Jogar e Pausa. Observer pode avisar vistas de mudanças. Uma fábrica pode escolher objetos na montagem.

Usa-os quando resolvem esse problema no projeto. Não precisas de aplicar todos os padrões nem de contar quantas classes criaste. Na justificação, liga a decisão a uma mudança concreta e explica o que ficou mais fácil de testar ou alterar.

## Trabalhar num projeto pequeno

Começa com uma funcionalidade que percorra a aplicação inteira: ler uma ação, validar uma mudança e mostrar o resultado. Guarda esse comportamento e os seus testes antes de acrescentar alternativas.

Divide trabalho por contratos e comportamentos, para evitar que cada pessoa construa uma camada sem nunca testar a ligação. Combina nomes, tipos e invariantes antes de trabalhar em paralelo. Integra cedo e executa o build depois de combinar os branches.

Um relatório técnico deve explicar as escolhas com exemplos do próprio código. Para uma refatoração, mostra a dificuldade inicial, a transformação e a evidência de que o comportamento foi preservado. Para um padrão, identifica participantes e consequências. Um diagrama deve responder a uma pergunta que o texto faz.

As regras e pesos de avaliação pertencem à [apresentação da cadeira](/cadeiras/ldts/). Usa as instruções do projeto da tua edição para requisitos, entregas e formato, sem confundir este jogo ilustrativo com um enunciado oficial.
