O algoritmo de movimento muda, mas o inimigo continua a ter posição e vida. Já separámos esse algoritmo através de uma interface. Um padrão dá um nome a essa colaboração, explica em que situações é útil e que custos introduz.

Não é uma classe pronta a copiar. Para aplicar um padrão, identifica o cliente, a decisão que varia e o contrato que permite separar essa decisão.

## Strategy: trocar o algoritmo

**Strategy** encapsula algoritmos alternativos com a mesma interface. O contexto guarda uma estratégia e delega-lhe a operação. O cliente ou a configuração escolhe a alternativa.

No exemplo de [composição](/cadeiras/ldts/java-orientado-objetos/#herança-interfaces-e-composição), `Inimigo` é o contexto, `Movimento` a estratégia e `ParaDireita` e `Parado` as alternativas. `passo()` não testa o tipo do movimento. Para acrescentar uma perseguição, criamos outra implementação do contrato.

A estratégia precisa dos dados suficientes para calcular o resultado, não de acesso a todo o estado interno. A escolha concreta continua a existir em algum lado, normalmente na construção ou configuração do inimigo. Se o algoritmo é fixo e pequeno, separar várias classes pode não ajudar.

## State: reagir conforme o estado

**State** delega o comportamento num objeto que representa o estado atual. As operações podem mudar esse estado. O foco é o ciclo de vida do contexto, em vez da seleção de um algoritmo pelo cliente.

Este programa completo mostra um jogo que começa ativo. Guarda-o em `Main.java` para correr localmente:

```java
interface Estado {
    void tick(Jogo jogo);
    void alternar(Jogo jogo);
}

class Ativo implements Estado {
    public void tick(Jogo jogo) { jogo.avancar(); }
    public void alternar(Jogo jogo) { jogo.mudar(new Pausa()); }
}

class Pausa implements Estado {
    public void tick(Jogo jogo) { }
    public void alternar(Jogo jogo) { jogo.mudar(new Ativo()); }
}

class Jogo {
    private Estado estado = new Ativo();
    private int passos;
    void tick() { estado.tick(this); }
    void alternar() { estado.alternar(this); }
    void mudar(Estado novo) { estado = novo; }
    void avancar() { passos++; }
    int getPassos() { return passos; }
}

public class Main {
    public static void main(String[] args) {
        Jogo jogo = new Jogo();
        jogo.tick();
        jogo.alternar();
        jogo.tick();
        jogo.alternar();
        jogo.tick();
        System.out.println(jogo.getPassos());
    }
}
```

A saída é `2`. O primeiro e o terceiro `tick` avançam; o segundo é tratado em Pausa e não altera o contador. A transição é definida pelos estados. Poderíamos deixá-la no contexto, desde que houvesse um responsável claro.

State e Strategy podem ter estruturas parecidas. A intenção distingue-os: trocar perseguição por patrulha é Strategy; reagir de outra forma depois de entrar em Pausa é State. Um pequeno conjunto de estados também pode ser representado por uma enumeração e condições sem perder clareza.

## Command: guardar um pedido

**Command** representa um pedido como objeto. O invocador não precisa de conhecer os detalhes da operação; o comando conhece o recetor e os dados necessários. Podemos guardar comandos numa fila ou num histórico.

Para desfazer um movimento, precisamos do estado anterior. Fazer o movimento inverso nem sempre recupera esse estado, por exemplo quando colisões ou limites impediram parte da ação.

  }
/>

Obtemos `5` e `2`. `Main` é o invocador; `Mover` o comando concreto; `Heroi` o recetor. Este exemplo supõe que nada altera o herói entre executar e desfazer. Num histórico, desfaz os comandos por ordem inversa. Um pedido com efeitos externos, como enviar uma mensagem, pode não ter inversão exata; o padrão não garante undo automaticamente.

## Observer: notificar interessados

**Observer** permite que um sujeito notifique vários observadores através de um contrato. O sujeito não conhece as classes concretas que reagem. Cada interessado subscreve e deve poder deixar de subscrever.

Na pontuação, um observador pode atualizar o texto e outro verificar uma conquista. A sequência é: alterar o valor, obter o novo estado válido e notificar os inscritos. O observador pode receber o valor, modelo **push**, ou pedir o estado ao sujeito, modelo **pull**.

Este excerto mostra um sujeito com notificação síncrona:

```java
interface Observador {
    void mudou(int pontos);
}

class Pontuacao {
    private int pontos;
    private final java.util.List<Observador> observadores =
        new java.util.ArrayList<Observador>();

    void subscrever(Observador observador) { observadores.add(observador); }
    void remover(Observador observador) { observadores.remove(observador); }

    void somar(int valor) {
        pontos += valor;
        java.util.List<Observador> copia =
            new java.util.ArrayList<Observador>(observadores);
        for (Observador observador : copia) observador.mudou(pontos);
    }
}
```

A cópia estabiliza os destinatários desta notificação se um callback alterar a lista. O exemplo pressupõe uma única thread e callbacks que não voltam a alterar a pontuação. Num sistema real, decide também o que acontece se um observador lança uma exceção e se a remoção vale logo para a notificação atual ou apenas para as seguintes.

Uma referência esquecida na lista pode manter um observador vivo e continuar a enviar-lhe eventos. Por isso o ciclo de vida da subscrição faz parte do contrato.

## Composite: tratar uma árvore pela mesma interface

**Composite** usa uma interface comum para folhas e grupos. O grupo guarda filhos dessa interface, que podem ser folhas ou outros grupos. O cliente pede a operação sem testar qual é o caso.

Imagina um grupo de inimigos com força total. Uma folha devolve a sua força. Um grupo soma a força dos filhos; se um filho for outro grupo, a mesma chamada continua recursivamente.

Este programa completo imprime a força de uma árvore:

```java
import java.util.Arrays;
import java.util.List;

interface Unidade {
    int forca();
}

class Soldado implements Unidade {
    private final int valor;
    Soldado(int valor) { this.valor = valor; }
    public int forca() { return valor; }
}

class Grupo implements Unidade {
    private final List<Unidade> filhos;
    Grupo(Unidade... filhos) { this.filhos = Arrays.asList(filhos); }
    public int forca() {
        int total = 0;
        for (Unidade filho : filhos) total += filho.forca();
        return total;
    }
}

public class Main {
    public static void main(String[] args) {
        Unidade grupo = new Grupo(new Soldado(2),
            new Grupo(new Soldado(3), new Soldado(4)));
        System.out.println(grupo.forca());
    }
}
```

A saída é `9`. O parâmetro `Unidade... filhos` aceita zero ou mais argumentos, reunidos num array dentro do construtor. `Arrays.asList` permite percorrer esse array como lista; não faz uma cópia dos seus elementos.

`Unidade` é o componente, `Soldado` a folha e `Grupo` o composto. Nem todas as operações têm de pertencer à interface comum: acrescentar um filho pode ficar só em `Grupo`, para não obrigar uma folha a fingir que suporta filhos.

Composite não é o mesmo que composição UML. O padrão trata uma árvore uniformemente; a relação UML descreve posse. Se permitires partilhar filhos ou criar ciclos, precisas de regras explícitas para evitar contagens duplicadas ou recursão sem fim.

## Factory Method: subclasses escolhem o produto

**Factory Method** deixa uma operação de criação ser redefinida por subclasses do criador. A lógica que utiliza o produto depende da interface desse produto.

Este programa completo separa a criação da arma da lógica de ataque:

```java
interface Arma {
    int dano();
}

class Espada implements Arma {
    public int dano() { return 4; }
}

class Feitico implements Arma {
    public int dano() { return 7; }
}

abstract class Combatente {
    protected abstract Arma criarArma();
    int atacar() { return criarArma().dano(); }
}

class Guerreiro extends Combatente {
    protected Arma criarArma() { return new Espada(); }
}

class Mago extends Combatente {
    protected Arma criarArma() { return new Feitico(); }
}

public class Main {
    public static void main(String[] args) {
        System.out.println(new Guerreiro().atacar());
        System.out.println(new Mago().atacar());
    }
}
```

A saída é `4` e `7`. `Combatente` é o criador; `criarArma` o factory method; `Guerreiro` e `Mago` os criadores concretos. `atacar` não escolhe classes de armas. Neste exemplo cria uma arma em cada ataque; guardar ou reutilizar o produto é uma decisão separada.

Evita chamar operações redefiníveis no construtor da base: o construtor da subclasse ainda pode não ter inicializado o estado de que elas dependem. Um método estático que contém um `switch` e devolve produtos pode ser uma fábrica simples, mas não demonstra esta colaboração por subclasses.

## Abstract Factory: escolher uma família

**Abstract Factory** fornece operações de criação para uma família de produtos relacionados. O cliente recebe a fábrica e usa as interfaces dos produtos. A fábrica concreta garante que as variantes pertencem à mesma família.

Uma arena pode ter uma fábrica de tema com `criarInimigo()` e `criarArma()`. A fábrica Medieval cria um cavaleiro e uma espada; a fábrica Espacial cria um robô e um laser. Trocar a fábrica troca a família sem editar o cliente que monta a arena.

O contrato das interfaces pode ser este excerto:

```java
interface FabricaTema {
    Inimigo criarInimigo();
    Arma criarArma();
}

interface Inimigo {
    String descricao();
}

interface Arma {
    int dano();
}
```

A implementação concreta fornece ambos os métodos. Acrescentar outra família é simples: outra fábrica e produtos. Acrescentar um novo **tipo de produto**, como `criarEscudo()`, exige mudar o contrato e todas as fábricas. Esta é uma consequência que deve pesar na escolha.

Factory Method resolve a decisão de um produto numa hierarquia de criadores. Abstract Factory fornece uma família através de um objeto fábrica. Uma Abstract Factory pode implementar os seus métodos de criação usando Factory Methods, mas as intenções continuam distintas.

## Adapter e Decorator

**Adapter** traduz uma interface existente para o contrato de que o cliente precisa. **Decorator** envolve um objeto, conserva a interface e acrescenta comportamento. Ambos usam composição, mas não resolvem o mesmo problema.

Neste exemplo, o cliente precisa de um preço em cêntimos. A biblioteca antiga fornece euros inteiros, por isso o adapter converte unidades. Um decorator acrescenta a taxa de entrega.

  }
/>

Obtemos `1200` e `1450`. O adapter permite usar a classe antiga sem a alterar. O decorator aceita qualquer `Preco`, incluindo outro decorator. Se aplicares duas entregas, cobras duas taxas; a composição não valida sozinha se essa combinação tem sentido.

Num adapter real, define também erros, unidades e conversões que podem perder informação. Num decorator, a ordem pode mudar o resultado: aplicar 10% de desconto antes ou depois de acrescentar 250 cêntimos não produz sempre o mesmo total. A interface comum não torna as operações comutativas.

## Singleton: uma instância com acesso global

**Singleton** impõe uma instância e um ponto global de acesso. Um exemplo Java com criação antecipada é:

```java
final class Configuracao {
    private static final Configuracao INSTANCIA = new Configuracao();
    private Configuracao() { }
    static Configuracao instancia() { return INSTANCIA; }
}
```

A inicialização da classe protege a criação da instância segundo as regras de Java. Isso não torna automaticamente thread-safe qualquer estado mutável acrescentado à classe. Uma implementação lazy sem sincronização pode criar mais de uma instância em acessos concorrentes.

O acesso global esconde dependências e pode fazer testes partilharem estado. Se a aplicação precisa de uma configuração única, muitas vezes podes criá-la uma vez na montagem e passá-la aos clientes. Ter uma instância durante uma execução é diferente de proibir outras instâncias pelo tipo.

## Escolher pelo problema

Quando vês classes com a mesma estrutura, pergunta quem decide variar e o que o cliente precisa de ignorar. Strategy varia um algoritmo; State varia a reação conforme o estado; Command guarda um pedido; Observer distribui notificações. Composite trata folhas e grupos; Adapter traduz; Decorator acrescenta responsabilidades. As fábricas separam criação; Singleton restringe instâncias e acrescenta acesso global.

Depois explica o custo. Um padrão pode acrescentar objetos, interfaces, gestão de ciclo de vida ou restrições de teste. A solução deve tornar uma mudança concreta mais simples e preservar um contrato compreensível.
