<Exercise
  id="git-snapshot"
  title="O que entra no commit?"
  explanation="/cadeiras/ldts/controlo-versoes/#as-três-áreas-do-git"
  answer={{
    kind: 'choice',
    options: [
      {
        text: 'A',
        correct: false,
        explanation: 'O add substituiu o conteúdo preparado por B.',
      },
      {
        text: 'B',
        correct: true,
        explanation: 'O commit usa o índice, que continua com B.',
      },
      {
        text: 'C',
        correct: false,
        explanation: 'A edição posterior ficou apenas no working tree.',
      },
    ],
  }}
>
  <p>
    O ficheiro seguido contém A. Editas para B, fazes{' '}
    <code>git add regra.txt</code>, editas para C e fazes commit sem outro add.
    Que conteúdo fica no novo commit?
  </p>
  <div slot="hint">
    <p>Distingue a versão no ficheiro da versão no índice.</p>
  </div>
  <div slot="hint-more">
    <p>O add copiou B; a edição para C não repetiu essa cópia.</p>
  </div>
  <div slot="solution">
    <p>
      O commit guarda B. C continua como mudança local. O diff normal compara C
      com B; o diff preparado compara B com A.
    </p>
  </div>
  <div slot="mistakes">
    <p>Não confundas guardar no editor com preparar no índice.</p>
  </div>
</Exercise>

<Exercise
  id="git-merge-pais"
  title="Contar os pais de um merge"
  explanation="/cadeiras/ldts/controlo-versoes/#branches-e-merges"
  answer={{ kind: 'number', value: 2, tolerance: 0 }}
>
  <p>
    Main e funcionalidade têm commits diferentes depois do mesmo antepassado. Um
    merge normal combina ambos e cria M. Quantos pais diretos tem M?
  </p>
  <div slot="hint">
    <p>Cada histórico integrado termina num commit.</p>
  </div>
  <div slot="hint-more">
    <p>
      M precisa de apontar para as duas pontas anteriores, não para todos os
      antepassados.
    </p>
  </div>
  <div slot="solution">
    <p>
      M tem dois pais diretos. Cada pai permite alcançar os seus próprios
      antepassados. Num fast-forward, não seria preciso criar M.
    </p>
  </div>
  <div slot="mistakes">
    <p>Não contes todos os commits do grafo como pais diretos.</p>
  </div>
</Exercise>

<Exercise
  id="gradle-teste-dependencia"
  title="Escolher o âmbito da dependência"
  explanation="/cadeiras/ldts/controlo-versoes/#dependências-com-gradle"
  answer={{
    kind: 'self',
    checklist: [
      'Indica testImplementation para compilar os testes.',
      'Distingue dependências dos testes das do programa.',
      'Refere o motor/plataforma necessário em runtime dos testes.',
    ],
  }}
>
  <p>
    JUnit só é usado pelos testes. Justifica em que configuração colocarias a
    dependência e por que o programa não deve precisar dela para arrancar.
  </p>
  <div slot="hint">
    <p>Pergunta em que conjunto de fontes aparecem os imports.</p>
  </div>
  <div slot="hint-more">
    <p>Os imports do JUnit estão em src/test/java, não em src/main/java.</p>
  </div>
  <div slot="solution">
    <p>
      JUnit Jupiter fica em testImplementation. A plataforma e o motor têm de
      estar disponíveis para executar os testes. O programa distribuído não
      precisa de carregar JUnit só porque tem testes.
    </p>
  </div>
  <div slot="mistakes">
    <p>
      Uma dependência de runtime dos testes não é necessariamente uma
      dependência de runtime do programa.
    </p>
  </div>
</Exercise>
