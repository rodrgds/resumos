  <div>
    Uma lista L começa com um elemento. Um método recebe L, acrescenta outro
    elemento e depois atribui uma lista vazia ao parâmetro. Quantos elementos
    tem L depois da chamada?
  </div>
  <div slot="hint">
    <div>Desenha duas referências para o objeto inicial.</div>
  </div>
  <div slot="hint-more">
    <div>
      Acrescentar altera o objeto; a atribuição muda só a referência local.
    </div>
  </div>
  <div slot="solution">

    </div>

>
  <div>
    Duas posições diferentes em memória têm as mesmas coordenadas. O tipo
    redefine `equals` corretamente, mas usa um hash dependente da identidade.

  <div slot="hint">

  <div>
    Um método só lê números de uma lista e chama doubleValue em cada um. Deve
    aceitar List&lt;Integer&gt; e List&lt;Double&gt;. Qual é o parâmetro
    adequado?
  </div>
  <div slot="hint">
    <div>A lista fornece valores ao método.</div>
  </div>
  <div slot="hint-more">
    <div>
      Precisamos de ler como Number, sem acrescentar um tipo arbitrário.
    </div>
  </div>
  <div slot="solution">
    <div>
      Usa List&lt;? extends Number&gt;. Integer e Double são subtipos de Number,

    </div>

>
  <div>
    Uma equipa guarda diretamente a lista de nomes recebida no construtor. O getter devolve `Collections.unmodifiableList(nomes)`. O chamador conserva a lista original e acrescenta `"Rita"`. A equipa prometia conservar os nomes do momento da construção. Explica a falha e corrige a fronteira de entrada e a de saída. Os nomes são strings.
  </div>
  <div slot="hint">
    Conta quantas referências chegam à lista que a equipa guardou.
  </div>
  <div slot="hint-more">
    A proibição do getter só atua sobre alterações feitas através dessa vista.
  </div>
  <div slot="solution">
    O estado da equipa passa a incluir Rita porque o campo e o chamador partilham a lista. No construtor, guarda `new ArrayList<String>(nomesRecebidos)`. <Exercise
  revision={2}
  id="java-genericos-proprios"
  title="Copiar entre listas com tipos diferentes"
  explanation="/cadeiras/ldts/java-orientado-objetos/#genéricos-e-wildcards"
  answer={{ kind: 'self', checklist: [
    'Declarei um parâmetro de tipo antes de `void`.',
    'Usei `extends` na origem e `super` no destino.',
    'Justifiquei a rejeição de `List<Double>` como destino dos `Integer`.',
  ] }}
>
  <div>

Escreve a assinatura e o corpo de um método genérico `copiar(origem, destino)` que acrescenta todos os elementos da origem ao fim do destino, sem casts. Ambas as listas são não nulas e diferentes, e o destino permite acrescentar elementos.

O método deve aceitar uma origem `List<Integer>` com `[2, 3]` e um destino `List<Number>` que já contém `1.5`. Mostra o conteúdo final e explica por que não deve aceitar `List<Double>` como destino dessa mesma origem.

  </div>
  <div slot="hint">A origem produz valores; o destino tem de aceitar esses valores.</div>
  <div slot="solution">

```java
static <T> void copiar(List<? extends T> origem, List<? super T> destino) {
    for (T valor : origem) destino.add(valor);
}
```

Com `T = Integer`, o destino `List<Number>` aceita os inteiros e fica `[1.5, 2, 3]`. A origem pode produzir valores lidos como T; o destino pode receber T. `Double` não é supertipo de `Integer`, por isso uma lista de Double não pode receber esses objetos. O compilador não converte automaticamente cada Integer para Double. O método declara T; os wildcards descrevem como cada lista o usa.

  </div>
</Exercise>

<Exercise
  revision={1}
  id="java-despacho"
  title="Sobrecarga e redefinição na mesma chamada"
  explanation="/cadeiras/ldts/java-orientado-objetos/#herança-interfaces-e-composição"
  answer={{
    kind: 'self',
    checklist: [
      'Obtém geral: gato.',
      'Escolhe visitar(Animal) pelo tipo declarado da variável.',
      'Escolhe Gato.falar pelo objeto em tempo de execução.',
    ],
  }}
>
  <div>

Considera este excerto. `Gato` redefine `falar()` de `Animal`:

```java
class Animal { String falar() { return "animal"; } }
class Gato extends Animal {
    @Override String falar() { return "gato"; }
}

// Estes dois métodos pertencem à classe Main.
static String visitar(Animal a) { return "geral: " + a.falar(); }
static String visitar(Gato g) { return "gato: " + g.falar(); }

// Estas chamadas pertencem ao método main de Main.
Animal a = new Gato();
System.out.println(visitar(a));
```

Prevê a linha escrita e explica como Java escolhe cada método.

  </div>
  <div slot="hint">
    As duas escolhas acontecem em momentos diferentes.
  </div>
  <div slot="hint-more">
    A variável passada chama-se a e tem tipo Animal. O objeto criado tem classe Gato.
  </div>
  <div slot="solution">
    A linha é `geral: gato`. A resolução da sobrecarga seleciona `visitar(Animal)` na compilação, porque `a` tem tipo declarado `Animal`. Dentro desse método, a chamada de instância a `falar()` usa a implementação de `Gato`, escolhida pelo objeto em tempo de execução. Não houve cast nem mudança de tipo da variável.
  </div>
  <div slot="mistakes">
    O tipo concreto do objeto não faz Java reconsiderar automaticamente todas as sobrecargas na execução.
  </div>
</Exercise>

<Exercise
  id="java-byte-promocao"
  revision={1}
  title="O cálculo cabe em int, o campo é byte"
  explanation="/cadeiras/ldts/java-orientado-objetos/#promoção-e-overflow-inteiro"
  answer={{ kind: 'self', checklist: ['Obtive 128 para soma e -127 para b.', 'Distingui promoção para int de conversão implícita em ++ e +=.', 'Expliquei por que a atribuição simples b = b + 1 não compila e o cast não recupera capacidade.'] }}
>

Considera este corpo de `main`:

```java
byte b = 127;
int soma = b + 1;
b++;
b += 1;
System.out.println(soma + " " + b);
```

Prevê a saída. Se substituirmos `b++` por `b = b + 1`, o programa compila? E por `b = (byte) (b + 1)`? Justifica cada caso pelos tipos e pelo intervalo de `byte`.

<div slot="solution">
A saída é `128 -127`. A soma inicial promove b para int, calcula 128 e não altera b. O incremento calcula o novo valor e converte-o de volta para byte: 127 passa a -128. A atribuição composta seguinte passa a -127.

`b = b + 1` não compila porque o resultado é int e a atribuição simples não autoriza essa redução implicitamente. Com o cast explícito, compila e volta a obter -128 nesse passo, terminando também em -127. O cast conserva os oito bits menos significativos; não aumenta a capacidade do byte nem lança uma exceção por este overflow.

</div>
</Exercise>

<Exercise
  id="java-equals-assinatura"
  revision={1}
  title="Um teste de igualdade que só passa com um tipo"
  explanation="/cadeiras/ldts/java-orientado-objetos/#a-assinatura-de-equals"
  answer={{ kind: 'self', checklist: ['Obtive true na primeira chamada e false na segunda.', 'Identifiquei a sobrecarga equals(Posicao), sem redefinir equals(Object).', 'Corrigi a assinatura e indiquei teste através de Object e hash compatível.'] }}
>

O tipo seguinte pretende comparar posições pela coordenada x:

```java
final class Posicao {
    private final int x;
    Posicao(int x) { this.x = x; }
    public boolean equals(Posicao outra) {
        return outra != null && x == outra.x;
    }
    @Override public int hashCode() { return x; }
}
```

Duas posições `a` e `b` são criadas separadamente com x igual a 7. Prevê `a.equals(b)` e `a.equals((Object) b)`. Diagnostica o erro e escreve a redefinição correta. Que verificação evitaria aceitar a versão original só porque o primeiro resultado é verdadeiro?

<div slot="solution">
A primeira chamada dá true: a compilação escolhe a sobrecarga equals(Posicao). A segunda dá false: o argumento tem tipo Object, seleciona equals(Object) herdado, que compara identidade; os objetos são distintos. O hash igual não obriga essa igualdade.

A redefinição correta é:

```java
@Override
public boolean equals(Object outra) {
    if (this == outra) return true;
    if (!(outra instanceof Posicao)) return false;
    Posicao p = (Posicao) outra;
    return x == p.x;
}
```

O tipo é final, a coordenada é imutável e o hash x é compatível com esta igualdade. Testa a operação também com argumento declarado Object, objetos diferentes e null; numa coleção hash, verifica que duas posições de x igual contam uma vez. Colocar @Override na assinatura errada faz o compilador recusá-la antes dos testes.

</div>
</Exercise>

<Exercise
  id="java-treeset-coordenadas"
  revision={1}
  title="Duas posições distintas, uma entrada"
  explanation="/cadeiras/ldts/java-orientado-objetos/#ordem-e-unicidade-num-treeset"
  answer={{ kind: 'self', checklist: ['Obtive false na inserção de (2,9) e tamanho 2 depois das três tentativas.', 'Relacionei comparação zero com equivalência no TreeSet.', 'Comparei x e depois y, sem subtração sujeita a overflow, coerente com equals.'] }}
>

`Posicao` é imutável e redefine corretamente `equals` e `hashCode` pelas duas coordenadas inteiras x e y. Um `TreeSet<Posicao>` recebe um comparator que compara **só x**. Inserimos, nesta ordem, `(2,1)`, `(2,9)` e `(1,5)`.

Que resultado dá a segunda chamada a `add`? Qual é o tamanho e que posição com x igual a 2 fica guardada? Escreve um comparator que preserve todas as posições distintas e as ordene por x e depois y. Por que `a.getX() - b.getX()` não é uma alternativa segura para todos os inteiros?

<div slot="solution">
A segunda inserção dá false: comparar (2,1) e (2,9) só por x dá zero. O conjunto guarda a primeira, (2,1), e depois aceita (1,5), ficando com tamanho 2. Não consultou o equals para decidir que (2,9) era distinto.

```java
Comparator<Posicao> ordem = (a, b) -> {
    int porX = Integer.compare(a.getX(), b.getX());
    return porX != 0 ? porX : Integer.compare(a.getY(), b.getY());
};
```

Com essa ordem, fica (1,5), (2,1), (2,9). A comparação só dá zero quando ambas as coordenadas coincidem, de acordo com equals. Subtrair pode fazer overflow e trocar o sinal: `Integer.MIN_VALUE - 1` produz um valor positivo em int, embora o primeiro operando seja menor. Integer.compare determina a ordem sem essa subtração.

</div>
</Exercise>
