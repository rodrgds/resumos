<Exercise
  revision={1}
  id="java-alias"
  title="Prever uma alteração através de um parâmetro"
  explanation="/cadeiras/ldts/java-orientado-objetos/#valores-e-referências"
  answer={{ kind: 'number', value: 2, tolerance: 0 }}
>
  <div>
    Uma lista L começa com um elemento. Um método recebe L, acrescenta outro
    elemento e depois atribui uma lista vazia ao parâmetro. Quantos elementos
    tem L depois da chamada?
  </div>
  <div slot="hint">
    <div>Desenha duas referências para o objeto inicial.</div>
  </div>
  <div slot="hint-more">
    <div>
      Acrescentar altera o objeto; a atribuição muda só a referência local.
    </div>
  </div>
  <div slot="solution">
    <div>
      L tem dois elementos. O método recebeu uma cópia da referência, que
      apontava para o mesmo objeto. Reatribuir o parâmetro não muda a referência
      do chamador.
    </div>
  </div>
  <div slot="mistakes">
    <div>Java não passa a variável do chamador por referência.</div>
  </div>
</Exercise>

<Exercise
  revision={1}
  id="java-hash-contrato"
  title="Igualdade sem identidade"
  explanation="/cadeiras/ldts/java-orientado-objetos/#igualdade-e-hash"
  answer={{
    kind: 'self',
    checklist: [
      'Distingue identidade de igualdade por coordenadas.',
      'Afirma que objetos iguais têm de ter o mesmo hash.',
      'Deriva o hash de estado compatível com equals.',
    ],
  }}
>
  <div>
    Duas posições diferentes em memória têm as mesmas coordenadas. O tipo
    redefine equals corretamente, mas usa um hash dependente da identidade.
    Explica o problema num HashSet e a correção.
  </div>
  <div slot="hint">
    <div>O HashSet começa a procurar através do hash.</div>
  </div>
  <div slot="hint-more">
    <div>
      Se os objetos iguais forem colocados em grupos diferentes, a igualdade
      pode não ser consultada entre eles.
    </div>
  </div>
  <div slot="solution">
    <div>
      As posições são iguais pelo contrato, mas os hashes podem diferir,
      violando o contrato de hashCode. O conjunto pode aceitar duplicados
      lógicos ou falhar uma procura. Calcula o hash a partir das coordenadas e
      mantém esse estado estável enquanto está no conjunto.
    </div>
  </div>
  <div slot="mistakes">
    <div>
      Não é necessário que todos os objetos diferentes tenham hashes diferentes.
    </div>
  </div>
</Exercise>

<Exercise
  revision={1}
  id="java-wildcard"
  title="Receber números de tipos diferentes"
  explanation="/cadeiras/ldts/java-orientado-objetos/#genéricos-e-wildcards"
  answer={{
    kind: 'choice',
    options: [
      {
        text: '`List<Number>`',
        correct: false,
        explanation: 'A invariância impede passar diretamente List<Integer>.',
      },
      {
        text: '`List<? extends Number>`',
        correct: true,
        explanation: 'Cada elemento pode ser lido como Number.',
      },
      {
        text: '`List<? super Number>`',
        correct: false,
        explanation:
          'Ao ler, só podemos assumir Object, e listas de Integer não satisfazem esse limite.',
      },
    ],
  }}
>
  <div>
    Um método só lê números de uma lista e chama doubleValue em cada um. Deve
    aceitar List&lt;Integer&gt; e List&lt;Double&gt;. Qual é o parâmetro
    adequado?
  </div>
  <div slot="hint">
    <div>A lista fornece valores ao método.</div>
  </div>
  <div slot="hint-more">
    <div>
      Precisamos de ler como Number, sem acrescentar um tipo arbitrário.
    </div>
  </div>
  <div slot="solution">
    <div>
      Usa List&lt;? extends Number&gt;. Integer e Double são subtipos de Number,
      e ambos fornecem doubleValue. A lista continua a poder ser mutável; o
      wildcard não dá imutabilidade.
    </div>
  </div>
  <div slot="mistakes">
    <div>
      Não acrescentes um Double a uma lista cujo tipo concreto pode ser Integer.
    </div>
  </div>
</Exercise>

<Exercise
  revision={1}
  id="java-copia-defensiva"
  title="Um getter não modificável chega?"
  explanation="/cadeiras/ldts/java-orientado-objetos/#proteger-uma-coleção"
  answer={{
    kind: 'self',
    checklist: [
      'Reconhece que a vista acompanha alterações na lista original.',
      'Copia a lista recebida no construtor.',
      'Não expõe a lista interna para alterações e distingue cópia superficial de cópia dos elementos.',
    ],
  }}
>
  <div>
    Uma equipa guarda diretamente a lista de nomes recebida no construtor. O getter devolve `Collections.unmodifiableList(nomes)`. O chamador conserva a lista original e acrescenta `"Rita"`. A equipa prometia conservar os nomes do momento da construção. Explica a falha e corrige a fronteira de entrada e a de saída. Os nomes são strings.
  </div>
  <div slot="hint">
    Conta quantas referências chegam à lista que a equipa guardou.
  </div>
  <div slot="hint-more">
    A proibição do getter só atua sobre alterações feitas através dessa vista.
  </div>
  <div slot="solution">
    O estado da equipa passa a incluir Rita porque o campo e o chamador partilham a lista. No construtor, guarda `new ArrayList<String>(nomesRecebidos)`. No getter, devolve uma vista não modificável dessa lista privada ou uma cópia, conforme o contrato. As strings são imutáveis, por isso partilhá-las não permite alterar os nomes. Se os elementos fossem mutáveis, esta cópia da coleção não bastaria para os tornar independentes.
  </div>
  <div slot="mistakes">
    `final` no campo também não impede o chamador de alterar o objeto partilhado.
  </div>
</Exercise>

<Exercise
  revision={1}
  id="java-despacho"
  title="Sobrecarga e redefinição na mesma chamada"
  explanation="/cadeiras/ldts/java-orientado-objetos/#herança-interfaces-e-composição"
  answer={{
    kind: 'self',
    checklist: [
      'Obtém geral: gato.',
      'Escolhe visitar(Animal) pelo tipo declarado da variável.',
      'Escolhe Gato.falar pelo objeto em tempo de execução.',
    ],
  }}
>
  <div>

Considera este excerto. `Gato` redefine `falar()` de `Animal`:

```java
class Animal { String falar() { return "animal"; } }
class Gato extends Animal {
    @Override String falar() { return "gato"; }
}

// Estes dois métodos pertencem à classe Main.
static String visitar(Animal a) { return "geral: " + a.falar(); }
static String visitar(Gato g) { return "gato: " + g.falar(); }

// Estas chamadas pertencem ao método main de Main.
Animal a = new Gato();
System.out.println(visitar(a));
```

Prevê a linha escrita e explica como Java escolhe cada método.

  </div>
  <div slot="hint">
    As duas escolhas acontecem em momentos diferentes.
  </div>
  <div slot="hint-more">
    A variável passada chama-se a e tem tipo Animal. O objeto criado tem classe Gato.
  </div>
  <div slot="solution">
    A linha é `geral: gato`. A resolução da sobrecarga seleciona `visitar(Animal)` na compilação, porque `a` tem tipo declarado `Animal`. Dentro desse método, a chamada de instância a `falar()` usa a implementação de `Gato`, escolhida pelo objeto em tempo de execução. Não houve cast nem mudança de tipo da variável.
  </div>
  <div slot="mistakes">
    O tipo concreto do objeto não faz Java reconsiderar automaticamente todas as sobrecargas na execução.
  </div>
</Exercise>
