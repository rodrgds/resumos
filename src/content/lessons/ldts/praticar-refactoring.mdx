<Exercise
  revision={2}
  id="refactoring-preco"
  title="Distinguir simplificação de mudança de tarifa"
  explanation="/cadeiras/ldts/smells-refactoring/#exemplo-extrair-a-regra-do-preço"
  answer={{ kind: 'self', checklist: [
    'Apresentei uma quantidade acima de cinco para a qual B muda o preço.',
    'Justifiquei as parcelas da versão A nos dois intervalos.',
    'Conservei a validação de 0 a 1000 e os erros observáveis.',
  ] }}
>
  <div>

A tarifa aceita de 0 a 1000 unidades. As primeiras cinco custam 200 cêntimos cada; as adicionais custam 150. Duas propostas pretendem simplificar só o cálculo:

```java
// A
Math.min(n, 5) * 200 + Math.max(0, n - 5) * 150
// B
n * (n > 5 ? 150 : 200)
```

Qual preserva a tarifa para todas as quantidades válidas? Justifica por intervalos e dá um contraexemplo para a outra. O que deve acontecer à validação e à mensagem de erro durante a refatoração?

  </div>
  <div slot="hint">Acima de cinco unidades, as primeiras cinco continuam a custar 200 cada.</div>
  <div slot="solution">
    A preserva a regra. Para 0 a 5, `min(n, 5)` dá n e `max(0, n - 5)` dá zero. Para 6 a 1000, a primeira parcela é 1000 e a segunda cobra só as unidades adicionais. Com n = 6, A dá 1150 e B dá 900: B aplica retroativamente 150 a todas as unidades. Mantemos a rejeição de -1 e 1001, o tipo `IllegalArgumentException` e a mensagem original. Uma fórmula equivalente no domínio válido não autoriza aceitar entradas que antes eram rejeitadas.
  </div>
</Exercise>

<Exercise

>
  <div>
    Um método verifica primeiro nome vazio e depois idade negativa, lançando
    erros diferentes. Uma refatoração troca a ordem. Quando a entrada viola
    ambos, o comportamento está preservado?
  </div>
  <div slot="hint">
    <div>Compara a exceção observada para a mesma entrada.</div>
  </div>
  <div slot="hint-more">
    <div>Na primeira versão o nome vence; na segunda pode vencer a idade.</div>
  </div>
  <div slot="solution">
    <div>
      Percorre a entrada que viola ambos: antes, o erro é de nome; depois da
      troca, o erro é de idade. Não necessariamente. A mesma entrada pode
      receber um erro diferente. Conserva a ordem se o contrato a exige ou trata
      a mudança de regra separadamente.
    </div>
  </div>
  <div slot="mistakes">
    <div>Ter testes verdes incompletos não demonstra equivalência.</div>
  </div>
</Exercise>

<Exercise

      'Não decide pela contagem de chamadas.',

>
  <div>
    Um serializador consulta dez atributos de uma entidade para construir texto.
    Um colega propõe movê-lo para a entidade porque tem mais chamadas à entidade
    do que a si próprio. Avalia a justificação.
  </div>
  <div slot="hint">
    <div>Pergunta quem deve conhecer o formato externo.</div>
  </div>
  <div slot="hint-more">
    <div>Ler dados é parte da função de um serializador.</div>
  </div>
  <div slot="solution">
    <div>
      A contagem é um sinal insuficiente. Se o método só traduz a entidade para
      um formato externo, o serializador pode ser o responsável certo. Mover o
      formato para a entidade pode juntar razões de mudança independentes. Se o
      método calcula uma regra do domínio, investiga essa parte separadamente.
    </div>
  </div>
  <div slot="mistakes">
    <div>
      Feature Envy não obriga a mover todo o código que consulta muitos getters.
    </div>
  </div>
</Exercise>
