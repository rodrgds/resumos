Acrescentar um inimigo não devia exigir alterar a leitura de teclas nem os testes de posições. Se essas alterações aparecem juntas, procura a decisão que atravessa os módulos. Os cinco princípios SOLID ajudam a separar responsabilidades e a manter os contratos dos clientes.

## Os cinco princípios

| Princípio                  | Pergunta a fazer ao desenho                                                   |
| -------------------------- | ----------------------------------------------------------------------------- |
| SRP, Single Responsibility | Esta classe junta razões independentes para mudar?                            |
| OCP, Open/Closed           | Consigo acrescentar esta alternativa sem reescrever os clientes estáveis?     |
| LSP, Liskov Substitution   | O subtipo mantém todas as promessas que o cliente da base usa?                |
| ISP, Interface Segregation | O cliente depende de operações que não precisa?                               |
| DIP, Dependency Inversion  | A regra da aplicação depende de detalhes externos ou de um contrato adequado? |

Uma classe não precisa de ser pequena para ter uma responsabilidade coerente. E uma aplicação não precisa de uma interface para cada classe. Vamos justificar cada princípio através de uma mudança concreta.

Para cada princípio, identifica uma alteração concreta que motivaria a separação. Distingue implementar uma interface de cumprir o seu contrato.

## SRP: uma razão para mudar

Uma `Pontuacao` calcula pontos, escreve um ficheiro e desenha um texto no ecrã. As regras de pontuação, o formato do ficheiro e a apresentação podem mudar por motivos independentes. Separar essas decisões evita que mudar o formato altere a regra do jogo.

O modelo pode fornecer o valor e operações válidas. Um adaptador guarda-o. Uma vista apresenta-o. Métodos relacionados com a mesma regra podem continuar juntos.

Concretiza numa pontuação. Antes, tudo vive junto:

```java
class Pontuacao {
    int pontos;
    void somar(int v) { pontos += v; }
    void guardarFicheiro() { /* formato + I/O aqui */ }
    void desenharEcra() { /* texto gráfico aqui */ }
}
```

Mudar o formato do ficheiro reedita a classe da regra do jogo. Depois, cada razão de mudança tem um dono:

```java
class Pontos { /* regra: somar, limites */ }
class PontuacoesFicheiro { /* formato + escrita */ }
class PontosVista { /* apresentação */ }
```

```text
antes:  Pontuacao --> Ficheiro, Ecra, Regra
depois: Jogo --> Pontos; PontuacoesFicheiro --> Pontos; PontosVista --> Pontos
```

A regra fica estável quando o formato muda. Dividir cada método numa classe sem separar uma decisão útil só cria ligações novas.

Se o designer muda a cor do texto, altera `PontosVista`. Se a regra passa a atribuir dois pontos por inimigo, altera `Pontos`. São pedidos independentes. A separação tem de se refletir nas dependências: o modelo não chama a vista para validar a soma.

## OCP: escolher onde permitir extensão

Imagina um controlador que recebe a tecla e contém um `switch` com todos os comandos. Cada comando novo altera o mesmo método. Se as ações variam frequentemente, o controlador pode depender de uma interface `Comando`, cujo `executar()` cada ação implementa.

Acrescentar uma classe e registá-la ainda muda a configuração da aplicação. OCP protege o cliente que usa o contrato, não promete que nenhum ficheiro possa mudar. Também não obriga a prever todas as extensões futuras.

Um mapa de comandos tem sentido quando queremos trocar ações sem alterar o controlador. Um `switch` pequeno sobre uma enumeração fechada pode continuar a ser a solução mais clara.

## LSP: substituição é um contrato

Suponhamos que `Retangulo` permite alterar largura sem alterar altura. O cliente escolhe largura 4 e altura 3, e espera área 12. Uma subclasse `Quadrado` que faz cada setter alterar ambas as dimensões produz área 9. O subtipo viola o contrato usado pelo cliente.

  }
/>

A saída é `12` e `9`. A relação matemática entre figuras não basta para justificar a herança de uma API mutável. Poderíamos definir uma interface imutável `Forma` com `area()`, sem prometer setters independentes, e deixar retângulos e quadrados implementá-la.

Em termos de contratos, um subtipo não deve exigir pré-condições mais fortes nem garantir pós-condições mais fracas. Deve também preservar os invariantes e as propriedades de evolução do estado que a base promete. Se a base aceita um valor positivo, o subtipo não pode passar a aceitar apenas valores acima de dez sem quebrar clientes válidos.

## ISP: interfaces segundo os clientes

Uma interface `Dispositivo` com `lerTecla`, `desenhar` e `tocarSom` obriga um teclado a implementar operações irrelevantes. Métodos vazios ou `UnsupportedOperationException` podem revelar esse problema.

Separa `Entrada`, `Vista` e `Audio` quando os clientes precisam dessas capacidades em separado. Um objeto real pode implementar várias interfaces. O controlador que só lê teclas depende de `Entrada`, por isso uma alteração ao áudio não muda o seu contrato.

A divisão deve seguir usos coerentes. Uma interface com uma única operação não é automaticamente melhor que outra com várias operações relacionadas.

## DIP: a regra define o contrato

Uma regra de fim de jogo que cria diretamente `FicheiroPontuacoes` passa a depender da pasta, do formato e das falhas do sistema de ficheiros. Em vez disso, define o que precisa, por exemplo `Pontuacoes.guardar(int valor)`. O adaptador de ficheiro implementa esse contrato.

O código de alto nível depende da abstração. O detalhe também depende dessa abstração para a implementar. A escolha do adaptador concreto fica na montagem da aplicação, normalmente perto do `main`.

Este excerto mostra a fronteira:

```java
interface Pontuacoes {
    void guardar(int valor);
}

class FimDeJogo {
    private final Pontuacoes pontuacoes;

    FimDeJogo(Pontuacoes pontuacoes) {
        this.pontuacoes = pontuacoes;
    }

    void concluir(int valor) {
        if (valor < 0) throw new IllegalArgumentException("pontos negativos");
        pontuacoes.guardar(valor);
    }
}
```

**Injeção de dependências** é passar o colaborador ao objeto, como no construtor. **Inversão de dependências** é a decisão sobre de que contratos os módulos dependem. Passar uma classe concreta pelo construtor é injeção, mas não demonstra por si só DIP.

A interface deve usar conceitos da regra, não obrigar o modelo a fornecer um caminho de ficheiro ou uma instrução SQL. Os testes podem passar uma implementação em memória ou um substituto controlado.

```text
FimDeJogo --usa--> Pontuacoes <--implementa-- FicheiroPontuacoes
                            <--implementa-- PontuacoesMemoria
```

As setas mostram dependências do código. A regra não importa os adaptadores. Em execução, a chamada continua a ir da regra para o objeto concreto que a montagem forneceu. Inverter dependências não inverte a ordem das chamadas.

## Coesão, acoplamento e pacotes

**Coesão** descreve como os elementos de um módulo colaboram numa responsabilidade. **Acoplamento** descreve quanto um módulo depende de outros e das suas decisões. Queremos dependências necessárias e explícitas, não eliminar toda a colaboração.

Classes que mudam juntas por uma razão comum podem pertencer ao mesmo pacote. Um ciclo entre pacotes torna mais difícil alterar ou reutilizar um deles isoladamente. Para o quebrar, localiza a dependência indevida e extrai um contrato no lado que precisa da capacidade.

Se `modelo` importa `vista`, uma regra do jogo passa a exigir a interface gráfica. Os princípios de pacotes pedem o mesmo raciocínio a maior escala: pacotes estáveis com contratos claros, sem ciclos que impeçam reutilizar um lado isolado. Inverter essa dependência permite reutilizar o modelo numa vista de terminal e nos testes. A lição de [MVC](/cadeiras/ldts/mvc-projeto/) aplica esta separação a uma interação completa.

## Justificar uma decisão

Antes de acrescentar uma abstração, escreve a mudança que ela deve suportar. Depois identifica o cliente que deve ficar estável e o contrato que as alternativas partilham. Finalmente compara a complexidade adicional com a dependência que removeste.

Por exemplo, trocar ficheiros por armazenamento em memória deve preservar `FimDeJogo`. O contrato `Pontuacoes` permite isso. Criar três interfaces entre duas funções puras sem qualquer alternativa concreta não resolve o mesmo problema.
