A regra de preço está repetida em três classes. Uma alteração exige editar as três e pode deixar respostas diferentes. Esse é um problema de manutenção concreto. Vamos reconhecer o sinal e melhorar a estrutura sem aproveitar a mudança para alterar a regra.

## O que é refactoring

**Refactoring**, ou refatoração, é uma transformação da estrutura interna que preserva o comportamento observável. Extrair um método ou mover uma regra pode mudar o local do código sem mudar valores, efeitos, erros ou ordem relevante.

Os testes ajudam a detetar alterações, mas não são uma prova completa de equivalência. Antes de transformar, identifica o contrato e os casos que poderiam mudar. Corrigir um erro e refatorar são passos diferentes: a correção muda um comportamento incorreto; a refatoração preserva o comportamento decidido.

## Os cheiros mais comuns

Um **code smell** é um sinal para investigar, não uma demonstração automática de mau código. Não existe um número de linhas que decida sozinho se um método está errado.

| Sinal               | Problema a investigar                                     | Transformação possível                                       |
| ------------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| Long Method         | Várias intenções e níveis de detalhe no mesmo método.     | Extract Method, com nomes que expliquem as intenções.        |
| Large Class         | Razões independentes para alterar a mesma classe.         | Extract Class.                                               |
| Duplicate Code      | A mesma regra exige mudanças em vários sítios.            | Extrair a regra para um responsável comum.                   |
| Feature Envy        | Uma operação depende sobretudo dos dados de outro objeto. | Move Method, se esse objeto deve ser responsável pela regra. |
| Data Clumps         | Um grupo de valores viaja sempre junto.                   | Introduce Parameter Object ou um tipo do domínio.            |
| Primitive Obsession | Primitivos representam conceitos com regras próprias.     | Criar um tipo que valide e ofereça operações adequadas.      |
| Long Parameter List | Muitas decisões independentes numa chamada.               | Separar operações ou agrupar dados que pertencem juntos.     |
| Refused Bequest     | Uma subclasse recusa operações prometidas pela base.      | Rever a hierarquia e usar composição.                        |

Feature Envy não se decide contando chamadas. Um serializador consulta muitos dados por função; isso não significa que a serialização deva entrar no modelo. Pergunta que módulo deve conhecer e proteger a regra.

Uma classe de dados pode ser adequada para transportar uma resposta ou representar um valor. Torna-se um problema quando regras do mesmo conceito ficam espalhadas pelos clientes. Uma operação `transferir` pode pertencer a uma conta; uma vista que consulta o saldo continua a ter uma responsabilidade distinta.

## Mudanças dispersas e dependências

**Divergent Change** ocorre quando mudanças de naturezas diferentes exigem editar a mesma classe. **Shotgun Surgery** ocorre quando uma mudança exige pequenas edições em muitas classes. O primeiro sugere separar responsabilidades; o segundo pode sugerir juntar uma regra que ficou dispersa.

Outros sinais ajudam a procurar a causa:

- `Temporary Field`: um campo só tem significado durante certas fases e exige verificações constantes.
- `Message Chains`: um cliente conhece um percurso como `arena.getHeroi().getPosicao().getX()`, ficando ligado à estrutura interna.
- `Middle Man`: uma classe só delega sem esconder uma decisão útil. Confirma antes se representa uma fronteira ou contrato necessário.
- `Speculative Generality`: abstrações e parâmetros para alternativas que não existem e aumentam o esforço de leitura.
- `Dead Code`: código sem uso que já não faz parte do contrato.

Um `switch` não é sempre um smell. Investiga quando a mesma decisão sobre tipo se repete em muitos módulos ou cresce sempre que acrescentas uma alternativa. Nesse caso, polimorfismo pode localizar cada comportamento.

## Como refatorar em segurança

1. Descreve o comportamento a preservar e corre os testes existentes.
2. Se faltam casos relevantes, acrescenta-os antes da transformação.
3. Faz uma transformação pequena, como extrair um método.
4. Compila e corre os testes. Inspeciona efeitos e erros que os testes não cobrem.
5. Repete até a responsabilidade ficar no local pretendido.

Ferramentas do IDE ajudam a atualizar referências, mas não conhecem todas as regras do domínio. Ao mover um método, confirma a ordem de chamadas, as exceções, o estado partilhado e a visibilidade.

## Exemplo: extrair a regra do preço

Neste exemplo próprio, cada unidade custa 200 cêntimos até cinco unidades; as seguintes custam 150. Aceitamos de zero a mil unidades. O preço é um inteiro em cêntimos, por isso não introduzimos arredondamentos de vírgula flutuante.

A primeira versão completa mistura a regra de preço com a impressão. Guarda-a como `Main.java` se quiseres compará-la localmente:

```java
public class Main {
    static void imprimir(int unidades) {
        if (unidades < 0 || unidades > 1000) {
            throw new IllegalArgumentException("quantidade invalida");
        }
        int preco;
        if (unidades <= 5) {
            preco = unidades * 200;
        } else {
            preco = 5 * 200 + (unidades - 5) * 150;
        }
        System.out.println(preco);
    }

    public static void main(String[] args) {
        imprimir(0);
        imprimir(3);
        imprimir(6);
    }
}
```

As saídas esperadas vêm da regra: zero custa `0`, três custam $3 \times 200 = 600$ e seis custam $5 \times 200 + 150 = 1150$.

Vamos extrair o cálculo e manter a validação dentro dele, para qualquer cliente obter a mesma regra. O método de impressão delega e continua a ter o mesmo efeito:

  }
/>

Voltamos a obter `0`, `600` e `1150`. Para zero a cinco unidades, `adicionais` é zero e `iniciais` é a quantidade. Acima de cinco, `iniciais` fica em cinco e `adicionais` é o excesso. Mantivemos a rejeição fora do intervalo e a mesma mensagem de erro.

Não alterámos a unidade monetária nem o desconto. Trocar a fórmula por uma que aplica 150 a todas as unidades acima de cinco produziria 900 para seis e seria uma mudança de regra, não uma refatoração.

## Outras transformações

**Extract Variable** dá um nome a uma expressão difícil. Preserva quantas vezes ela é calculada quando há efeitos ou estado que muda. Extrair uma chamada do interior de um ciclo para fora pode mudar o resultado.

**Guard Clauses** tratam casos que terminam cedo e deixam o percurso normal visível. Mantém a ordem de verificações se ela decide qual erro acontece primeiro.

**Move Method** aproxima uma regra dos dados que ela precisa. Começa por criar o método no destino e delegar do local antigo; depois atualiza clientes se isso fizer parte da mudança.

**Encapsulate Collection** impede clientes de contornar as operações do dono. Devolver uma cópia ou uma vista não modificável pode resolver problemas diferentes: uma vista não modificável ainda pode refletir mudanças na coleção original.

**Replace Conditional with Polymorphism** separa alternativas que variam. Só o faz quando as alternativas têm um contrato comum útil. O objetivo é reduzir a propagação de mudanças, não eliminar toda a condição do programa.
