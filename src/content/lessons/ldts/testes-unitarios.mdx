Com responsabilidades separadas pelos princípios SOLID, verifica agora automaticamente se o comportamento cumpre o contrato. A arena promete que células fora do intervalo são rejeitadas; o teste confirma essa promessa sem olhar para a condição escrita no código.

Imagina uma arena dividida em células, que são as casas numeradas onde o herói pode estar. A regra que diz em que células o herói pode entrar é o contrato que vamos testar: um teste unitário, que é uma verificação automática de um comportamento pequeno, compara o resultado com essa regra. O valor esperado vem da regra da arena, não de copiar a condição do código para o teste.

## Escolher o que verificar

Um teste unitário verifica uma unidade pequena através do seu comportamento observável. Pode abranger vários objetos simples que colaboram. Um teste de integração verifica a colaboração com uma fronteira real, como leitura de ficheiros. Um teste do sistema percorre a aplicação completa.

Deriva os casos de partições do contrato antes de escreveres código de teste. Para `contem` com largura 5, há três partições: dentro (`0` a `4`), abaixo (`< 0`) e acima (`>= 5`). Escolhe um representante de cada, mais as fronteiras exatas `0`, `4`, `-1` e `5`. O esperado vem da regra da arena, não da condição copiada do código: isto é teste black-box. Depois de leres a implementação, acrescenta casos white-box que a estrutura sugere, como largura zero no construtor.

Usa casos normais, limites e inválidos. Para largura 5, as células 0 e 4 estão dentro; -1 e 5 estão fora. Uma largura zero ou negativa não representa uma arena válida e deve ser rejeitada. Este último caso pertence ao contrato de construção, não à pergunta sobre uma célula válida.

Prepara o cenário, executa a ação e verifica o resultado, Arrange, Act, Assert. Um comportamento pode exigir várias asserções relacionadas. Por exemplo, mover deve produzir a posição certa **e** preservar a origem quando a operação promete imutabilidade.

## O primeiro teste com JUnit

Os exemplos desta página correm no projeto Gradle de [controlo de versões](/cadeiras/ldts/controlo-versoes/#dependências-com-gradle), com JUnit 5.13.4 e Mockito 4.11.0. São ficheiros locais completos. O editor Java do site não carrega essas bibliotecas.

Guarda `src/main/java/Limite.java`:

```java
public final class Limite {
    private final int largura;

    public Limite(int largura) {
        if (largura <= 0) throw new IllegalArgumentException("largura invalida");
        this.largura = largura;
    }

    public boolean contem(int x) {
        return x >= 0 && x < largura;
    }
}
```

Guarda `src/test/java/LimiteTest.java`:

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;
import static org.junit.jupiter.api.Assertions.*;

class LimiteTest {
    @ParameterizedTest
    @ValueSource(ints = {0, 2, 4})
    void aceitaCelulasInteriores(int x) {
        Limite limite = new Limite(5);
        boolean resultado = limite.contem(x);
        assertTrue(resultado);
    }

    @ParameterizedTest
    @ValueSource(ints = {-1, 5, 6})
    void rejeitaCelulasExteriores(int x) {
        assertFalse(new Limite(5).contem(x));
    }

    @Test
    void rejeitaLarguraZero() {
        assertThrows(IllegalArgumentException.class, () -> new Limite(0));
    }

    @Test
    void rejeitaLarguraNegativa() {
        assertThrows(IllegalArgumentException.class, () -> new Limite(-1));
    }
}
```

Corre `./gradlew test`. Os testes parametrizados fazem uma execução por argumento. A falha identifica o valor que não cumpriu o contrato. `assertThrows` executa a ação e confirma a exceção esperada, incluindo subclasses compatíveis.

Para valores de vírgula flutuante, uma tolerância adequada evita exigir igualdade bit a bit a um cálculo aproximado. Para objetos, `assertEquals` usa igualdade lógica; `assertSame` exige identidade.

## Independência dos testes

Um teste não deve depender da ordem, do estado deixado por outro teste ou de uma pausa arbitrária. JUnit Jupiter cria normalmente uma instância da classe por método de teste. `@BeforeEach` prepara estado antes de cada execução e `@AfterEach` liberta recursos depois.

`@BeforeAll` e `@AfterAll` tratam preparação e limpeza da classe inteira. Sob o ciclo de vida predefinido, estes métodos são estáticos. Evita partilhar estado mutável entre testes por conveniência.

Se o resultado depende de tempo, aleatoriedade ou I/O, injeta um colaborador que o teste controla. Um teste que só confirma que o método não lançou exceção pode ser útil para esse contrato, mas não verifica automaticamente o resultado calculado.

## Mocks e stubs com Mockito

Um **test double** substitui um colaborador. Um **stub** fornece respostas controladas. Um **fake** é uma implementação simplificada funcional, como armazenamento em memória. Um **mock** permite verificar chamadas esperadas. O mesmo objeto criado com Mockito pode servir de stub numa interação e de mock noutra; a distinção descreve o uso no teste.

Vamos testar um controlador que lê uma ação e envia a posição resultante à vista. A string `"direita"` move uma célula; outras ações mantêm a posição. Guarda `src/main/java/Controlador.java`:

```java
interface Entrada {
    String ler();
}

interface Vista {
    void mostrar(int x);
}

public final class Controlador {
    private final Entrada entrada;
    private final Vista vista;
    private int x;

    public Controlador(Entrada entrada, Vista vista, int x) {
        this.entrada = entrada;
        this.vista = vista;
        this.x = x;
    }

    public void passo() {
        if ("direita".equals(entrada.ler())) x++;
        vista.mostrar(x);
    }
}
```

Guarda `src/test/java/ControladorTest.java`:

```java
import org.junit.jupiter.api.Test;
import static org.mockito.Mockito.*;

class ControladorTest {
    @Test
    void mostraPosicaoDepoisDeMover() {
        Entrada entrada = mock(Entrada.class);
        when(entrada.ler()).thenReturn("direita");
        Vista vista = mock(Vista.class);
        Controlador controlador = new Controlador(entrada, vista, 2);

        controlador.passo();

        verify(vista).mostrar(3);
    }

    @Test
    void acaoDesconhecidaMantemPosicao() {
        Entrada entrada = mock(Entrada.class);
        when(entrada.ler()).thenReturn("pausa");
        Vista vista = mock(Vista.class);
        Controlador controlador = new Controlador(entrada, vista, 2);

        controlador.passo();

        verify(vista).mostrar(2);
    }
}
```

A entrada é um stub, porque fornece uma resposta fixa. A vista é um mock, porque verificamos o resultado enviado. `verify(vista).mostrar(3)` exige uma chamada correspondente; `times(2)` exigiria duas, e `never()` nenhuma. Por si só, essa verificação não proíbe todas as outras chamadas possíveis.

Verifica interações quando são parte do contrato, como enviar o resultado à vista. Não congeles cada chamada interna de um algoritmo: uma refatoração válida pode mudar essas chamadas e preservar o resultado. Para testar regras puras, prefere verificar o valor ou estado final.

Um **spy** envolve um objeto real e, por defeito, executa os seus métodos. `when(spy.metodo())` também pode executar o método durante a configuração. `doReturn(valor).when(spy).metodo()` evita essa execução quando precisas de substituir a resposta. Um spy não elimina a necessidade de perceber os efeitos do objeto real.

## Cobertura e mutation testing

Cobertura mede código executado pelos testes. Cobertura de linhas pergunta se uma linha foi executada; cobertura de branches distingue alternativas de uma condição. Nenhuma das duas prova que as asserções reconhecem um erro.

Imagina um teste que chama `contem(2)` e não verifica nada. Executa a linha da condição, mas aceita tanto `true` como `false`. A cobertura pode subir sem melhorar a proteção.

O curto-circuito mostra outro limite da cobertura de linhas. Em `x >= 0 && x < largura`, um teste só com `x = 2` executa a linha mas nunca avalia o segundo operando a falso por causa do primeiro. Precisas de casos que façam cada condição decidir o resultado: `-1` chumba na primeira, `5` passa a primeira e chumba na segunda.

**Mutation testing** altera o programa em pequenas operações, por exemplo trocar `<` por `<=`. Um mutante é **morto** quando os testes falham com essa mudança. Se todos passam, o mutante **sobrevive**. Um mutante sem cobertura nem sequer teve esse comportamento exercitado.

No nosso `Limite`, trocar `x < largura` por `x <= largura` faz `contem(5)` passar de falso a verdadeiro. O teste exterior com `5` mata esse mutante. Testar só `2` e `6` não distingue as duas condições.

Um mutante sobrevivente pode indicar uma falta nos testes, mas também pode ser **equivalente**, sem mudança observável dentro do domínio válido. Analisa o efeito antes de acrescentar uma asserção sem relação com o contrato.

O Gradle da primeira lição já tem JaCoCo. `./gradlew jacocoTestReport` gera cobertura. Para executar mutação neste projeto de treino, acrescenta `id 'info.solidsoft.pitest' version '1.19.0'` ao bloco `plugins` do mesmo `build.gradle`. No fim do ficheiro acrescenta:

```groovy
pitest {
    pitestVersion = '1.19.4'
    junit5PluginVersion = '1.2.3'
    targetClasses = ['Limite']
    targetTests = ['LimiteTest']
    threads = 1
    outputFormats = ['HTML', 'XML']
    timestampedReports = false
}
```

Corre `./gradlew pitest` e abre `build/reports/pitest/index.html`. As classes alvo são nomes completos: neste exemplo não há pacotes; num projeto com pacotes usa, por exemplo, `pt.equipa.Limite`. A integração JUnit é uma dependência da ferramenta de mutação, distinta das dependências dos testes. Estas versões formam um exemplo reproduzível; no projeto da cadeira preserva a configuração fornecida.

No relatório, escolhe a condição de `contem` e lê a mudança de cada mutante. Relaciona o mutante da fronteira superior com o teste de `x == 5`, em vez de concluir apenas que uma percentagem alta torna o programa correto.

## Trabalhar com um teste que falha

Num ciclo de desenvolvimento guiado por testes, começa com uma exigência pequena e observa a falha pelo motivo esperado. Implementa a mudança mínima que cumpre o contrato, observa o teste passar e só depois melhora a estrutura.

Um erro de importação não prova que o teste deteta o comportamento. E ver verde antes de existir uma implementação pode revelar que o teste não verifica o requisito.

Property-based testing, nos slides e no resumo estudantil, gera muitos valores aleatórios e verifica uma propriedade em vez de exemplos fixos. É um complemento útil para descobrir fronteiras esquecidas, não matéria obrigatória enumerada na ficha atual. Num defeito já existente, tenta reproduzi-lo através da interface pública mais próxima do utilizador e conserva esse caso como regressão.
