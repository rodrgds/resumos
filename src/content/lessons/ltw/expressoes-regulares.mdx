Depois de validar dados no servidor e de os mostrar como texto na página, esta página responde como descrever formatos de texto para validar e pesquisar.

Uma expressão regular descreve um padrão de texto: procura uma parte, extrai grupos, substitui correspondências ou valida um formato completo. Primeiro define a tarefa, porque encontrar `LTW-042` dentro de uma frase é diferente de exigir que toda a entrada seja exatamente esse código.

## Peças e precedência

| Padrão           | Significado habitual                                                  |
| ---------------- | --------------------------------------------------------------------- |
| `abc`            | Os caracteres literais nessa ordem                                    |
| `[abc]`, `[0-9]` | Um caráter do conjunto ou intervalo                                   |
| `[^0-9]`         | Um caráter fora do conjunto                                           |
| `.`              | Um caráter, habitualmente excluindo mudanças de linha                 |
| `\d`, `\w`, `\s` | Classes abreviadas de dígito, palavra e espaço                        |
| `^`, `$`         | Posições de início e fim, com pormenores dependentes do motor e flags |
| `\b`             | Fronteira de palavra, sem consumir caracteres                         |
| `a?`, `a*`, `a+` | Zero ou um, zero ou mais, um ou mais `a`                              |
| `a{3}`, `a{2,4}` | Exatamente três, ou entre dois e quatro `a`                           |
| `a\|b`           | Alternativa, quando a barra não está escapada no padrão               |
| `(ab)`           | Grupo que captura                                                     |
| `(?:ab)`         | Grupo sem captura                                                     |

As abreviaturas e o tratamento de Unicode dependem do motor; `[A-Za-z]` não representa todas as letras portuguesas.

Quantificadores aplicam-se à peça anterior. `ab+` exige um `a` e um ou mais `b`; `(ab)+` repete o par. Alternância tem baixa precedência: `^LTW|BD$` aceita entradas que comecem por LTW ou terminem por BD. Para prender ambas as alternativas às pontas, usa `^(?:LTW|BD)$`.

## Construir e testar um formato

Queremos aceitar `LTW-042` ou `BD-007`, com três dígitos no fim, e capturar esses dígitos. As peças são início, grupo de prefixos, hífen, grupo de três dígitos e fim:

```js
/^(?:LTW|BD)-([0-9]{3})$/;
```

O primeiro grupo só organiza alternativas. O segundo captura e, por ser o primeiro grupo capturante, fica em índice 1. O índice 0 é sempre a correspondência completa.

Dois dígitos falham a repetição e o `x` inicial falha a âncora, ou seja obténs `042`, `007` e depois dois inválidos. Isto verifica o formato, não prova que o código exista no catálogo. Para dados externos, define também limites de comprimento e regras semânticas.

## Guloso, preguiçoso e primeiro resultado

No texto `A <b>rede</b> e <i>web</i>.`, `<.*>` escolhe `<b>rede</b> e <i>web</i>`. O `*` guloso tenta consumir tanto quanto possível e depois recua até conseguir o `>` final. `<.*?>` escolhe primeiro `<b>`: o quantificador preguiçoso tenta o mínimo e expande se o restante padrão não puder casar.

`<[^>]*>` também pára antes do primeiro `>`, pela classe negada. Estes padrões são úteis para observar quantificadores, mas não são parsers seguros de HTML. Aspas, comentários e estrutura aninhada exigem um parser.

Ao pedir a primeira correspondência, o motor começa na primeira posição em que o padrão pode casar. "Guloso" não significa escolher uma posição inicial mais à direita para obter um resultado maior. Flags como `g` em JavaScript pedem correspondências globais; `i` ignora diferenças de maiúsculas conforme as regras do motor; `m` altera as âncoras para linhas; `s` permite que `.` inclua quebras de linha.

## Capturas e referências

Uma referência `\1` exige o mesmo texto que o primeiro grupo capturou:

```js
/\b(\w+)\s+\1\b/.exec('livro livro novo')[0]; // livro livro
```

Não exige "outra palavra qualquer"; exige `livro` de novo. Numa substituição JavaScript, `$1` refere a primeira captura:

```js
'2026-10-02'.replace(/^(\d{4})-(\d{2})-(\d{2})$/, '$3/$2/$1'); // 02/10/2026
```

O padrão verifica a forma numérica, não que o dia exista no calendário. `2026-02-31` também tem a forma certa. Valida a data com regras de calendário quando esse é o objetivo.

## Lookaround e backtracking

Lookaround verifica contexto sem o incluir na correspondência. `livro(?=s)` escolhe `livro` apenas quando vem seguido de `s`; `livro(?!s)` exige que não venha `s`. `(?<=EUR )[0-9]+` encontra dígitos precedidos de `EUR `; o prefixo não faz parte do resultado. Lookbehind e algumas regras têm limites de compatibilidade entre motores.

Backtracking é a tentativa de alternativas após uma escolha não permitir acabar o padrão. Em `a.*b`, o motor pode consumir até ao fim e recuar à procura de um `b` final. Padrões com repetições ambíguas, como `(a+)+$`, podem exigir muitas tentativas numa entrada quase válida. Limita a entrada e evita estruturas com custo explosivo em dados controlados pelo cliente.

Expressões regulares clássicas correspondem a linguagens reconhecíveis por autómatos finitos. Motores práticos incluem extensões, como referências a capturas, que ultrapassam esse modelo. Não uses a palavra "regular" para assumir que qualquer padrão de um motor moderno tem custo simples ou expressividade idêntica.

## JavaScript, PHP e HTML

Em JavaScript, `test` devolve booleano e `exec`/`match` permitem obter capturas. `match` sem `g` devolve a primeira correspondência e as capturas; com `g`, devolve as correspondências completas, sem as capturas de cada uma. Para obter capturas de todas, usa `matchAll` com `g`.

```js
const texto = 'LTW-042 e BD-007';
for (const resultado of texto.matchAll(/(?:LTW|BD)-([0-9]{3})/g)) {
  console.log(resultado[1]); // 042, depois 007
}
```

Um objeto regex com flag `g` conserva `lastIndex` entre chamadas de `test`: `/a/g` sobre `'a'` dá `true` na primeira chamada e `false` na segunda com o mesmo objeto. Evita `g` numa validação repetida sem controlar esse estado.

Em PHP, os padrões PCRE precisam de delimitadores. `preg_match` devolve 1 para correspondência, 0 para ausência e `false` para erro. Para exigir o texto completo de forma estrita em PCRE, `\A` e `\z` fixam as pontas sem o caso especial de uma quebra de linha final de `$`:

```php
<?php
$valido = preg_match('/\A(?:LTW|BD)-[0-9]{3}\z/', $codigo) === 1;
```

No HTML, `pattern` recebe o padrão sem `/.../` e aplica-o ao valor completo nos tipos suportados. `pattern="(?:LTW|BD)-[0-9]{3}"` não exige sozinho uma entrada não vazia; acrescenta `required` se for obrigatória. A sintaxe atual usa regras Unicode próprias, por isso confirma compatibilidade ao usar classes avançadas. O servidor tem de validar novamente, independentemente do formulário.
