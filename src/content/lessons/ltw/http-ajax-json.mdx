HTTP é um protocolo de aplicação baseado em pedidos e respostas. O cliente pede um recurso; o servidor responde com estado, cabeçalhos e, quando existe, um corpo. Cada pedido é independente ao nível do protocolo. Cookies e sessões acrescentam mecanismos para ligar vários pedidos ao mesmo utilizador.

## URL e origem

Em `https://biblioteca.example:443/livros/12?q=redes#reserva`, temos esquema `https`, host `biblioteca.example`, porta 443, caminho `/livros/12`, query `q=redes` e fragmento `reserva`. A porta habitual de HTTPS é 443 e a de HTTP é 80. O fragmento fica no navegador e não integra o alvo enviado ao servidor.

Uma origem combina esquema, host e porta. `https://biblioteca.example` e `http://biblioteca.example` são origens distintas. Duas páginas com caminhos diferentes, mas o mesmo esquema, host e porta, têm a mesma origem. URL localiza um recurso; URI é o conceito mais geral de identificação, que também inclui identificadores sem localização de acesso.

## Ler mensagens

Esta representação textual usa HTTP/1.1. Versões mais recentes mudam a codificação no transporte, conservando conceitos como método, estado e campos de cabeçalho.

```http
GET /livros?q=redes HTTP/1.1
Host: biblioteca.example
Accept: application/json
Cookie: PHPSESSID=exemplo

```

A primeira linha identifica método, alvo e versão. `Host` identifica o servidor pedido; `Accept` indica formatos que o cliente aceita. A linha vazia separa cabeçalhos do corpo, que aqui não existe.

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 20
Cache-Control: no-store

[{"titulo":"Redes"}]
```

`Content-Type` descreve o corpo enviado, não os formatos desejados. `Accept` é uma preferência do cliente; o servidor pode responder com um formato compatível ou recusar quando não consegue satisfazê-la. `Content-Length` conta os bytes do corpo, não letras nem linhas. Na rede, HTTP/1.1 separa linhas com CRLF. Um pedido com corpo precisa de enquadramento, como Content-Length ou Transfer-Encoding, para o servidor saber onde termina.

Um formulário normal pode produzir:

```http
POST /reservas HTTP/1.1
Host: biblioteca.example
Content-Type: application/x-www-form-urlencoded
Content-Length: 21

livro=12&quantidade=2
```

JSON usa outra codificação, como `{"livro":12,"quantidade":2}`, e `Content-Type: application/json`. Em PHP, não confundas essa mensagem com `$_POST`: lê o corpo e descodifica JSON explicitamente. Uploads costumam usar `multipart/form-data` e limites que separam as partes.

## Métodos, segurança e idempotência

Um método **seguro** pede leitura, sem solicitar uma alteração de estado da aplicação. **Idempotente** significa que repetir o mesmo pedido tem o mesmo efeito pretendido que o fazer uma vez. A resposta pode variar e pode haver efeitos acessórios, como registos de acesso.

| Método    | Uso habitual                              | Seguro | Idempotente         |
| --------- | ----------------------------------------- | ------ | ------------------- |
| `GET`     | Obter uma representação                   | Sim    | Sim                 |
| `HEAD`    | Obter cabeçalhos como em GET, sem corpo   | Sim    | Sim                 |
| `POST`    | Submeter dados para processamento         | Não    | Não, em geral       |
| `PUT`     | Criar ou substituir no endereço escolhido | Não    | Sim                 |
| `DELETE`  | Remover a associação do recurso           | Não    | Sim                 |
| `PATCH`   | Aplicar alterações parciais               | Não    | Depende da operação |
| `OPTIONS` | Consultar opções de comunicação           | Sim    | Sim                 |

Dois `DELETE /reservas/7` podem responder primeiro 204 e depois 404, conservando a idempotência da remoção. Dois `POST /reservas` podem criar duas reservas. Uma API pode implementar chaves de idempotência para uma operação POST, mas isso é um contrato adicional da aplicação. `GET /apagar?id=7` viola a semântica segura, apesar do nome do método.

REST usa recursos, representações e uma interface uniforme. `/livros/12` identifica um recurso; o método indica a operação. JSON não torna uma API automaticamente REST. Stateless significa que cada pedido inclui a informação necessária para o interpretar; não proíbe guardar livros ou reservas na base de dados.

## Estados, cookies e cache

| Estado | Interpretação                                                    |
| ------ | ---------------------------------------------------------------- |
| 200    | Pedido bem-sucedido, com representação quando aplicável          |
| 201    | Recurso criado, frequentemente identificado por `Location`       |
| 204    | Sucesso sem corpo                                                |
| 303    | Pedir ao cliente que consulte outro destino, normalmente por GET |
| 304    | A representação em cache continua válida, sem novo corpo         |
| 400    | Pedido inválido                                                  |
| 401    | Faltam credenciais válidas de autenticação                       |
| 403    | Operação recusada                                                |
| 404    | Recurso não encontrado, ou existência não divulgada              |
| 405    | Método não permitido; `Allow` indica os admitidos                |
| 500    | Erro interno do servidor                                         |

`Set-Cookie` vai na resposta para pedir que o navegador guarde um cookie; `Cookie` vai em pedidos posteriores conforme domínio, caminho, segurança e política aplicáveis. Um cookie é entrada controlada pelo cliente, não prova independente de permissão. `HttpOnly` impede leitura por JavaScript; não impede que o navegador envie o cookie em pedidos.

`Cache-Control: no-store` pede que não guardem a resposta. `no-cache` admite guardá-la, mas exige revalidação antes de a reutilizar. `ETag` identifica uma versão; o cliente pode enviar `If-None-Match`, e o servidor responder 304 se ela não mudou. Não guardes respostas privadas em caches partilhadas por engano.

## Promessas e ordem de execução

Uma Promise representa um resultado futuro, que pode cumprir-se ou rejeitar-se. `then` regista o que fazer após cumprir; `catch` trata rejeições; `finally` permite finalizar. `async` faz a função devolver uma promessa; `await` suspende essa função até à conclusão, sem bloquear todo o navegador.

```js
console.log('A');
Promise.resolve().then(() => console.log('B'));
console.log('C');
```

A saída é `A`, `C`, `B`. O código corrente acaba antes do callback da promessa. Microtarefas de promessas pendentes são processadas antes da tarefa seguinte, como um callback de temporizador que entretanto esteja pronto. Um ciclo pesado continua a bloquear a execução dos callbacks; `async` não transforma cálculo síncrono numa thread.

`Promise.all` reúne resultados e rejeita se uma das promessas rejeitar. Só inicia operações concorrentes se elas forem efetivamente iniciadas antes de esperar por cada uma. Erros lançados dentro de `async` tornam-se rejeições; envolve `await` num `try/catch` para os tratar nesse percurso.

## JSON e fetch

JSON representa objetos, arrays, strings, números, booleanos e `null`. Na troca entre sistemas, usa UTF-8; o media type `application/json` não define um parâmetro charset. Nomes de propriedades e strings usam aspas duplas; não admite comentários, funções nem vírgulas finais. `JSON.stringify` transforma valores em texto, e `JSON.parse` faz o inverso. Não uses `eval` para ler JSON.

Esta função é um excerto para uma página com `ul#resultados`:

```js
async function pesquisar(termo) {
  const parametros = new URLSearchParams({ q: termo });
  const resposta = await fetch('/api/livros?' + parametros);
  if (!resposta.ok) throw new Error('HTTP ' + resposta.status);
  const livros = await resposta.json();
  const lista = document.querySelector('#resultados');
  lista.replaceChildren();
  for (const livro of livros) {
    const item = document.createElement('li');
    item.textContent = livro.titulo;
    lista.append(item);
  }
}
```

`fetch` resolve a promessa mesmo para muitos erros HTTP, incluindo 404 e 500. É o teste a `ok`, que corresponde a estados 200 a 299, que os transforma em erro neste programa. Erros de rede podem rejeitar antes de existir resposta. `json()` lê e descodifica o corpo e também é assíncrono. O cabeçalho do formato não substitui a validação do conteúdo recebido.

Se duas pesquisas estão pendentes, a mais antiga pode acabar depois e substituir a mais recente. Usa um contador de pedidos para ignorar resultados antigos ou cancela com `AbortController`. Encodar parâmetros com `URLSearchParams` preserva espaços, `&`, `+` e acentos como dados, em vez de alterar a estrutura do endereço.

:::details[ajax.js]

```js
let pedido = 0;
const estado = document.querySelector('#estado');
const lista = document.querySelector('#resultados');
document
  .querySelector('#pesquisa')
  .addEventListener('submit', async (evento) => {
    evento.preventDefault();
    const atual = ++pedido;
    estado.textContent = 'A pesquisar…';
    const parametros = new URLSearchParams({
      q: document.querySelector('#q').value,
    });
    try {
      const resposta = await fetch('api-livros.php?' + parametros);
      if (!resposta.ok) throw new Error('HTTP ' + resposta.status);
      const livros = await resposta.json();
      if (atual !== pedido) return;
      lista.replaceChildren();
      for (const livro of livros) {
        const item = document.createElement('li');
        item.textContent = livro.titulo;
        lista.append(item);
      }
      estado.textContent = `Resultados: ${livros.length}`;
    } catch (erro) {
      if (atual !== pedido) return;
      lista.replaceChildren();
      estado.textContent = 'Pesquisa indisponível.';
    }
  });
```

:::details[api-livros.php]

```php
<?php
header('Content-Type: application/json');
if ($_SERVER['REQUEST_METHOD'] !== 'GET') {
    header('Allow: GET');
    http_response_code(405);
    echo json_encode(['erro' => 'Método não permitido']);
    exit;
}
$termo = $_GET['q'] ?? '';
if (!is_string($termo) || strlen($termo) > 100) {
    http_response_code(400);
    echo json_encode(['erro' => 'Pesquisa inválida']);
    exit;
}
$catalogo = [['titulo' => 'Redes'], ['titulo' => 'Algoritmos'], ['titulo' => 'SQL']];
$resultados = array_values(array_filter($catalogo, function ($livro) use ($termo) {
    return stripos($livro['titulo'], $termo) !== false;
}));
echo json_encode($resultados, JSON_UNESCAPED_UNICODE);
```

:::

Pesquisar `red` mostra `Redes` e `Resultados: 1`; vazio mostra os três livros. O endpoint responde 405 a POST e 400 a `q[]=red`. `array_values` repõe índices consecutivos após filtrar para `json_encode` emitir um array JSON, não um objeto com chaves numéricas descontínuas.

`XMLHttpRequest` faz o mesmo tipo de comunicação por callbacks: `open` configura, `setRequestHeader` define campos depois de abrir, `send` envia, e `load` indica chegada da resposta. Verifica `status` antes de usar `responseText`. No callback normal, `this` pode ser o objeto do pedido; numa arrow function, essa associação não segue a mesma regra.

Para enviar um formulário por Ajax, indica método e corpo. Este excerto pressupõe uma ação `/actions/reservar.php` que devolve JSON e verifica sessão, token CSRF e dados:

```js
async function reservar(livro, quantidade, csrf) {
  const resposta = await fetch('/actions/reservar.php', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({ livro, quantidade, csrf }),
  });
  if (!resposta.ok) throw new Error('HTTP ' + resposta.status);
  return resposta.json();
}
```

O corpo codificado chega a `$_POST`. A função devolve uma promessa, que o chamador deve esperar e tratar com `try/catch` ou `.catch(...)`. Se o endpoint redirecionar para HTML em vez de devolver JSON, `json()` falha mesmo que o estado final seja 200. O cliente e o servidor têm de concordar no formato da resposta.

## SOP e CORS

A same-origin policy restringe o acesso de scripts a dados de outras origens. Não impede todos os pedidos entre sítios: por exemplo, formulários e recursos embebidos podem causar pedidos sem permitir ler a resposta. Por isso SOP e CORS não substituem proteção contra CSRF.

CORS permite ao servidor declarar quais as origens autorizadas a ler a resposta. Um pedido que exige preflight envia primeiro `OPTIONS`, com `Origin`, método e cabeçalhos pretendidos. Não há preflight em todos os pedidos. Um `GET` sem cabeçalhos adicionais pode ser enviado diretamente; um `POST` com `Content-Type: application/json` exige normalmente preflight. O servidor responde com os campos de autorização adequados. Por exemplo, para uma página em `https://a.example` enviar JSON a `https://api.example`:

```http
OPTIONS /reservas HTTP/1.1
Host: api.example
Origin: https://a.example
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type

```

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://a.example
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: Content-Type
Vary: Origin

```

Se a resposta autorizar o pedido, o navegador envia o POST. A resposta ao POST também precisa de `Access-Control-Allow-Origin`, para ser legível pelo script. `Vary: Origin` informa caches de que a resposta pode depender da origem. A aplicação continua a precisar de autenticar e autorizar o pedido real.

Para credenciais entre origens, o cliente usa `credentials: 'include'` e o servidor precisa de permitir credenciais e a origem concreta, não `Access-Control-Allow-Origin: *`. As regras dos cookies ainda podem impedir o envio. `mode: 'no-cors'` não desbloqueia leitura de JSON: produz uma resposta opaca.

## MPA, SPA e PWA

Uma MPA navega entre documentos produzidos pelo servidor. Uma SPA carrega um documento inicial e atualiza a interface e a navegação sobretudo no cliente. SPA não significa ausência de servidor nem dispensa URLs, histórico, estados de carregamento e controlo de acesso. Uma MPA também pode usar Ajax em algumas ações.

Uma PWA pode acrescentar manifest, instalação e service worker para cache e funcionamento offline. Esses mecanismos não são sinónimos de SPA. `localStorage` guarda pares de strings por origem e normalmente conserva-os entre sessões; `sessionStorage` separa-os também por separador e sessão da página. Não são cookies, não seguem automaticamente em pedidos e não devem guardar segredos acessíveis a qualquer script dessa origem. A History API pode atualizar o URL e o histórico de uma SPA sem carregar outro documento; o programa precisa de restaurar o conteúdo correto ao voltar atrás. APIs como geolocalização e notificações têm permissões, contextos e limites próprios. Frameworks organizam código e componentes, mas não alteram as regras de HTTP, DOM ou segurança que acabámos de estudar.

SSR constrói a representação HTML no servidor; CSR constrói-a sobretudo no cliente a partir de dados. Esta distinção é independente de MPA/SPA. Um Worker pode executar trabalho sem acesso direto ao DOM e comunica por mensagens. Um service worker tem um ciclo de instalação e ativação e pode intercetar pedidos das páginas que controla; não é uma função que corre dentro de cada evento do DOM.
