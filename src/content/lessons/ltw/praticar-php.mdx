<Exercise
  revision={1}
  id="ltw-nota-zero"
  title="Distinguir zero de ausência"
  explanation="/cadeiras/ltw/php-dinamicas-bd/#valores-strings-e-arrays"
  answer={{"kind": "self", "checklist": ["Conservei 0 como valor válido.", "Usei uma única chamada e comparação estrita."]}}
>

Uma função obterNota devolve um inteiro de 0 a 20 ou <code>{"null"}</code> quando não existe nota. Porque falha `if (obterNota($id))`? Escreve uma condição correta chamando a função uma só vez.

<div slot="hint">

Zero é falso numa condição booleana.

</div>
<div slot="solution">

Usa `$nota = obterNota($id); if ($nota !== null) { /* existe */ }`. A nota zero é um resultado válido e passa esta condição. A condição original confundia um valor existente igual a zero com ausência.

</div>
<div slot="mistakes">

Não usar empty, porque também rejeita 0, nem assumir que uma nota em falta é uma string vazia.

</div>
</Exercise>

<Exercise
  revision={1}
  id="ltw-parametro-array"
  title="Validar a fronteira HTTP"
  explanation="/cadeiras/ltw/php-dinamicas-bd/#receber-um-pedido"
  answer={{"kind": "self", "checklist": ["Rejeitei ausência, lixo e array.", "Passei um inteiro validado à função."]}}
>

Uma ação aceita quantidade inteira entre 1 e 5. Analisa as entradas ausente, <code>{"quantidade=3"}</code>, <code>{"quantidade=3x"}</code> e <code>{"quantidade[]=3"}</code>. Descreve a validação antes de chamar <code>{"reservar(int $q)"}</code>.

<div slot="hint">

Uma entrada HTTP não é necessariamente uma string.

</div>
<div slot="hint-more">

Confirma <code>{"is_string"}</code> antes de <code>{"filter_var"}</code> e usa <code>{"min_range"}</code>/<code>{"max_range"}</code>.

</div>
<div slot="solution">

A ausência deve falhar porque não há valor. `3` deve produzir o inteiro 3. `3x` deve falhar porque contém lixo, mesmo que `intval` extraísse 3. `quantidade[]=3` chega como array e deve falhar no teste `is_string` antes da validação escalar. Obtém `$_POST['quantidade'] ?? null`, exige string e `FILTER_VALIDATE_INT` entre 1 e 5. Só depois passa o inteiro à função.

</div>
<div slot="mistakes">

<code>{"intval('3x')"}</code> devolveria 3 e perderia o lixo da entrada, por
isso converter não substitui validar.
<code>{'strict_types'}</code> na função não substitui validação HTTP.

</div>
</Exercise>

<Exercise
  revision={1}
  id="ltw-consulta-limite"
  title="Escolher SQL e ordenação"
  explanation="/cadeiras/ltw/php-dinamicas-bd/#sqlite-e-consultas-preparadas"
  answer={{"kind": "self", "checklist": ["Preparei o limite como valor.", "Escolhi a coluna numa lista fechada."]}}
>

Escreve uma consulta PDO para listar titulo e preco de livros com preco menor ou igual a um limite recebido. A ordenação recebida só pode ser titulo ou preco. Explica por que não usar ORDER BY :coluna.

<div slot="hint">

Valores usam marcadores; nomes de colunas precisam de uma lista fixa.

</div>
<div slot="hint-more">

Escolhe um dos dois textos conhecidos e prepara a condição de preço.

</div>
<div slot="solution">

Com `$db` conectado e `$limite` já validado, a escolha de coluna pode ser feita assim:

```php
$colunas = ['titulo' => 'titulo', 'preco' => 'preco'];
$ordem = $_GET['ordem'] ?? null;
if (!is_string($ordem) || !isset($colunas[$ordem])) {
    throw new InvalidArgumentException('Ordenação inválida');
}
$sql = 'SELECT titulo, preco FROM livro WHERE preco <= :limite ORDER BY '
    . $colunas[$ordem];
$stmt = $db->prepare($sql);
$stmt->execute(['limite' => $limite]);
$livros = $stmt->fetchAll(PDO::FETCH_ASSOC);
```

A concatenação usa apenas um dos dois nomes fixos. `:limite` representa um valor; `ORDER BY :coluna` não transforma o valor recebido num nome de coluna. Numa ação real, trata a exceção como erro de entrada, sem expor detalhes internos.

</div>
<div slot="mistakes">

Preparar não torna seguro concatenar uma coluna arbitrária enviada pelo cliente.

</div>
</Exercise>

<Exercise
  revision={1}
  id="ltw-acao-reserva"
  title="Separar alteração e confirmação"
  explanation="/cadeiras/ltw/php-dinamicas-bd/#alterar-dados-de-forma-consistente"
  answer={{"kind": "self", "checklist": ["Expliquei rollback da primeira alteração.", "Usei commit no sucesso e 303 com exit."]}}
>

A reserva reduz stock e insere uma linha. A inserção falha após o <code>{"UPDATE"}</code>. O que tem de acontecer à primeira alteração? Após sucesso, como evitas repetir o <code>{"POST"}</code> ao atualizar a confirmação?

<div slot="hint">

As duas alterações pertencem à mesma transação.

</div>
<div slot="hint-more">

O cliente deve seguir um 303 para uma página de leitura.

</div>
<div slot="solution">

Se a inserção falha, faz rollback da transação, recuperando o stock. Só faz commit depois dos dois passos. No sucesso, envia Location para um destino fixo com estado 303 e termina com exit. O cliente lê a confirmação por <code>{"GET"}</code>, de modo que atualizar essa página não repete o <code>{"POST"}</code>.

</div>
<div slot="mistakes">

Location sozinho não termina o PHP. A transação não substitui validar stock no <code>{"UPDATE"}</code> nem confirmar a autorização.

</div>
</Exercise>

<Exercise
  id="ltw-chaves-json"
  revision={1}
  title="Conservar chaves e emitir uma lista"
  explanation="/cadeiras/ltw/php-dinamicas-bd/#valores-strings-e-arrays"
  answer={{kind: 'self', checklist: ["Distingui posição 0 de false.", "Expliquei a chave 1 preservada e usei array_values."]}}
>

Prevê as duas saídas e corrige a segunda para que uma API envie uma lista JSON com apenas SQL.

```php
<?php
$livros = ['Redes', 'SQL'];
$filtrados = array_filter($livros, fn($titulo) => $titulo === 'SQL');
var_dump(strpos('SQL avançado', 'SQL'));
echo json_encode($filtrados);
```

<div slot="hint">

<code>{'array_filter'}</code> conserva as chaves da entrada.

</div>
<div slot="solution">

A primeira saída é `int(0)`, uma correspondência no início, não ausência. A segunda é `{"1":"SQL"}`, porque a chave 0 foi removida e a chave 1 foi conservada. Usa `echo json_encode(array_values($filtrados));` para obter `["SQL"]`. Se usasses o resultado de strpos como booleano, rejeitarias esta correspondência válida.

</div>
<div slot="mistakes">

Não presumir que filtrar renumera a lista, nem testar a posição com if sem comparação estrita com false.

</div>
</Exercise>

<Exercise
  id="ltw-global-captura-pedido"
  revision={1}
  title="Distinguir captura de estado global"
  explanation="/cadeiras/ltw/php-dinamicas-bd/#âmbito-global-e-captura-de-uma-variável"
  answer={{ kind: 'self', checklist: ['Obtive 0 3 3 e distingui as duas capturas.', 'Identifiquei global como acesso à variável exterior.', 'Expliquei por que um novo pedido não recupera este total sem persistência.'] }}
>
  <div>

Prevê os três valores escritos. O ficheiro é executado desde o início em cada pedido e não usa sessão, ficheiro nem base de dados. Um novo pedido começa no total 3?

```php
<?php
$total = 0;
function somar(int $valor): void {
    global $total;
    $total += $valor;
}
$antes = function () use ($total) { return $total; };
$agora = function () use (&$total) { return $total; };
somar(3);
echo $antes(), ' ', $agora(), ' ', $total;
```

Refatora o cálculo para uma função que receba total e valor e devolva a soma, sem alterar uma global. Indica a atribuição que atualiza o total no chamador.

  </div>
  <div slot="solution">

A saída é `0 3 3`. `somar` liga o nome local à global e deixa-a em 3. A closure `antes` conservou 0 na criação; `agora` refere a variável agora igual a 3. A terceira leitura é da mesma global.

Um novo pedido volta a executar `$total = 0` e não recupera o valor anterior. A global é estado do programa desse pedido, não estado persistente do utilizador.

```php
function somado(int $total, int $valor): int {
    return $total + $valor;
}
$total = somado($total, 3);
```

A função só calcula. A atribuição no chamador torna explícito que valor é atualizado. Nem uma variável com o mesmo nome numa função nem uma captura por valor criam acesso automático à global.

  </div>
</Exercise>

<Exercise
  id="ltw-foreach-vinculo"
  revision={1}
  title="Um percurso de leitura que altera a última posição"
  explanation="/cadeiras/ltw/php-dinamicas-bd/#terminar-uma-referência-de-foreach"
  answer={{ kind: 'self', checklist: ['Obtive [4,8,8] e segui a referência à última posição.', 'Coloquei unset depois do ciclo por referência.', 'Conservei [4,8,12] na leitura corrigida.'] }}
>
  <div>

Prevê o array escrito e explica por que o segundo ciclo o altera, apesar de não ter `&` na sua declaração. Corrige o programa para conservar todos os valores duplicados pelo primeiro ciclo.

```php
<?php
$valores = [2, 4, 6];
foreach ($valores as &$valor) {
    $valor *= 2;
}
foreach ($valores as $valor) {
    // Apenas pretendemos percorrer os valores.
}
echo json_encode($valores);
```

  </div>
  <div slot="hint">

O segundo ciclo também atribui valores ao nome que recebe cada elemento.

  </div>
  <div slot="solution">

Depois do primeiro ciclo, o array é `[4,8,12]`, e `$valor` continua a referir a sua última posição. No segundo, atribuir 4 a esse nome deixa o último elemento em 4; atribuir 8 deixa-o em 8. A última iteração lê essa posição já alterada, que vale 8. A saída é `[4,8,8]`.

Coloca `unset($valor);` imediatamente depois do primeiro ciclo. O segundo passa então a usar uma variável independente e conserva `[4,8,12]`. Usar outro nome no segundo ciclo evitaria esta alteração concreta, mas deixaria a referência pendente para o código posterior. Não apagues `$valores[2]`: o objetivo é terminar o vínculo, não perder uma nota.

  </div>
</Exercise>
