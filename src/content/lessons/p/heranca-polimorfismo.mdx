Um `Produto` de 100 euros devolve `100` em `total()`. Uma `Promocao` com desconto de 25% devolve `75` pela mesma operação. A classe base `Produto` define a interface comum; a derivada `Promocao` acrescenta o desconto e outra implementação do cálculo.

## Herdar de uma classe base

`class Promocao : public Produto` estabelece herança pública. Um objeto `Promocao` contém um subobjeto `Produto` e os membros próprios. Uma referência ou um apontador para `Promocao` pode ser convertido para o acesso correspondente à base.

A herança pública deve permitir usar a derivada onde o contrato da base é esperado. Se a derivada recusa operações válidas para a base ou muda o seu significado, a relação precisa de ser revista. Ter código em comum não é razão suficiente para herdar. Para representar "tem um", usa composição, um membro de outro tipo.

Neste exemplo, o preço é não negativo e o desconto está entre `0` e `1`. O desconto `0.25` reduz `100` para `100 * (1 - 0.25) = 75`. Uma versão com dados externos teria de validar essas condições.

`preco_` continua privado. A derivada consulta-o através do método protegido `preco()`. Membros privados da base não são acessíveis diretamente à derivada. Na herança pública, os membros públicos da base continuam públicos e os protegidos continuam protegidos. Herança privada ou protegida altera a acessibilidade e não oferece a mesma substituição pública.

## Funções virtuais e override

O **tipo estático** é o tipo conhecido a partir da declaração. `referencia` tem tipo estático `const Produto&`. O **tipo dinâmico** corresponde ao objeto concreto referido, aqui `Promocao`.

Numa chamada virtual através de uma referência ou apontador para a base, a implementação é escolhida pelo tipo dinâmico. Por isso, `referencia.total()` chama `Promocao::total()` e produz `75`. Sem `virtual`, uma chamada pela interface da base escolheria a função da base pelo tipo estático.

`override` pede ao compilador que confirme que a função substitui uma virtual da base. O `const` faz parte da assinatura. Sem `override`, este erro compila e cria outra função:

```cpp
// Código incorreto para análise. Falta o const da base.
double total() override { return preco() * (1.0 - desconto_); }
```

O compilador rejeita: a assinatura sem `const` não substitui `total() const`. Sem a palavra `override`, o erro passaria despercebido e a chamada pela base usaria sempre o preço sem desconto. Sobrecarga escolhe entre assinaturas; substituição virtual escolhe a implementação de uma assinatura herdada. São mecanismos diferentes.

Uma chamada explicitamente qualificada, como `promocao.Produto::total()`, escolhe a implementação da base. Durante construção e destruição, as chamadas virtuais não chegam a partes derivadas ainda não construídas ou já destruídas. Evita depender desse tipo de despacho para inicializar a derivada.

## A armadilha do slicing

`Produto copia = promocao` constrói um novo `Produto` só com a parte base, por isso `copia` tem tipo dinâmico `Produto` e usa a implementação da base.

Passar uma derivada por valor a um parâmetro de tipo base também corta a parte derivada. Um `vector<Produto>` guarda objetos base, não preserva objetos derivados completos. Para observar objetos polimórficos usa referências ou apontadores; para os possuir usa donos polimórficos, como `vector<unique_ptr<Forma>>` da secção seguinte.

## Classes abstratas

Uma função `virtual double area() const = 0;` é virtual pura. A classe é **abstrata** e não permite construir um objeto diretamente. Define uma operação que as classes concretas devem completar.

Programa completo para compilar localmente:

```cpp
#include <iostream>
#include <memory>
#include <stdexcept>
#include <vector>

class Forma {
public:
    virtual ~Forma() = default;
    virtual double area() const = 0;
};

class Retangulo : public Forma {
public:
    Retangulo(double largura, double altura) : largura_(largura), altura_(altura) {
        if (!(largura > 0 && largura <= 1000000 && altura > 0 && altura <= 1000000))
            throw std::invalid_argument("Dimensoes invalidas");
    }
    double area() const override { return largura_ * altura_; }
private:
    double largura_;
    double altura_;
};

class Quadrado : public Forma {
public:
    explicit Quadrado(double lado) : lado_(lado) {
        if (!(lado > 0 && lado <= 1000000))
            throw std::invalid_argument("Lado invalido");
    }
    double area() const override { return lado_ * lado_; }
private:
    double lado_;
};

int main() {
    std::vector<std::unique_ptr<Forma>> formas;
    formas.push_back(std::make_unique<Retangulo>(3.0, 4.0));
    formas.push_back(std::make_unique<Quadrado>(5.0));
    double total = 0;
    for (const auto& forma : formas) total += forma->area();
    std::cout << total << "\n";
}
```

Saída:

```text
37
```

O vetor guarda donos de `Forma` para um retângulo e um quadrado. Cada chamada `forma->area()` escolhe a implementação concreta, por isso a soma é `12 + 25 = 37`.

Usamos `const auto&` no ciclo porque um `unique_ptr` não se copia. O apontador permite chamar métodos do objeto; a propriedade exclusiva mantém-no vivo. Este desenho não exige expor os campos de cada forma.

## A regra do destrutor virtual

Quando um objeto derivado é destruído através de um apontador para a base, o destrutor da base tem de ser virtual. Caso contrário, a destruição desse objeto por `delete Base*` tem comportamento indefinido. Isto também vale para um `unique_ptr<Base>` com o destrutor habitual.

`virtual ~Forma() = default;` permite destruir primeiro a parte derivada e depois a base. Se a interface proíbe destruição pela base, outra opção de desenho é um destrutor protegido não virtual. Para uma coleção dona de formas, o destrutor público virtual é a escolha adequada.

## Ordem de construção

Uma derivada constrói primeiro a base, depois os seus membros pela ordem de declaração e finalmente executa o corpo do construtor. Em `Promocao`, `Produto(preco)` corre antes de inicializar `desconto_`. A destruição faz a ordem inversa. A derivada não inicializa diretamente campos privados da base; chama o construtor da base.

## Herança ou composição

Um quadrado pode partilhar o cálculo de área com um retângulo, mas uma interface de retângulo com setters independentes de largura e altura cria um problema. Um quadrado precisa de manter as dimensões iguais. Herdar dessa interface alteraria o contrato dos setters. No exemplo, ambos implementam `Forma` e cada tipo conserva o seu próprio invariante. A relação escolhida depende das operações públicas, não só do desenho geométrico.
