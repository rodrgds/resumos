Já sabes pedir programas à shell. Agora queres uma biblioteca com contrato claro, sem devolver endereços de variáveis que já terminaram. Como está organizado um programa em C antes de pedir serviços ao sistema?

Em C, um **apontador** é um valor que indica onde está guardado um dado, ou seja dá acesso a um objeto, mas não diz se esse objeto ainda existe nem quem o deve libertar. Antes de usares a API do sistema, ou seja as funções com que o programa pede serviços ao núcleo, acompanha os valores, os endereços e o tempo de vida dos dados.

## Do ficheiro fonte ao executável

O comando `gcc` coordena várias ferramentas. Pré-processamento expande includes e macros; compilação analisa sintaxe e tipos e gera assembly; montagem produz objetos; ligação resolve referências entre objetos e bibliotecas.

```sh
gcc -E programa.c -o programa.i
gcc -S programa.c -o programa.s
gcc -c programa.c -o programa.o
gcc programa.o -o programa
```

`-c` não liga. Se o programa usa uma função declarada mas sem definição disponível, a compilação do objeto pode passar e a ligação falhar com `undefined reference`. Um cabeçalho descreve a interface; incluir um `.h` não fornece automaticamente a implementação.

No terminal Linux, um ponto de partida é `gcc -std=c17 -Wall -Wextra -Wpedantic -g programa.c -o programa`. `-g` acrescenta informação para depuração, ou seja não corrige o programa. `-Wall` não ativa literalmente todos os avisos. Lê-os e corrige a causa. No debugger, põe um breakpoint em `main` e usa `next` e `step` para acompanhar linhas e entrar em funções.

## Programa e processo

O executável é um ficheiro com código e dados iniciais. Um processo é uma execução desse programa, com estado próprio. O mesmo executável pode dar origem a vários processos com valores diferentes nas suas variáveis.

Num modelo típico, `.text` contém código, `.data` dados estáticos inicializados e `.bss` dados estáticos inicialmente a zero. A pilha contém quadros de chamadas e muitos objetos automáticos. O heap fornece blocos com duração controlada pelo programa. Compiladores podem manter variáveis em registos; o modelo ajuda a raciocinar, mas não fixa a posição física de cada variável.

## Apontadores e passagem por valor

`&x` obtém o endereço de `x`; `*p` acede ao objeto apontado por `p`.

```c
int x = 5, y = 3;
int *p = &x;
int *q = p;
*p = 7;
p = &y;
*q = 9;
```

No fim, `x == 9` e `y == 3`. Alterar `p` não altera `q`: cada apontador guarda uma cópia do endereço. `q` continua a apontar para `x`.

C passa todos os argumentos por valor. `swap(int a, int b)` troca cópias. `swap(int *a, int *b)` também recebe cópias, mas essas cópias apontam para os objetos do chamador e permitem alterá-los com `*a` e `*b`.

Num array, `p + 1` avança um elemento, não necessariamente um byte, porque para um `int *` o avanço é `sizeof(int)` bytes. `a[i]` equivale a `*(a + i)` quando o índice é válido.

Só podes desreferenciar dentro do array. O apontador imediatamente a seguir pode servir como limite, mas não para ler um elemento.

`sizeof array / sizeof array[0]` conta elementos quando `array` ainda é um array nesse âmbito. Num parâmetro `int array[]`, o tipo ajusta-se para apontador e essa conta deixa de medir o array, por isso passa também o comprimento.

`void *` guarda um endereço de objeto sem fixar o seu tipo. É o retorno de `malloc` e o tipo do argumento de uma thread. Em C, podes atribuí-lo a um apontador para o tipo concreto antes de aceder ao objeto, sem cast. Não podes desreferenciar `void *` nem fazer a sua aritmética em C17. `void f(void)` declara uma função sem argumentos e sem retorno; em C17, `f()` numa declaração não especifica os argumentos.

## Tempo de vida e propriedade

Não devolvas `&local` de uma função, porque quando ela retorna a variável automática deixa de existir. O endereço pode continuar a ter bits aparentemente plausíveis, mas usá-lo tem comportamento indefinido. Não existe uma saída obrigatória, nem sequer a garantia de um segmentation fault.

Um bloco obtido com `malloc` continua a existir até `free`. A função que devolve esse bloco deve deixar claro quem o liberta. `malloc` não inicializa os bytes; `calloc` põe os bytes a zero. Testa `NULL` antes de escrever.

O programa escreve `original=4 copia=9`. O segundo bloco tem uma cópia do valor, não do endereço. Depois de `free`, deixa de ser válido aceder ao bloco. Atribuir `NULL` ao apontador libertado pode ajudar a detetar usos locais, mas não corrige outros apontadores que ainda guardem o endereço.

Para redimensionares, usa um temporário, porque escrever diretamente `valores = realloc(...)` perderia o endereço antigo se a operação falhasse:

```c
int *novo = realloc(valores, novo_tamanho * sizeof *valores);
if (novo == NULL) {
    /* valores continua válido, se o tamanho pedido não for zero */
} else {
    valores = novo;
}
```

Este é um excerto: confirma antes que `novo_tamanho` é positivo e que a multiplicação cabe em `size_t`. Quando tiver sucesso, o endereço antigo deixa de ser utilizável, mesmo que os bits não tenham mudado.

## Strings e estruturas

Uma string C termina em `\0`. Para guardar `"ola"`, precisas de quatro bytes. `strlen` conta bytes anteriores ao terminador; não mede a capacidade do buffer. `sizeof` de um apontador mede o apontador, não a string.

`strcmp(a, b)` devolve zero se forem iguais, negativo se `a` vier antes de `b` e positivo no caso contrário. Não exijas exatamente `-1` ou `1`. `strcpy` e `strcat` exigem espaço suficiente no destino. Para concatenar duas strings, a reserva precisa de `strlen(a) + strlen(b) + 1` bytes, depois de verificar overflow.

`strtok` modifica o buffer e mantém estado entre chamadas. Se precisares de conservar o original, faz uma cópia que possas alterar. `strsep` é uma extensão comum de UNIX, não parte de C17. Ao usar `tolower`, converte primeiro para `unsigned char` se o valor vier de um `char` que pode ser negativo.

Uma `struct` reúne campos num objeto. A atribuição de estruturas copia os campos, incluindo apenas os endereços de campos apontador. Duas estruturas que copiem o mesmo apontador ainda podem partilhar o mesmo bloco. Para objetos pequenos, devolver uma estrutura por valor evita uma reserva dinâmica e simplifica a propriedade.

## Argumentos e conversão

Em `int main(int argc, char *argv[])`, `argc` inclui o nome usado para invocar o programa. `argv[argc]` é `NULL`. Os argumentos são strings, mesmo quando escreves `42` na shell. Verifica `argc` antes de ler `argv[1]`.

`atoi` é conveniente para um exercício com entradas garantidamente válidas, mas não permite distinguir bem zero de uma conversão inválida. Para validar um inteiro, usa `strtol`, com `<stdlib.h>`, `<errno.h>` e limites adequados:

```c
errno = 0;
char *fim;
long n = strtol(argv[1], &fim, 10);
if (errno == ERANGE || fim == argv[1] || *fim != '\0') {
    /* rejeitar argumento */
}
```

`fim == argv[1]` significa que não foi convertido nenhum dígito; `*fim != '\0'` deteta texto que sobrou. Se precisas de `int`, verifica também `INT_MIN <= n <= INT_MAX`. Para um máximo de números que podem ser negativos, inicializa com o primeiro valor validado, não com zero.

## Bibliotecas e APIs

Uma API diz que funções existem, que argumentos aceitam e o que devolvem. Uma implementação cumpre esse contrato. Por exemplo, uma biblioteca de vetores pode devolver `struct vetor` por valor ou devolver `struct vetor *` que exige libertação: são contratos diferentes, mesmo que representem o mesmo vetor.

```sh
gcc -Wall -Wextra -c vetor.c
ar rcs libvetor.a vetor.o
gcc usar.c -L. -lvetor -lm -o usar
```

Um exemplo mínimo completo tem três ficheiros. O cabeçalho `vetor.h` declara a função, a implementação `vetor.c` define-a e o cliente `usar.c` chama-a e imprime o resultado:

```c
/* vetor.h */
#ifndef VETOR_H
#define VETOR_H
int soma(int a, int b);
#endif
```

```c
/* vetor.c */
#include "vetor.h"
int soma(int a, int b) {
    return a + b;
}
```

```c
/* usar.c */
#include <stdio.h>
#include "vetor.h"
int main(void) {
    int r = soma(2, 3);
    printf("2 + 3 = %d\n", r);
    return 0;
}
```

```sh
cc -std=c17 -Wall -Wextra -Wpedantic -c vetor.c
ar rcs libvetor.a vetor.o
cc -std=c17 -Wall -Wextra -Wpedantic usar.c -L. -lvetor -o usar
./usar
```

A saída observada é `2 + 3 = 5`. O cliente inclui o cabeçalho para conhecer a declaração, mas só a ligação com a biblioteca fornece a definição. A biblioteca estática fornece código ao executável na ligação. `-L.` acrescenta um diretório de pesquisa e `-lvetor` procura uma biblioteca com esse nome. A ordem importa para arquivos estáticos: põe a biblioteca depois dos objetos que usam os seus símbolos. `-lm` fornece a biblioteca matemática em ambientes que a separam.

Para uma biblioteca partilhada em Linux:

```sh
gcc -Wall -Wextra -fPIC -c vetor.c
gcc -shared vetor.o -o libvetor.so
gcc usar.c -L. -lvetor -o usar
LD_LIBRARY_PATH=. ./usar
```

Aqui distinguimos pesquisa na ligação de pesquisa durante a execução. `-L.` resolve a primeira; o carregador ainda precisa de encontrar a `.so`. A atribuição de `LD_LIBRARY_PATH` só vale para esse comando. Bibliotecas partilhadas podem permitir partilhar páginas de código e atualizar código sem reconstruir cada aplicação, mas exigem compatibilidade da interface binária.

Um apontador de função, como `int (*f)(int)`, guarda uma função com esse tipo. `f(3)` chama-a. Serve para callbacks e tabelas de operações; antes de indexar uma tabela de funções, valida o índice.

## Objetos compostos e listas

Numa biblioteca de números complexos, `struct complexo { double real, imag; };` pode representar $a+bi$. Somar `(1,2)` e `(3,-1)` dá `(4,1)`; multiplicar dá $(1\times3-2\times(-1),\;1\times(-1)+2\times3)=(5,5)$. Devolver este objeto por valor não cria uma obrigação de `free`. Se a API devolvesse um apontador para um objeto reservado, precisaria de declarar essa obrigação. O mesmo cuidado aplica-se a vetores: distinguir um vetor matemático de dimensão fixa de um array dinâmico evita misturar contratos.

Numa lista ligada, cada nó guarda um valor e o endereço do seguinte. A cabeça é `NULL` na lista vazia. Inserir no início muda o apontador da cabeça, por isso uma função recebe o seu endereço, `struct no **`. Segue os estados ao inserir 5 e depois 2 numa lista vazia: a cabeça passa de `NULL` para o nó de 5, depois para o nó de 2, que aponta para o de 5. A função escreve através de `*cabeca`, por isso a alteração sobrevive ao retorno. Passar só a cabeça por valor mudaria uma cópia local e perderia a nova lista. Este excerto requer `<stdlib.h>` e uma cabeça inicialmente nula:

```c
struct no {
    int valor;
    struct no *seguinte;
};

int inserir(struct no **cabeca, int valor) {
    struct no *novo = malloc(sizeof *novo);
    if (novo == NULL) return -1;
    novo->valor = valor;
    novo->seguinte = *cabeca;
    *cabeca = novo;
    return 0;
}

int retirar(struct no **cabeca, int *valor) {
    if (*cabeca == NULL) return -1;
    struct no *antigo = *cabeca;
    *valor = antigo->valor;
    *cabeca = antigo->seguinte;
    free(antigo);
    return 0;
}
```

Assumimos argumentos apontador válidos e uso por uma tarefa. Depois de inserir 5 e depois 2, a cadeia é `2 → 5 → NULL`. Retirar devolve 2 e deixa a cabeça no nó de 5. Guardamos `seguinte` antes de libertar: ler `antigo->seguinte` depois de `free` seria usar um objeto que já não existe. Se a reserva falhar, a cabeça conserva o valor anterior.

A lista é dona dos seus nós. Quem a destrói percorre os nós, guarda o próximo e liberta o atual. Se cada nó contivesse uma string reservada, o contrato também precisaria de dizer se a lista é dona dessa string. Copiar apenas a cabeça cria dois apontadores para os mesmos nós, não duas listas independentes. Inserir no fim exige percorrer a lista ou manter uma cauda cuja consistência também tens de preservar.
