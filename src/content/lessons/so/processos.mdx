Já vimos programas e ficheiros; esta página responde a: o que é um processo e como cria um programa outros processos?

Um processo é uma execução com identidade e estado. Dois processos podem correr o mesmo programa e usar o mesmo valor numérico de endereço virtual, ou seja o número que cada processo usa para indicar uma posição na sua própria memória, sem partilharem a variável que esse endereço designa.

## O que o núcleo guarda

O bloco de controlo do processo, ou **PCB**, representa o estado que o sistema precisa de gerir: identificador PID, relação com o pai, registos guardados, estado de execução, mapa de memória, descritores, sinais, limites e dados de escalonamento. Numa implementação real, esta informação pode estar distribuída por várias estruturas.

O espaço de endereçamento contém código e dados do programa. Não o confundas com o PCB, que é informação de gestão no núcleo. O limite teórico de um endereço com $m$ bits é $2^m$ posições, ou seja isso não significa que cada processo tenha essa quantidade de RAM atribuída.

Terminar liberta a memória de execução e outros recursos. Pode restar um registo com PID e estado de saída para o pai consultar. Esse filho é um **zombie** e já não executa instruções. Um filho vivo cujo pai terminou é **órfão**, outra situação; em Linux pode ser adotado por um subreaper ou pelo processo de inicialização.

## fork devolve duas vezes

`fork()` cria um filho. Retorna `-1` em caso de falha, 0 no filho e o PID do filho no pai. Ambos continuam depois da chamada. A variável que recebe o retorno tem valores diferentes nas duas memórias.

Os programas desta página têm uma única thread antes de `fork`. Num processo com várias threads, o filho só conserva a thread que chamou `fork`, mas pode herdar locks obtidos pelas outras. Até `exec`, só deve chamar funções seguras nesse contexto, as _async-signal-safe_; copiar o exemplo para uma aplicação multithread exige esse cuidado.

```c
int x = 4;
pid_t pid = fork();
if (pid == 0) x = 9;
```

Este é um excerto, assumindo `fork` bem-sucedido. O filho tem `x == 9`; o pai conserva `x == 4`. A cópia costuma ser implementada com _copy-on-write_: as páginas físicas podem ser partilhadas inicialmente e copiadas quando alguém escreve. A semântica dos dados privados continua a ser a de memórias separadas.

Os descritores herdados referem as mesmas descrições abertas, por isso uma leitura do pai pode avançar a posição que o filho observa. É partilha de estado do núcleo, não partilha automática de todas as variáveis C.

## Contar processos pela árvore

Se todos os processos executam três chamadas sucessivas de `fork`, temos $1 \to 2 \to 4 \to 8$ processos, incluindo o inicial, assumindo sucesso. Foram criados sete filhos no total.

Agora considera um ciclo em que cada filho termina imediatamente:

```c
for (int i = 0; i < 3; i++) {
    pid_t pid = fork();
    if (pid == 0) _exit(0);
}
```

Há um pai que faz as três iterações, por isso ficam quatro processos criados ao longo da execução, não oito. O excerto omite tratamento de falhas e recolha; serve só para desenhar a árvore. A fórmula $2^n$ depende de cada descendente chegar às chamadas seguintes.

## exec substitui, não cria

A família `exec` carrega outro programa no processo atual. Mantém o PID, mas substitui a imagem de memória, incluindo código, heap e pilha. Em caso de sucesso não retorna ao código antigo.

`execlp` recebe argumentos individuais e procura o comando no `PATH`. `execvp` recebe um vetor terminado por `NULL`, também com pesquisa no `PATH`. O primeiro argumento do novo programa costuma ser o seu nome. Passar apenas `"ls -l"` como nome não faz parsing de shell: tentaria encontrar um executável com esse nome inteiro.

Os descritores mantêm-se abertos salvo os marcados para fechar em `exec`, por exemplo com `FD_CLOEXEC` ou `O_CLOEXEC`. É isso que permite preparar redirecionamentos antes da substituição do programa.

## Esperar e interpretar o estado

`waitpid(pid, &estado, 0)` espera pelo filho indicado e recolhe o estado. `wait` escolhe um filho que termine. O estado bruto não é diretamente o código de saída: testa `WIFEXITED` antes de `WEXITSTATUS`, e `WIFSIGNALED` antes de `WTERMSIG`.

O programa seguinte executa um comando com os argumentos que receber. Guarda-o em `executar.c` e compila num terminal UNIX com `cc -std=c17 -Wall -Wextra -Wpedantic executar.c -o executar`.

```c
#define _POSIX_C_SOURCE 200809L
#include <errno.h>
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(int argc, char *argv[]) {
    if (argc < 2) {
        fprintf(stderr, "uso: %s comando [argumentos]\n", argv[0]);
        return 1;
    }
    pid_t filho = fork();
    if (filho < 0) {
        perror("fork");
        return 1;
    }
    if (filho == 0) {
        execvp(argv[1], argv + 1);
        perror("execvp");
        _exit(127);
    }
    int estado;
    pid_t r;
    do {
        r = waitpid(filho, &estado, 0);
    } while (r < 0 && errno == EINTR);
    if (r < 0) {
        perror("waitpid");
        return 1;
    }
    if (WIFEXITED(estado)) {
        printf("estado=%d\n", WEXITSTATUS(estado));
        return WEXITSTATUS(estado);
    }
    if (WIFSIGNALED(estado))
        printf("sinal=%d\n", WTERMSIG(estado));
    return 1;
}
```

`./executar printf 'ola\n'` escreve `ola` e depois `estado=0`. O `waitpid` impõe que o pai só imprime depois do fim do filho. Para um nome inexistente, `execvp` falha, o filho termina com 127 e o pai mostra esse estado. O filho não deve continuar o código da shell depois da falha.

`return` de uma função auxiliar só retorna dessa função. `exit` termina o processo, executa funções registadas com `atexit` e trata buffers stdio. `_exit` termina sem essa limpeza da biblioteca, por isso no filho que falhou antes de `exec` usa `_exit` para evitar repetir limpezas e descarregar buffers herdados do pai.

## Buffers e ordem observável

Um `printf("antes")` sem descarga antes de `fork` pode deixar bytes num buffer que será copiado. Se pai e filho terminarem com `exit`, ambos podem descarregar a cópia. Usa `fflush` antes de criar o filho quando tens saída pendente, ou prepara o programa para não a duplicar.

Uma mudança de linha não garante descarga em todas as situações: num terminal, stdout costuma ter buffer por linha; redirecionado para ficheiro, costuma ter buffer por blocos.

Duas linhas impressas por processos concorrentes não têm ordem garantida só porque aparecem nessa ordem no código de ramos diferentes. Para impores ordem, precisas de uma relação como esperar pelo fim do filho ou receber uma mensagem dele. Um `sleep` só atrasa, ou seja não prova sincronização.

## Criar vários trabalhadores

Para lançar várias tarefas em paralelo, o pai cria os filhos primeiro e espera depois. Se esperar logo em cada iteração, serializa as tarefas. Guarda os PIDs criados com sucesso, recolhe todos e verifica os estados antes de avançar para uma etapa dependente, como ligar ficheiros objeto depois de compilá-los.

Uma shell repete ler, analisar, criar, executar e recolher. Comandos internos que alteram o seu estado, como `cd` ou `exit`, ficam na própria shell. Um parser que divide apenas por espaços não suporta automaticamente aspas, expansões ou pipelines.
